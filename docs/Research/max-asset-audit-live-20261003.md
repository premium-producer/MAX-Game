# MAX — сохранение разметки в проекте и настройки экранов

Дата: 03.10.2026. Это исследование до реализации; фактические проверки и применение сервера должны быть отражены отдельным отчётом в `artifacts/reports/`.

## Установлено по существующему коду

- `artifacts/service/server.mjs` обслуживает `/max-game/` из `apps/max-game/` в обоих режимах мастера. Сейчас у редактора есть только отдельная браузерная IndexedDB; она не является общим проектным файлом и не применяется к игре.
- Все маршруты сервера сначала проверяют Host и Origin. `GET /api/state` отдаёт токен текущего процесса; мутации требуют `x-vk-token`. Токен нельзя сохранять в отчётах или пользовательском JSON.
- `/api/max-game/v1` передаётся в лениво запускаемый backend, который может быть отключён. Не следует активировать игровую сессию ради редактора.
- `ProjectStore` имеет контроль ревизии, но использует собственный синхронный `atomicJSON`: временный файл и rename без fsync/retry. Не расширять этот механизм для нового редактора.
- Существующий SQLite PersistencePort реализован на `node:sqlite` в worker, но принимает именно игровые записи и имеет специальные таблицы сессий/импорта. Это не универсальное хранилище редактора: притворная игровая запись повредит разделение данных.

## Рекомендуемый готовый механизм

Для небольшого общего JSON — `atomically@2.1.1`, MIT. Библиотека сама выполняет атомарную замену файла, очередь записей одного пути и повтор временных ошибок файловой системы. Использовать асинхронный `writeFile` с ожиданием fsync (оба параметра по умолчанию включены), отвечать «Сохранено в проекте» только после resolve. Документация описывает повтор EPERM/EBUSY и предел ожидания 7500 мс. Это готовая реализация проблемной записи, а не ссылка для собственного temp/rename. [README](https://github.com/fabiospampinato/atomically), [package.json версии 2.1.1](https://raw.githubusercontent.com/fabiospampinato/atomically/master/package.json).

README содержит устаревшее заявление о нуле зависимостей: текущий package.json указывает `stubborn-fs` и `when-exit`. Версии дерева нужно закрепить lock-файлом, лицензии включить в комплект. Подтверждённый пример внедрения — `conf@15.1.0` использует `atomically ^2.0.3`; это доказывает применение библиотеки в менеджере конфигурации, но не подтверждает работу нашего HTTP-протокола. [Зависимости conf](https://raw.githubusercontent.com/sindresorhus/conf/main/package.json).

Альтернатива `write-file-atomic` предоставляет fsync и последовательные записи одного файла, лицензия ISC. В реальном issue #49 описан Windows EPERM при записи JSON в Electron; в `graceful-fs` #104 описан аналогичный сбой при параллельных HTTP-запросах. Эти старые случаи не доказывают дефект текущей версии, но подтверждают необходимость проверки Windows и готового retry. Поэтому для этой задачи предпочтён atomically. [Документация](https://github.com/npm/write-file-atomic), [Electron/Windows issue #49](https://github.com/npm/write-file-atomic/issues/49), [параллельные запросы issue #104](https://github.com/isaacs/node-graceful-fs/issues/104).

Ограничения: атомарная запись не выполняет сравнение ревизий, не объединяет изменения разных клиентов и не является межпроцессным lock. Для нашего мастера один процесс является владельцем файла; проектная валидация и проверка ожидаемой ревизии должны происходить внутри последовательной обработки мутации. При конфликте нельзя молча перезаписывать чужой снимок. Не менять файл внешним редактором одновременно с открытой разметкой. Открытое upstream предложение об отбрасывании промежуточных записей также означает, что эту оптимизацию нельзя считать гарантированной возможностью библиотеки. [Issue #2](https://github.com/fabiospampinato/atomically/issues/2).

## Минимальный контракт интеграции

Предлагаемый отдельный маршрут: `GET /api/max-asset-audit` и `POST /api/max-asset-audit`. Добавить до общего запрета методов API; сохранить существующие Host/Origin/token проверки. Точное имя маршрута фиксируется реализацией, здесь это рекомендация.

Хранилище — отдельный JSON в `apps/stand-service/configs/`, например `max-asset-audit.json`, включённый в переносимый комплект и сохраняемый сборкой. В записи нужны schema/contentRevision, ревизия сохранения, геометрия по screenId/actionId, assetId/SHA и свойства экранов. Сырой каталог, ассеты, игровые сессии и их IDB/SQLite не изменять.

Редактор должен различать «сохраняется», подтверждённую запись и ошибку. IndexedDB можно сохранить как черновик на случай недоступного сервера; наличие черновика нельзя отображать как подтверждение серверной записи. Экспорт остаётся необязательным резервом. После рестарта токен перечитывается. Один удачный запрос не должен скрывать другое ещё не сохранённое изменение.

Для активности и финального экрана необходимы стабильные идентификаторы, а не индексы карточек. Неактивный экран сохраняет свою разметку. Смысл «финального» явно обозначить в интерфейсе: финальный экран задания либо финальный экран всей миссии — разные переходы. Не считать пустой список экранов завершённой миссией; неактивный финал и несколько несовместимых финалов должны отвергаться/разрешаться явным правилом. Применение настроек к проигрыванию — отдельный потребитель этих же данных, и его наличие нужно подтвердить кодом и реальным сценарием, а не только флажком редактора.

## Доставка без расширения зоны изменений

`artifacts/web/tools/build_service_slice.py` позволяет применить только выбранные JS/MJS-модули относительно сохранённого baseline и обновить manifest. Нужны исходники до правки в `artifacts/workspace/backups/`; существующий runtime должен совпадать со своим manifest. Новый модуль в уже существующей `max-game/` также попадает в полный `build_service.py` через glob. Зависимость можно собрать в выделенный server bundle штатным esbuild; не устанавливать/обновлять Electron только ради небольшой библиотеки.

Новый HTTP-маршрут требует загрузки нового `server.mjs`: перезагрузка страницы или сборка файлов его не активирует. По `vk-master-startup` нужен штатный Stop/Start через `apps/STARTUP`, с сохранением текущего режима. Это затронет общий мастер, поэтому нельзя выдавать такой restart за перезапуск только MAX. Перед применением согласовать с основной задачей/активными владельцами; не создавать отдельный произвольный сервер на другом порту для обхода правила. После применения — реальный GET/POST, reload и проверка файла; токены не выводить.

## Короткая проверка реализации

1. Изменить рамку → дождаться подтверждения → новый клиент/перезагрузка получает ту же геометрию из сервера без экспорта.
2. Два запроса со старой ревизией не затирают подтверждённые изменения; ошибка записи не меняет память на неподтверждённое состояние.
3. Активность/финал сохраняются независимо от рамки, не исчезают при смене действия и работают в назначенном контексте задания.
4. После штатного рестарта тот же документ читается; исходные игровые сессии не изменены. Короткая проверка actual page и консоли завершает технический цикл.
