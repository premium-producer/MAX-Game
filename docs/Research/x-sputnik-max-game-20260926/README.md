## Как устроена игра

Игрок последовательно проходит стартовый экран, обучение, карту миссий, игровую попытку и финал. Миссии открываются после успешного выполнения предыдущих. Игрок выбирает оборудование, ставит его на Землю, меняет положение/высоту спутников и поворачивает глобус. Система автоматически проверяет маршрут. Таймер, повтор попытки, результаты и доступность миссий управляются состоянием приложения.

| Слой | Реализация и вывод |
|---|---|
| Глобальное состояние | `game-state.mjs`: переходы экранов и открытие миссий; удобно тестировать без WebGL |
| Попытка | `mission-game.mjs`: размещения, инвентарь, время, результат; отдельный жизненный цикл |
| Правила | `mission-evaluation.mjs`: вычисление связей, условия all/any/not/atLeast, привязки ролей; ограниченный поиск 4096 шагами |
| Проекция и маршрут | `screen-connectivity.mjs`, `route-layout.mjs`: снимки сцены, порядок узлов и нижняя полоса должны согласовываться |
| 3D | `webgl-field.js`: одна сохраняемая сцена/камера/renderer между экранами, GPU-эффекты и оборудование |
| Представление | `main.js`, CSS, JSON оболочки: DOM, обработчики ввода, отображение состояния |
| Данные | Каталог и JSON миссий, wording, параметры Земли/камер/оболочки, локальные ассеты |

Важная особенность: production-миссии используют **hybrid**, а не только физическое расстояние на сфере. Наземные пары связаны по мировой геометрии; пары с орбитальными узлами — по экранной проекции. Изменение камеры может изменить игровую связность. Это часть исходной механики, сохранённая в MAX. Заменять её обычным поиском кратчайшего пути без отдельного продуктового решения нельзя.

Для победы недостаточно визуально пересечь линии: устройство пробуждается через 350 мс, соединение удерживается 300 мс, снимок проекции должен быть свежим (до 120 мс) и соответствовать текущим размещениям. Перетаскивание, скрытие страницы и устаревший снимок сбрасывают удержание. Внизу показывается тот же логический порядок, который использует evaluator. Эти ограничения объясняют, почему перенос одного красивого `webgl-field.js` не даёт работающую игру.

Три миссии: первое подключение к интернету (120 с), арктический маршрут с орбитальным оборудованием (150 с), соединение большой страны через ядро сети (90 с). Сохранены исходные конфигурации правил и географические стартовые условия. Утверждений о реальных спутниковых сервисах MAX не добавлено.

## Вёрстка и motion

Оболочка проектируется в 1920×1080 и масштабируется целиком с сохранением пропорций. Шапка, рамка сцены, правая панель оборудования и нижний маршрут задаются согласованным JSON. DOM-текст и интерактивные элементы накладываются на одну WebGL-сцену. На узком/высоком экране это даёт поля и более мелкие элементы, а не отдельную мобильную вёрстку.

Камера и Земля сохраняются между экранами, меняются их состояние и презентация. Motion использует CSS/WAAPI и собственные обновления; наличие GSAP-рекомендаций среди skills не означает GSAP в runtime. В реализации есть WebGL RAF и отдельный RAF DOM-маркеров карты. Правило skills про общий цикл — ориентир для развития, а не буквальное описание всех текущих обновлений.

Загрузка включает локальные данные/ассеты, шрифты, подготовку аудио и прогрев GPU. Финальный статус загрузки нельзя подменять скачиванием JS: тяжёлая сцена ещё должна подготовиться. В MVP оставлен этот порядок; внешние редакторы, их панели и ассеты не нужны игроку и не перенесены.

## Какие skills полезны

Источник таблицы — `.agents/skills/` исходного X-SPUTNIK. Skills прочитаны вместе с относящимися к ним references; продуктовые ограничения исходника не считаются новой инструкцией для пользователя MAX.

| `x-sputnik-performance-budget` | Ограничение буфера/качества, разделение загрузки и подготовки GPU | Обещание FPS без целевого устройства |
| `x-sputnik-three-effects` | Согласование bloom, Земли и HUD; локальная настройка эффектов | Чужую палитру как «фирменную MAX» |
| `x-sputnik-visual-qa` | Короткая проверка состояния, пропорций, читаемости и консоли | Многоступенчатые screenshot-прогоны вопреки запросу пользователя |
| `threejs` | Жизненный цикл ресурсов, камера/геометрия, осмысленная работа с Three | Версию зависимостей из текста без сверки lockfile |

## Что сделано в MVP

Перенесена замкнутая цепочка runtime-модулей и нужные локальные карты Земли, маски, аудио, схемы и пиктограммы. Исключены редакторы, старые QR/каналы, Bureau-шрифты, старые логотипы, reference-скриншоты и неиспользуемые альтернативные карты. Итоговый объём и контрольные суммы — в техническом отчёте.

Добавлены официальный белый монохромный логотип, Max Sans, градиент Main с тремя исходными точками, тёмные панели, фиолетовая Земля и голубые акценты. Старт и финал переписаны под «Космос на связи». Оборудование, задания и логика связи остаются космическими. Зелёный/красный используются для функциональных статусов; это не новые фирменные цвета.

Брендинг организован слоями: проверенный пакет MAX → локальные ассеты/tokens → `max-theme.css` → параметры визуальной сцены в JSON → тексты. У бренда нет собственного evaluator. Такой подход позволяет менять оформление без размножения механики. В текущем MVP это отдельная поставка, а не универсальный переключатель брендов на лету.

Three.js 0.185.1 из исходника изолирован в bundle, не заменяет Three других приложений. Устранены обнаруженные предупреждения deprecated Clock и SVGLoader.createShapes: применены Timer и эквивалентный ShapePath.toShapes. Основные модули правил не переписывались ради ребрендинга.

Добавлены самостоятельный localhost-сервер с повторным использованием своего процесса, маршрут `/max-game/` в мастере, пункт навигации и включение игры в сборщик полного переносимого комплекта. Источники — `artifacts/max-game`, готовая игра и её документация — `apps/max-game`. Никаких зависимостей runtime от абсолютного пути исходного X-Спутника нет.

## Как развивать дальше

1. Принять визуальную подачу и сложность трёх сохранённых миссий на реальном сенсорном экране. Это следующий продуктовый шаг; CPU-тесты не заменяют пользовательскую проверку.
2. Уточнить сценарий стенда: отдельный игрок у экрана, ограничение сессии, возврат в attract mode, необходимость сохранения результата и события для других экранов.
3. После этого реализовать адаптер жизненного цикла игры к Stand Service: запуск/остановка/сброс, готовность, назначение поверхности и при необходимости Spout. Сейчас игра — интерактивная веб-страница в составе мастера, не экранный worker.
4. Новые миссии добавлять через данные и тесты правил; готовый renderer переиспользовать. При изменении hybrid-механики отдельно пересматривать evaluator, снимки проекций и нижний маршрут.
5. Для следующего брендбука повторять curate → tokens/assets → theme/content → сборка → короткая проверка, сохраняя evidence каждого брендового решения. Пакет MAX стал первой реальной интеграцией ранее подготовленного брендового pipeline.
