Ниже — подтверждённое поведение кода в детерминированных сценариях; частота этих сценариев в пользовательской сессии пока не измерена.

## Подтверждённые причины

1. **Остановка CTA пропускает ожидающие ваншоты.** AudioDirector.trigger вызывает playOneShot асинхронно; AudioEngine регистрирует voice только после await initialize/loadAsset. stopAllOneShots видит только зарегистрированные voices. Событие, принятое до CTA и ещё ожидающее продолжения, запускается после остановки. Воспроизведение: принять navigation-back, в том же стеке войти на CTA, разрешить microtasks — стартуют оба файла. Это возможно даже при закэшированных buffers. Обычное новое событие, поступившее непосредственно во время действующего lock, правильно отклоняется.

2. **Lock использует время запроса, а не фактическое воспроизведение CTA.** blockOneShotsUntil = Date.now() + 6800 задаётся до запуска source. При задержке старта на 200 мс новый camera-orbit разрешён на 6801-й мс, когда CTA звучит всего 6601 мс. Мастер CTA длится 6679 мс по sound-event-map; duration контейнера WebM — 6687 мс. При скрытии вкладки AudioContext останавливается, но Date.now продолжает идти: после 10 секунд скрытия lock уже истёк, а CTA ещё не доиграл. Повторной проверки эксклюзивности непосредственно перед source.start нет.

3. **Ваншот молча пропускается после задержки более 350 мс.** В playOneShot лимит maxLateStartMs проверяется после первого await. Даже с готовыми buffers синхронная работа между trigger и продолжением microtask может превысить лимит. В тесте +351 мс дают null вместо voice, хотя trigger вернул true. Нет очереди, уведомления о причине отказа или подтверждения фактического старта; lastTriggeredAt/lastVariant уже обновлены. Это подтверждённый механизм потери, но реальную длительность render на устройстве не измеряли.

4. **Не начавшийся CTA всё равно блокирует остальные звуки.** Та же задержка +351 мс приводит к пропуску CTA, но блокировка остаётся: ещё 6449 мс обычные ваншоты отвергаются. Правило не связано с успешным созданием voice или завершением source.

5. **Первый переход может обогнать unlock.** Capture keydown вызывает async unlock, а обработчик Enter/Space может в том же событии выполнить переход CTA → ONBOARDING. Primary отклоняется из-за pendingScreenEntry, enterScreen очищает pending до завершения unlock. После разблокировки не звучат ни CTA entry, ни primary. Воспроизведено на последовательности реальных adapter/director вызовов; не утверждается для каждого pointer-click, где между pointerdown и click обычно есть время.

6. **Новый ваншот может возобновить скрытую вкладку.** trigger не проверяет hidden, а playOneShot вызывает context.resume, если engine.unlocked и state=suspended. После handleVisibility(true) событие game.popup.error возвращает context в running при director.hidden=true. Таймерные/отложенные события могут обойти lifecycle; частота таких событий в скрытой игре не измерена.

7. **Попап завершения всех миссий всегда теряет свой звук.** renderMissionSelect вызывает showOutcomePopup с kind=success/action=finish. Adapter выбирает game.popup.success, но screens этого события в audio.json содержит только MISSION_PLAY. На MISSION_SELECT trigger возвращает false независимо от загрузки или производительности.

## Штатные ограничения, которые тоже слышны как обрыв

- camera-orbit: cooldown 180 мс, hover: 300 мс, placement/move: 80 мс. Повтор раньше cooldown сознательно отклоняется.
- Для этих событий maxInstances=1: новое воспроизведение гасит предыдущий экземпляр за 80 мс. В частности hover-семпл длится около 3 секунд, поэтому быстрый переход между карточками не даёт ему закончиться. Это действующая политика, её изменение требует отдельного решения по миксу.
- Переходы на CTA намеренно отдают приоритет entry: back и end-finish не должны конкурировать с ним. Само отсутствие этих звуков при CTA-приоритете не считается найденным дефектом.

## Проверки

- Существующие audio.test.mjs: 14/14. Тест CTA использует FakeEngine с мгновенной записью вызова и не моделирует ожидающие source.start, задержки и остановку аудиочасов.
- Диагностика: tmp/audio-audit-2026-09-09.mjs, запуск из корня командой `app/runtime/win-x64/node.exe tmp/audio-audit-2026-09-09.mjs`. Восемь сценариев: перечисленные причины, с отдельными проверками задержки CTA и скрытия. Assertions фиксируют текущее ошибочное поведение; это диагностический скрипт, а не регрессионный suite правильного поведения.
- HTTP: 21/21 runtime audio-файл возвращает 200, байты совпадают с dist. Манифест одинаков в public/dist/HTTP; HTTP app.js совпадает с dist по SHA-256. Отсутствующие файлы и устаревшая серверная копия этих ресурсов не подтверждены. Уже открытая вкладка отдельно не инспектировалась.
