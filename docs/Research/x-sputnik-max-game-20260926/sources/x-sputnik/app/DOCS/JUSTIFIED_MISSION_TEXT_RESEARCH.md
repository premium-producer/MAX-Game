# Выключка описаний миссий по ширине

**Принято пользователем 2026-09-08:** adaptive является основным видом, доступным по обычному `/`. `left`, `justify`, `justify-4` — дополнительные. Решение реализовано в adaptive-default-167, сохранено в ui-shell и отражено в редакторе.

Актуальное уточнение пользователя, 2026-09-08: **приоритет — обязательная выключка по ширине**. В `mission-text-justify-165` адаптивный режим больше не возвращает текст к левому краю. Он проверяет все 13 ширин и выбирает минимальный максимальный межсловный интервал среди вариантов без переполнения; близость к исходной ширине — только дополнительный критерий при равных интервалах. Лимит переносов 4+4 и диапазон ±24 px сохранены. Прежние предложения и реализация fallback слева ниже являются историей и отменены этим уточнением. Последняя строка абзаца, как и прежде, не растягивается.

Дата исследования: 2026-09-08. Первый вариант реализован как альтернатива в `mission-text-layout-161`; исследовательские основания ниже сохранены.

## Реализация после исследования

По следующему прямому запросу пользователя режим распространён на `.mission-description` и `.mission-summary` в карточках выбора. Опциональный `ui-shell.typography.missionTextLayout` принимает `left` (исходный вид и default старых файлов) или `justify`. Редактор миссий содержит выбор «Описания миссий и карточек», сохранение общей кнопкой и две ссылки сравнения. `?textLayout=left` / `?textLayout=justify` переопределяет вид только открытой вкладки, не записывая настройку.

Включены русские нативные переносы `6 3 2`, последние строки start; пользовательские переводы строк и wording сохранены. В альтернативном режиме автоматические sentence-break для этих двух компонентов не создаются; прежние сгенерированные `<br>` удаляются без затрагивания авторских. Layout-аудит учитывает прямоугольники фрагментов перенесённого слова, а не общий bounding box.

Настройка проходит серверный parser/serializer, public/dist, черновик и экспорт редактора; старая вкладка без поля не стирает уже сохранённый выбор. Изолированный тест проверяет сохранение обоих режимов, перезагрузку, редактор Земли/банк/старый payload и побайтовую сохранность wording. 39/39 профильных тестов, check/build/portable и read-only HTTP прошли. Два устаревших ожидания тестов камеры приведены к существующим нормализованным defaults и resolveMissionEarthOrbit; поведение камеры не менялось.

Сервер localhost:4174 перезапущен с новым модулем сохранения. Пользовательская визуальная приёмка переносов на целевом браузере ожидается. Нативный режим не гарантирует отсутствие любых больших интервалов для произвольного нового текста; словарь-polyfill и автоматический подбор строк пока не добавлялись.

Запрос: выровнять верхние правые описания трёх миссий по ширине с корректными русскими переносами, избегая больших пробелов. Текст должен оставаться редактируемым. Формулировки, пустая строка перед «Задача:» и заданный пользователем перевод строки перед «Для этого» сохраняются.

## Вывод и выбор для проекта

Рекомендуется начать с нативной выключки и русских автопереносов, применённых только к `.mission-description`. Это небольшое изменение без новой зависимости. Однако идеально ровные края и ограниченные пробелы для любого текста при фиксированных ширине и шрифте нельзя гарантировать одной CSS-настройкой. При недостатке допустимых переносов придётся выбирать: изменить композицию, использовать более сложный подбор строк либо допустить свободный правый край проблемного абзаца.

Сначала проверить все три текущих описания на целевом игровом ПК. Если словарь недоступен — рассмотреть локальный словарь переносов. Если словарь работает, но остаются плохие строки, нужен контроль композиции, а не ещё одна библиотека расстановки переносов. Это разные задачи.

## Что обнаружено в проекте

- `src/styles.css`: у `.mission-description` ширина 300 px, внутренние отступы по 16 px; при глобальном `border-box` текстовая область составляет 268 CSS px. Шрифт Bureau 1440 Text, 13 px, интерлиньяж 1.35. Это параметры исходной вёрстки, не измерения скриншота.
- Профиль `.ui-copy-body` задаёт `hyphens: none`, `text-wrap: pretty`, `overflow-wrap: break-word`. Сейчас корректные внутрисловные переносы запрещены.
- `index.html` уже содержит `lang="ru"`.
- `main.js`, `missionDescriptionHtml`: всё описание выводится одним `<p>`, метки перед двоеточием выделяются через `<strong>`. `white-space: pre-line` сохраняет авторские переводы строк.
- `src/typography.mjs`: однобуквенные слова связываются с последующим словом неразрывным пробелом. Для профиля body дополнительные двухбуквенные предлоги не связываются. Не следует расширять эти ограничения: каждое убирает возможность разрыва строки.
- `balanceShortSentenceStarts` добавляет автоматические `<br>` при коротком начале следующего предложения на предыдущей строке. Для выравниваемых по ширине описаний следует исключить эту эвристику или переработать её: случайные принудительные окончания строк мешают композиции. Авторские переносы остаются.
- `renderedWordLines` измеряет слово единым Range. При переносе слова на две строки его общий прямоугольник уже не соответствует одной строке. Для будущей проверки интервалов нужен анализ отдельных фрагментов через `getClientRects()` и границ символов.

## Практики и основания

### Корректные переносы определяются языком

`hyphens: auto` требует языка и доступного словаря; поддержка CSS-свойства сама по себе не доказывает наличие русского словаря. `CSS.supports()` также не проверяет словарь. В актуальных данных MDN русский указан для Chrome с версии 112, Edge наследует поддержку Chromium. Версия и результат на игровом ПК в этом исследовании не проверялись. [MDN: hyphens](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/hyphens), [данные совместимости MDN, language_russian](https://raw.githubusercontent.com/mdn/browser-compat-data/main/css/properties/hyphens.json).

Переносить «через каждые N букв» нельзя. Русские правила запрещают, например, оставлять одну букву, отделять ь/ъ от предшествующей согласной; переносы аббревиатур также ограничены. Нужны языковые правила и проверка терминов/географических названий. [Академические правила переноса на Грамоте](https://gramota.ru/biblioteka/spravochniki/pravila-russkoy-orfografii-i-punktuatsii/pravila-perenosa).

`hyphenate-limit-chars: 6 3 2` — возможная стартовая настройка: слова от шести символов, минимум три до переноса и два после. Это предлагаемая настройка проекта, не орфографическая норма; сравнить с менее строгой `5 2 2`, если переносов недостаточно. Ужесточение ограничений может увеличить пробелы. [MDN: hyphenate-limit-chars](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/hyphenate-limit-chars).

### Последняя строка и абзацы

Последнюю строку абзаца не нужно растягивать: `text-align-last: start`. Свойство действует также перед принудительным разрывом строки. Поэтому заданные автором переводы строки не создадут растянутую строку из двух слов, но частые автоматические `<br>` будут оставлять неровные края. [MDN: text-align-last](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-align-last).

Для первого небольшого изменения можно сохранить существующий `pre-line`. Если вводить абзацную диагностику, лучше разбирать двойной перевод строки в отдельные `<p>` внутри контейнера, одинарный — в авторский `<br>`. Нельзя вкладывать `<p>` в `<p>`. Межабзацный отступ перед задачей должен соответствовать одной пустой строке, а не сумме стандартных margin браузера.

### Pretty помогает, но не гарантирует качество

Chrome описывает `pretty` как улучшение разбивки строк, в том числе при выключке по ширине, с акцентом на короткую последнюю строку. WebKit отдельно подчёркивает различия алгоритмов браузеров. Поэтому сохранить `pretty` разумно, но считать его гарантией отсутствия «коридоров» пробелов нельзя. `balance` также не является средством ограничения максимального межсловного интервала. [Chrome: text-wrap pretty](https://developer.chrome.com/blog/css-text-wrap-pretty), [объяснение WebKit](https://webkit.org/blog/16547/better-typography-with-text-wrap-pretty/).

`text-justify: inter-word` задаёт способ распределения пробелов, а не их верхний предел; поддержка свойства ограничена. Не делать его условием работы. Отрицательный `word-spacing`, растягивание букв и `word-break: break-all` не решают языковую задачу. [CSS Text 3: justification](https://www.w3.org/TR/css-text-3/#justification), [MDN: text-justify](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-justify).

### Читаемость

Выключка по ширине — оформительский выбор, а не универсальная рекомендация для экранного текста. W3C связывает неравномерные пробелы с затруднениями чтения. Критерий 1.4.8 относится к уровню AAA и предусматривает возможность получить текст без такой выключки; это не общий запрет в рамках AA. Для этой узкой колонки качество нужно оценивать по реальному набору, а не только по ровному краю. [W3C: Visual Presentation](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation.html).

## Варианты реализации

| Вариант | Что даёт | Ограничение | Решение |
|---|---|---|---|
| CSS и словарь браузера | Автоматически работает с новым wording, минимальная сложность | Различия движков, возможны плохие строки | Первый кандидат |
| Локальный русский словарь, мягкие переносы | Контроль доступных точек разрыва, независимость от наличия словаря браузера | Дополнительные ресурсы; не оптимизирует весь абзац | Только при подтверждённой необходимости |
| Проверенные исключения для отдельных слов | Точечное исправление нежелательных переносов | Требует поддержки при изменении терминов | Дополнение к словарю |
| Подбор строк по всему абзацу с ограничением пробелов | Можно учитывать соседние строки и штрафы за переносы | Сложнее; иногда допустимой композиции вообще нет | Если нативного результата недостаточно |

Кандидат локального движка — Hyphenopoly: предоставляет браузерный polyfill и модуль Node, использует языковые шаблоны. Поставлять нужные файлы локально, без обязательного CDN; перед включением проверить лицензии кода и русского набора. Движок расставляет возможности переноса, не гарантирует ровные интервалы. [Документация автора Hyphenopoly](https://github.com/mnater/Hyphenopoly).

Мягкий перенос U+00AD показывает дефис только при фактическом разрыве. Добавлять его в производное представление, не сохранять в исходный wording и не вставлять обычные дефисы в слова. Редактор и экспорт должны получать исходный текст. Генерацию повторять после изменения текста; операции должны быть идемпотентными. При `hyphens: manual` и U+00AD ограничения длины частей нужно обеспечивать самим генератором.

## Предложение первого изменения

Это эскиз, не применённый код:

```css
.mission-description {
  text-align: justify;
  text-align-last: start;
  hyphens: auto;
  hyphenate-limit-chars: 6 3 2;
  word-break: normal;
  overflow-wrap: normal;
  text-wrap: pretty;
}
```

Локальный селектор переопределяет запрет переносов профиля body. Не менять глобальные кнопки, карточки и заголовки. `overflow-wrap: normal` исключает аварийные разрывы в произвольном месте; переполнение чрезвычайно длинным непереносимым токеном при этом нужно обнаружить, а не скрывать. Существующий `lang="ru"` сохранить.

Перед применением исключить описания из автоматической вставки sentence-break; сохранить авторские переводы строк, формулировки и отдельный абзац задачи. При вводе абзацного представления повторно проверить выделение «Задача:» и «Небольшая подсказка:».

## Как подтвердить результат

1. Дождаться реальной загрузки Bureau, проверить текущие три описания и изменение одного из них через редактор. Сохранённый текст не должен получать служебные символы вёрстки.
2. На целевой версии Chrome/Edge проверить реальные русские переносы, включая холодный запуск без сети. Таблица совместимости этого не заменяет.
3. Сопоставить нормальный пробел Bureau с фактическими интервалами строк. Для начала помечать интервалы больше 1.5 обычного пробела как кандидаты ручной проверки; это рабочий диагностический порог, а не стандарт и не гарантия отсутствия коридоров.
4. Проверить отсутствие переполнения, одиночных букв в частях слова, случайных разрывов и чрезмерных последовательностей дефисов. Стремиться не более чем к двум переносам подряд, но не выдавать это за обеспеченное универсальным CSS-свойством ограничение.
5. Для плохого абзаца сначала ослабить допустимые ограничения переносов или добавить проверенное исключение. Если решения нет, согласовать изменение ширины либо свободный правый край. Автоматически уменьшать шрифт или переписывать формулировки не следует.
6. Если вводится измеритель, запускать его после загрузки шрифта, смены миссии, текста или ширины; не в постоянном игровом кадровом цикле. Предусмотреть однозначный fallback без повторного колебания между стилями.

Проверены исходники и опубликованные первичные источники. Браузерные измерения, интерактивная QA, изменения runtime, установка зависимостей, сборка, Git и deployment в рамках исследования не выполнялись.

## Третий тестовый вариант · mission-text-four-162

Если браузер не поддерживает ограничение, переносы отключены. Ссылка добавлена в редактор; сохраняемые left/justify и предыдущие сравнения не изменены. Более строгие ограничения могут увеличивать межсловные интервалы. 10/10 typography tests, check/build/portable и HTTP прошли; визуальная приёмка ожидается.

## Подбор ширины · mission-text-adaptive-164

Четвёртое сравнение `?textLayout=adaptive`, ссылка в редакторе. Референсы NEW-018: REF-033 и REF-034. Проверяются до 13 ширин: исходная и ±4…24 CSS px. Пробел измеряется относительно обычного пробела того же шрифта при том же масштабе; сравниваются соседние символы на одной строке. При интервале до 1.6 и отсутствии переполнения применяется ближайшая ширина. Если подходящей нет, исходная ширина/левое выравнивание всего проблемного блока. Лимит переноса 4+4, авторские абзацы, wording и привязки карточек сохранены.

Скрытая копия удаляется в finally; WeakMap кеширует текст/шрифт/исходную ширину, поэтому таймер/обычный повторный рендер не повторяет поиск. Подготовка шрифтов предшествует измерению; размеры сцены фиксированы в CSS-пикселях и масштабируются целиком. 14/14 детерминированных тестов с модельными прямоугольниками, check/build/portable и HTTP прошли. Живая браузерная вёрстка не измерялась агентом; требуется пользовательская приёмка. Это эвристический подбор, не гарантия идеальной композиции.
