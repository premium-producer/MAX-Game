# Mission System v2 — архитектура и редактирование

Дата: 2026-09-05. Документ описывает реализованный код, а не весь исследовательский backlog из [аудита](MISSION_SYSTEM_AUDIT.md).

## 1. Источники данных

```text
public/config/
  mission-system.json           каталог типов, библиотека SVG, размеры, радиусы, высоты, правила
  mission-system.schema.json    схема общих параметров
  mission-v2.schema.json        схема одной миссии
  ui-shell.json                 существующие пять экранов и ракурсы
  missions/
    index.json                  список файлов и ревизия набора
    first-signal.json
    arctic-route.json
    protected-network.json
```

`missions/index.json` — единственная точка входа игры и редактора. Порядок прохождения определяется `number`, зависимости разблокировки — `unlock.requiresCompleted`. Редактор при перестановке перенумеровывает миссии и зависимости. ID миссии становится именем файла: латиница, цифры, дефис, подчёркивание. Произвольные пути из JSON не исполняются.

Старый `public/config/missions.json` оставлен неизменным как исходник миграции и fixture тестов совместимости v1. Новая игра его **не загружает**. Не редактируйте его для настройки v2. Неиспользуемые файлы старых ID могут оставаться на диске, но вне индекса не участвуют в игре.

Единый `MissionEvaluation` возвращает `complete`, `objectives`, `paths`, `bindings`, `links`, `states`, `diagnostics`, `indeterminate`. Результат зависит от миссии, размещений, настроек и явно переданного времени. `screenX`, камера, порядок добавления и UI в расчёте v2 не используются. Интерфейс не может засчитать победу отдельно от условий: переход выполняется через reducer `CHECK`.

Во время drag интерфейс передаёт evaluator временный snapshot размещений один раз за кадр существующего WebGL-loop. Этот snapshot нужен только для немедленного отображения связей и состояний: authoritative `missionRun`, `droppedAt`, popup-сессия и история не меняются. При pointer-up reducer получает один обычный `MOVE` и повторяет тот же расчёт уже для сохранённой позиции.

## 3. Миссия: независимые части

- `endpoints`: словарь фиксированных географических точек с произвольными ID. A/Б — обычные совместимые ключи старых миссий, не зарезервированные игровые роли. Каждая точка обязана ссылаться через `icon` на запись `system.pointIcons`; отдельной текстовой сущности точки нет. Точка имеет `latitude`, `longitude`, редакторские `roles: ["start"|"finish"]` и необязательные `size`, `signalRadius`. Роли определяют принадлежность к равноправной группе начала/завершения; одна точка может иметь обе роли. Старые A/Б без `icon` мигрируют на `point-a/point-b`, роли выводятся из существующих маршрутов. Число стартовых и завершающих точек не ограничено.
- `equipmentSet`: ссылка на именованный набор в `system.equipmentSets`. Runtime-поле `inventory` вычисляется из этого набора и не сохраняется вторым источником. Для старых/независимых миссий без ссылки поддерживается локальный `inventory`. Количество должно покрывать все уникальные роли; набор — состав оборудования, не правильная последовательность.
- `topology.paths`: направленные маршруты. Каждый имеет ID, опорные `from`/`to`, список `steps: [{role, type}]`, параметры физического коридора, `endpointSelection` и `endpointSignals`. Для каждой стороны `endpointSelection.specific` использует только опорную точку, а `anyRole` рассматривает все endpoints с ролью `start` или `finish` как равноправные варианты. `endpointSignals.nearest` активирует ровно одну точку — ближайшую к крайнему размещённому объекту маршрута; `parallel` сохраняет связи от всех допустимых точек, чьи радиусы достигают объекта. Evaluator сначала применяет политику сигнала, затем выбирает наиболее собранный физический вариант и сохраняет фактически выбранные `from/to` в результате пути.
- `objectives`: отображаемые задачи с ID, текстом и составным условием.
- `completion`: дополнительное условие победы. Все задачи также обязательны.
- `objectSettings`: частичные переопределения общих параметров для этой миссии.
- `feedbackEvents.success/error`: упорядоченные авторские списки попапов. В игре отображается только крупный `title`; прежние `eyebrow/message` читаются ради совместимости, но не рендерятся и скрыты из формы редактора. У каждого события свои условие и действие; у ошибки отдельно задаётся область негативной окраски `none/invalid/matched/all`. `invalidConnection` становится активным только после появления неправильного узла с двумя физическими связями, поэтому одиночная установка не вызывает ошибку порядка. Поддерживаются выполнение миссии/задачи/маршрута, неправильное соединение и порог высоты оборудования. Полный контракт и пример — в [ERROR_SYSTEM.md](ERROR_SYSTEM.md).
- `feedback.invalid`: низкоуровневый совместимый режим evaluator. Новые миссии используют `neutral`, а пользовательскую красную индикацию включает только `feedbackEvents`, поэтому текст, логика победы и визуальный негатив больше не склеены.
- Тексты, время, mapPosition, successText, unlock и декоративное замыкание сохраняют прежнее назначение.

Общая роль в разных маршрутах требует **один и тот же экземпляр** оборудования. Разные роли не могут одновременно использовать один экземпляр. Поэтому `west-satellite-1/2/3`, `network-core`, `east-satellite-1/2/3` — разные роли даже при одинаковом типе спутника. Общий узел ветвления задаётся одинаковым ID роли в пересекающихся маршрутах.

Равноценные старты/финиши одного маршрута задаются `endpointSelection.from/to = "anyRole"`: новая точка соответствующей роли автоматически начинает работать без дублирования paths. Способ одновременной активации задаётся отдельно через `endpointSignals.from/to = "nearest" | "parallel"`, поэтому состав группы не смешивается с её поведением. Независимые направления по-прежнему задаются несколькими маршрутами. Равноценные маршруты — `any`, доставка во все — `all`, минимум N — `atLeast`. Отдельный тип «только A→Б» не существует.

## 4. Физическое соединение: geographicCorridor

В этой реализации автор задаёт направленный географический коридор от начала к концу. На сфере радиуса 3 позиции без высоты проецируются на хорду между конечными точками:

`t = dot(position − start, end − start) / |end − start|²`

Участвуют все размещения с `0 < t < 1`, чьё поперечное расстояние до хорды не больше `corridorWidth`. Они упорядочиваются по t. У каждого стартового и завершающего endpoint есть торцевая зона: если радиусы пересекаются, в маршрут дополнительно допускается один достигнутый объект, наиболее близкий к оси именно этого пути, даже при `t ≤ 0` или `t ≥ 1`. Поэтому небольшой сдвиг «за» фиксированную метку не отключает сигнал, а общая точка нескольких веток не затягивает в каждую ветку все соседние объекты. Все объекты маршрута участвуют **до проверки типов**: движок не пропускает лишний спутник ради ядра. Совпадение t в пределах `ambiguityEpsilon` означает неоднозначность, а не выбор по ID. Остальные объекты за пределами коридора не становятся звеньями данного маршрута.

Далее соседние звенья, включая обе фиксированные точки, проверяются по 3D-расстоянию с учётом высоты и суммы индивидуальных радиусов. Размещённые объекты должны проснуться (текущая задержка 700 мс). Визуальное `connectEndpointsOnComplete` **не отключает** проверку реальных концов; оно добавляет только декоративную поверхностную линию после победы.

Типы сопоставляются с конкретными позициями и ролями от начала. После первой неправильной позиции цепочка не становится зелёной за счёт совпадений типов в другом месте ответа. Обратная проверка участка от конечной точки доступна явно через `segment.anchor = end`; это позволяет собрать восточную часть отдельно, но не исправляет неправильный основной маршрут.

Визуальный статус отделён от самого факта пересечения радиусов. Узел получает `LINK` или `WRONG` только когда в рамках маршрута у него есть физическая связь с предыдущим и следующим элементом, включая фиксированную стартовую/завершающую точку на краях. При одной связи узел остаётся `BASE`; линия также остаётся нейтральной. Renderer окрашивает обычную линию только если она касается уже окрашенного узла, поэтому диагностический `correct` сам по себе не создаёт зелёный или красный участок. Декоративный link с `closing: true` является исключением: evaluator добавляет его только для полностью успешного пути, и renderer показывает его зелёным даже между двумя endpoint без node-state.

Это детерминированная модель направленных коридоров, **не универсальный поиск произвольной радиосети**. Она подходит текущей игре и нескольким направленным веткам. Для петляющих маршрутов, ручных портов, радиоканалов, препятствий/LOS и произвольных циклов требуется новый физический policy-адаптер. Эти возможности не объявлены реализованными. Роль/условия/UI отделены от policy, поэтому добавление такого адаптера не требует переписывать миссии в JS.

## 5. Условия и согласованные назначения

```json
{
  "type": "all",
  "children": [
    { "type": "path", "path": "west" },
    {
      "type": "any",
      "children": [
        { "type": "path", "path": "east-city" },
        { "type": "path", "path": "east-backup" }
      ]
    }
  ]
}
```

Поддерживаются:

- `all`, `any`, `not`, `atLeast` с `children`; для `atLeast` — `count`.
- `path` с ID маршрута; `allPaths` — все маршруты.
- `segment` с `path`, `from`, `to`, `anchor: start|end`. Позиция 0 — начало, 1…N — роли, N+1 — конечная точка; проверяются все рёбра участка. `anchor:end` выравнивает участок по конечной точке даже при несобранном начале.
- `placed` с `object` и `count`; `allPlaced` — весь заданный инвентарь.

AND и «минимум N» объединяют не только true/false, но и назначения экземпляров ролям. OR выбирает совместимое доказательство из альтернатив; невыбранная альтернатива не навязывает свои роли успешной сети. Конфликт назначений блокирует победу. Есть ограничение вложенности AST 16 и вычислительный бюджет поиска доказательств 4096 операций. При превышении — `indeterminate`, диагностика и запрет победы. Это защитные пределы сложности выражения, не ограничение на восемь объектов.

Условия задач сейчас **live**: галочка снимается при разрыве. События попапов также вычисляются из текущего состояния, но дедуплицируются на время входа в миссию. Таймовые `stableFor` и latched-цели пока не входят в контракт.

## 6. Размеры, радиусы, высоты

Общие параметры находятся в `mission-system.json.objectSettings`. Частичные настройки миссии накладываются поверх них. Размер/радиус конкретной фиксированной точки имеет последний приоритет; новые точки без переопределений наследуют профиль `endpoint:A`, точка с ID B — профиль `endpoint:B`.

`size` масштабирует 3D-маркер, ножку, основание и hit-area, но не радиопокрытие. `signalRadius` — радиус в единицах сцены, а не пикселях. У спутника есть `minAltitude`, `maxAltitude`, `defaultAltitude`, `radiusAtMinAltitude`, `radiusAtMaxAltitude`. Проверяется `min < max`, стартовая высота внутри диапазона. Между границами радиус интерполируется линейно, вне диапазона берётся крайний радиус. Допускается как рост, так и уменьшение.

В разделе оборудования банка есть пакетный блок общих параметров. Он записывает введённый `size` и/или `signalRadius` во все записи `system.objectSettings`; пустое поле не изменяет соответствующий параметр. Для орбитальных типов пакетный радиус одновременно записывается в `radiusAtMinAltitude` и `radiusAtMaxAltitude`, то есть создаёт одинаковый базовый радиус на любой высоте; после этого кривую конкретного спутника можно снова настроить индивидуально. Пакетное действие не меняет локальные `missions[*].objectSettings`. Новый тип оборудования наследует общий размер/радиус, если у существующего банка эти значения одинаковы.

Рендер и доменный расчёт используют одни параметры. Все типы с `behavior: orbital`, а не только ID `satellite`, имеют собственные границы высоты и кривую радиуса. Их reducer, перетаскивание, колесо, ручка высоты и 3D-маркер используют настройки данного типа. Точки и оборудование используют SVG-геометрию из своих банков; отдельный DOM/text-renderer для точек удалён. Основной WebGL renderer и камера остаются одними.

При миграции геопозиции, названия, время и файл ракурсов не изменялись. Радиусы A/Б в v2 намеренно уменьшены с legacy 6.5 до 0.22: значение 6.5 делало близость к точкам практически бессмысленной. Остальные исходные значения сохранены. Баланс надо проверять тестовой сборкой, а не увеличивать радиус до размера планеты ради победы.

## 6a. Общий каталог оборудования и иконок

Единственный общий банк хранится в `mission-system.json`. Страница **`object.html`** (также доступен alias `objects.html`) редактирует его отдельно от миссий. Три пользовательских раздела: оборудование, иконки фиксированных точек, наборы для миссий. Внутри данных SVG-исходники переиспользуются по ссылкам, а не копируются в каждую миссию.

```json
{
  "icons": {
    "terminal": { "label": "Терминал", "src": "./icons/terminal.svg" },
    "my-relay": {
      "label": "Моё реле",
      "svg": "<svg xmlns=\"http://www.w3.org/2000/svg\" viewBox=\"0 0 24 24\"><path fill=\"#ffffff\" d=\"M2 2H22V22H2Z\"/></svg>"
    }
  },
  "objectTypes": {
    "relay": { "label": "РЕЛЕ", "short": "РЕЛЕ", "icon": "my-relay", "behavior": "ground" }
  },
  "objectSettings": { "relay": { "size": 1, "signalRadius": 0.46 } },
  "pointIcons": ["terminal"],
  "equipmentSets": {
    "set-1": { "label": "Набор 1", "inventory": { "relay": 2 } },
    "set-2": { "label": "Набор 2", "inventory": { "relay": 5 } }
  }
}
```

Это фрагмент, не замена полного system: `schemaVersion`, connection/feedback и используемые остальными миссиями типы необходимо сохранить.

- `objectTypes.<id>` — определение типа оборудования. Видимое название едино: редактор изменяет `short` и синхронизирует legacy-поле `label` с тем же значением, поэтому карточка, селекторы и наборы не могут показать две разные подписи. `icon` — ссылка в общий `icons`; `behavior` — наземный `ground` или высотный `orbital`. Изменение иконки/названия не меняет ID и правила. Изменение определения действует во всех миссиях.
- `pointIcons` — список SVG-ID, образующих отдельный пользовательский банк обозначений начальных/конечных точек. `icons[id].label` служит только внутренним названием для поиска и выбора в банке; рядом с самой точкой в игре оно не выводится. Графика хранится в `src/svg`. Оборудование не появляется в этом списке автоматически. Для совместимости ранее назначенные точкам SVG добавляются в банк при нормализации. В `editor.html` выбирается готовая иконка, загрузка SVG производится только на странице банка.
- `equipmentSets.<id>` — имя и словарь количеств объектов банка. Один объект входит в несколько наборов по одному стабильному ID; дублирование набора копирует количества, не определения. Пустой неиспользуемый набор можно сохранить как заготовку. Миссия выбирает `equipmentSet: "set-1"`; изменение набора применяется ко всем связанным миссиям. Список использования показан на странице набора. 0 исключает объект. Некорректное/недостаточное для ролей количество блокирует запись всего проекта, а не создаёт неиграбельную миссию молча.
- Отказ от общей ссылки в редакторе копирует **текущий** состав в локальный inventory; последующие изменения набора на эту миссию не влияют. Локальный режим оставлен для совместимости. Сохранение связанной миссии всегда удаляет derived inventory из JSON, даже если старый UI-кеш содержал другое значение.
- `objectSettings.<id>` — физические размеры/радиусы/высоты. Типы больше не ограничены пятью JS-константами. Удаление используемого типа блокируется до изменения инвентаря, ролей и условий. ID существующего типа стабилен; для нового определения создаётся или дублируется тип с новым ID.
- `inventory.<id>`, `steps[].type` и `placed.object` ссылаются на этот каталог. Новый объект появляется в меню конкретной миссии, когда ему задано количество > 0. Список прокручивается при большом числе типов. Наземные/высотные — два реализованных поведения, не произвольный исполняемый скрипт из JSON.
- Фиксированная точка обязана использовать `icon` из `pointIcons`: например `"city": {"icon":"city-marker","roles":["finish"],"latitude":55.8,"longitude":49.1}`. В WebGL и начале/конце footer отображается только SVG. Название самой записи банка служит для поиска и выбора в редакторе, но не рисуется рядом с точкой. Иконка не добавляет оборудование в инвентарь и не влияет на маршрутную роль.
- `src` допускает только комплектные SVG. Пользовательские SVG импортируются как текст `svg` в JSON, без внешних URL, файловых путей и отдельной загрузки в Downloads. Библиотека переносится вместе с конфигом и попадает в тот же backup. Замена SVG оборудования не меняет графику другого объекта/иконки точки, даже если прежде они ссылались на один исходник. Замена SVG записи банка точек, напротив, изменяет **эту общую иконку** во всех использующих её точках; использование показано перед редактированием.
- Поддерживаются `svg/g/path/rect/circle/ellipse/line/polyline/polygon`, fill/stroke и transforms. Текст нужно перевести в кривые. Скрипты, обработчики событий, ссылки, raster image, style/CSS, маски, фильтры, clipPath, use и полупрозрачные контуры отклоняются с объяснением. Это редактор монохромных пиктограмм: fill/stroke нормализуются в белый; цвет на карте определяется состоянием узла. Ограничения: 128 КБ на SVG, 1 МБ исходников библиотеки, 160 символов для имени/надписи типа. Это ограничения данных, не Full-HD/4K-разрешения.
- Импорт перед добавлением в историю проверяет реальную SVG-геометрию. Сервер повторно валидирует безопасный формат и все ссылки. DOM показывает тот же нормализованный SVG; WebGL строит кешированную геометрию. Редактор меняет иконки существующих узлов без пересоздания Земли; неиспользуемая геометрия освобождается. При смене ground/orbital перестраивается только данный узел.

Старый v2 system без этих словарей получает пять прежних определений и комплектные иконки для совместимости. Новое сохранение записывает словари явно. Legacy-профили `endpoint:A/B` сохранены только как значения размера/радиуса по умолчанию; они не ограничивают имена, иконки или число точек.

## 7. Рабочий процесс редактора

Сначала открыть **`object.html`**:

1. «Оборудование»: создать/дублировать объект, назначить название, SVG, размещение и физические параметры. Над списком индивидуальных параметров можно одним действием применить размер маркера и радиус сигнала ко всему оборудованию.
2. «Иконки точек»: подготовить отдельные именованные SVG-обозначения; это не игровое оборудование и не инвентарь.
3. «Наборы для миссий»: создать/дублировать именованный набор, задать количества объектов общего банка. Видно, какие миссии используют набор.
4. Нажать «Сохранить изменения». Записывается проект с backup; нет экспорта в Downloads. У банка отдельный IndexedDB-черновик `object-bank`, undo/redo и поиск. Удаление используемых объектов, иконок и наборов запрещено до изменения ссылок.

Затем перейти в **`editor.html`**. В нём больше нет редактора общего банка и импорта SVG:

1. Выбрать/добавить миссию. Задать тексты, время, разблокировку.
2. Над вьюпортом открыть «СТАРТОВЫЕ ТОЧКИ» или «ЗАВЕРШАЮЩИЕ ТОЧКИ». Палитра показывает созданные точки и весь банк SVG; нажатие на иконку создаёт новый уникальный endpoint выбранной роли и сразу включает размещение кликом по Земле. Одну и ту же иконку можно использовать сколько угодно раз. У каждой созданной точки есть кнопка удаления; если она участвует в маршруте, редактор автоматически переключает маршрут на другую точку той же роли, а при отсутствии замены просит сначала добавить её. В инспекторе доступны обе роли, иконка, координаты, размер, радиус и переименование ID.
3. «Развернуть схемы» → добавить маршруты, выбрать начало/конец, добавить роли, типы и переставить стрелками. Общие ID ролей означают общие узлы. Ширина коридора и допуск доступны у каждого маршрута.
4. Выбрать общий набор оборудования. Его состав показывается только для чтения со ссылкой на банк. При необходимости отсоединить набор в локальный режим; только там доступны ручные количества и «По уникальным ролям». Изменения последовательности не переписывают набор автоматически.
5. Собрать задачи и условие победы вложенными формами. Выбрать красное/нейтральное оформление ошибки.
6. В разделе размеров/радиусов задать переопределения этой миссии. Общие физические параметры оборудования редактируются в банке. Очистка локального поля возвращает наследование.
7. «Тест сети во вьюпорте» → выбрать оборудование → разместить/перетащить/изменить высоту. Диагностика и галочки используют тот же evaluator, что игра. Тест не изменяет миссию и не записывает тестовые размещения в JSON; таймер в тесте не идёт. «Сбросить тест» очищает сеть.
8. «Сохранить изменения» сохраняет полный набор и текущий ракурс выбранного state. Открытая игра получает уведомление обновления. Undo/redo и локальный черновик включают правила и параметры.

При некорректной промежуточной форме предпросмотр приостанавливается, последняя корректная сцена остаётся. Ошибки блокируют запись. Ввод не заменяется молча дефолтами. Старые черновики v1 не применяются поверх v2 автоматически.

Локальные правки размеров/радиусов сохраняют тестовые размещения. Если меняются высотные границы размещённого типа, тестовая сеть сбрасывается с уведомлением. После записи отдельного банка чистый редактор перечитывает проект целиком; тестовая сеть не является сохраняемой частью миссии и не переживает такую перезагрузку. Миссия и ракурсы не удаляются.

## 8. Запись и целостность

Сервер остаётся локальным (`127.0.0.1:4174`, `START-EDITOR-WINDOWS.bat`). Запрос содержит полный каталог v2, `revision` и `shellConfig`.

1. Сериализованная очередь запросов, нормализация всего набора до записи.
2. Проверка ревизии с диска. Устаревшая вкладка получает конфликт; старая вкладка v1 не может перезаписать v2.
3. Backup исходных файлов и manifest в `backups/editor/<time>-<id>/`, включая ранее индексированные миссии.
4. Запись временных файлов рядом с целевыми; затем rename, индекс публикуется последним. Источники и `dist/config` получают одинаковые данные.
5. При ошибке — восстановление предыдущих source/dist файлов. Если откат не удался, ошибка указывает backup, а не сообщает успех.
6. Каждая миссия и общий system имеют `_revision`; загрузчик отвергает смешанный набор и повторяет чтение. При жёстком завершении процесса возможен незавершённый набор, но он не будет принят как корректная конфигурация. Для восстановления используется backup. Это не обещание ACID-транзакции файловой системы при выключении питания.

Редактирование во время асинхронного запроса не помечается сохранённым: UI запоминает именно отправленный snapshot. Никаких скачиваний в Downloads.

Обе страницы работают через один API, общую очередь и ревизию. Уведомление о записи банка обновляет чистый редактор миссий; при несохранённых правках или активном вводе показывает предупреждение, не заменяя данные. Банк аналогично реагирует на запись миссий. Устаревший snapshot не может затереть другой редактор. Черновик банка от другой ревизии не применяется автоматически и не удаляется; конфликт требует ручного согласования. Встроенного merge двух одновременно изменённых черновиков нет.
