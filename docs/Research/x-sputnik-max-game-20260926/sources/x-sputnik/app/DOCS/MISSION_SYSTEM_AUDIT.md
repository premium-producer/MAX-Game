# Аудит логики миссий и проект Mission Engine v2

> После этого аудита реализована первая версия системы. Её фактический контракт, отличия от исследовательского предложения и ограничения: [MISSION_ARCHITECTURE.md](MISSION_ARCHITECTURE.md). JSON-примеры ниже остаются эскизами, не схемой текущего API.

Дата: 2026-09-05. Основание: текущие исходники и два пользовательских скриншота. Статус: предложение архитектуры, не реализованный API. Примеры v2 ниже пока нельзя вставлять в действующий missions.json.

## Вывод

Текущая система умеет сравнивать один список типов и проверять локальные соседние пары. Она не моделирует миссию как сеть с реальными источниками, получателями и обязательными промежуточными ролями. Дополнение этой модели новыми типами галочек не исправит связь между положением объектов, зелёными состояниями и победой.

Предлагается один движок оценки миссии: физические соединения → сопоставление с заданной схемой → проверка условий → единый результат для игры, редактора, цветов, ошибок и завершения. A/Б становятся обычными фиксированными узлами с произвольными id и ролями. Правильность не зависит от камеры.

Положение сейчас всё же влияет на расстояние между внутренними соседями: совсем разнесённые ноды не соединятся. Ошибка точнее формулируется так: не проверяется требуемая топология от реального источника к реальному получателю, а локальная валидность не учитывает роль ноды в этой топологии.

### Проверено прямым вызовом текущего runtime

Без браузера и без записи в игровые конфиги выполнены четыре диагностических сценария. Ноды ставились на широте −45°, долготы −30 + index × 8°, затем проверялись после NODE_WAKE_DELAY_MS. Подмена условия ниже была только в памяти процесса.

| Сценарий | Полученный результат |
| --- | --- |
| Миссия 2: полный правильный список оборудования вдали от концов | `status=complete`, число endpoint-линков: `0` |
| Миссия 3: terminal → шесть satellite → terminal, core отсутствует | Все шесть satellite имеют `link`; все 7 внутренних линков `correct=true`; задачи `[true,true,false,false]` |

Существующие 88 тестов защищают прежний контракт, а не новый. Зелёный статус тестового прогона не подтверждает правильность требований пользователя: часть тестов прямо закрепляет сортировку по экрану и разрешённые концевые ноды в BASE.

## 2. Целевая модель данных

Нужны разные сущности с разными обязанностями:

| Сущность | Что содержит |
| --- | --- |
| ObjectType | Тип оборудования, визуальный размер, порты, радиусы, высотная кривая, ограничения размещения |
| NodeInstance | Конкретный экземпляр, постоянный id, тип, координаты, высота, время активации |
| FixedNode | Тот же экземпляр, но с фиксированной позицией; label A/Б — только отображение |
| EndpointGroup | Набор фиксированных узлов, например sources, northernReceivers, backupExits |
| Inventory | Доступные типы и квоты, независимо от правильного решения |
| MissionBlueprint | Требуемые роли, связи между ролями, альтернативы и ограничения |
| Binding | Соответствие `roleId → instanceId`, объясняющее, какой реальный объект выполняет какой шаг |
| Condition | Типизированное условие над общей оценкой, её bindings и игровым состоянием |
| FeedbackPolicy | Правила покраски и popup; не меняют допустимость решения |
| MissionEvaluation | Единый результат вычисления текущей миссии |

Одна роль по умолчанию требует отдельного экземпляра. Повтор из трёх спутников компилируется в три разные роли `west.sat.1/2/3`. Восточная тройка получает свои роли. Один экземпляр не может одновременно закрывать два шага; намеренно общий core задаётся одним общим roleId, на который ссылаются обе ветви.

Приоритет настроек: каталог типов → переопределение миссии → переопределение конкретного фиксированного узла. Это позволяет иметь разные радиусы двух приёмников одного типа. Размер интерфейсной иконки остаётся независим от радиуса связи.

## 3. Физическая сеть и правила присоединения

Движок строит физическую сеть из мировых координат всех узлов, включая фиксированные точки. Camera, screenX и положение DOM в этот расчёт не поступают.

Сначала строятся **кандидаты связей**: по радиусу, готовности узлов, совместимости портов, типу канала и, когда требуется, видимости. Затем применяется **политика присоединения**, которая определяет реальные физические рёбра. Только после этого проверяется правильность решения.

Нельзя выбирать из близких объектов только те, с которыми получится правильный ответ: иначе движок незаметно пропустит лишний четвёртый спутник и найдёт удобное ядро дальше. Неверное оборудование должно иметь возможность физически подключиться и получить диагностируемую ошибку роли.

Предлагаемый первый режим для текущей игры — `autoPorts`: игрок по-прежнему перемещает оборудование, а связь выбирается между ближайшими доступными совместимыми физическими портами. Для линейного участка задаётся ограничение степени/портов. Тип следующего шага из решения не участвует в выборе ближайшего кандидата. Привязка сохраняется в runtime; смена происходит при разрыве или однозначно лучшем кандидате с гистерезисом. При одинаково подходящих вариантах состояние — `ambiguous`, с подсветкой вариантов, без ложной победы.

Для сложных развилок тот же движок поддерживает `explicitPorts`: пользователь выбирает конкретное соединение. Меняется только создание физического ребра, а не проверка миссии. В редакторе можно назначать степень и совместимость портов каждого типа. Для слияния нескольких ветвей core получает нужное число портов.

Гистерезис влияет на привязку к порту, но не разрешает считать разорванный радиоканал рабочим. Детерминированный повтор включает историю действий и состояние привязок, а не только последнюю фотографию позиций.

Тип канала задаётся отдельно:

- `radio`: пересечение покрытия; видимость проверяется по сегменту между физическими передатчиками, а не визуальными иконками;
- `surface`: связь по поверхности, с собственным пределом длины или явно заданным фиксированным каналом;
- декоративное замыкание после победы: только эффект, не доказательство победы.

Запрет прохождения сквозь Землю нельзя включить без миграции наземных каналов: обычная хорда между наземными нодами проходит через сферу. Наземные соединения надо явно обозначить surface или задать высоту реального передатчика. Косметическая ножка и её размер не должны менять физическую точку передачи.

## 4. Правильная схема и точное количество повторов

Для автора удобны шаблоны «цепочка», «развилка», «слияние», «один из выходов». Внутри все они компилируются в граф именованных ролей и ограничений. Текстовая последовательность — удобный способ ввода простой схемы, не единственная модель хранения.

Пример предлагаемого авторского фрагмента для миссии 3:

```json
{
  "schemaVersion": 2,
  "mission": {
    "id": "protected-network",
    "inventory": { "terminal": 2, "satellite": 6, "core": 1 },
    "fixedNodes": [
      { "id": "west-origin", "label": "A", "type": "endpoint", "position": { "latitude": 54.71, "longitude": 20.51 } },
      { "id": "east-origin", "label": "Б", "type": "endpoint", "position": { "latitude": 43.12, "longitude": 131.89 } }
    ],
    "blueprint": {
      "template": "sequence",
      "id": "country-network",
      "steps": [
        { "fixedNode": "west-origin" },
        { "id": "west-terminal", "type": "terminal" },
        { "id": "west-sat", "type": "satellite", "repeat": { "exact": 3 } },
        { "id": "backbone", "type": "core" },
        { "id": "east-sat", "type": "satellite", "repeat": { "exact": 3 } },
        { "id": "east-terminal", "type": "terminal" },
        { "fixedNode": "east-origin" }
      ],
      "extraConnections": "forbidWithinSolution",
      "reuseInstance": false
    },
    "feedback": {
      "unexpectedSuccessor": {
        "validity": "invalid",
        "appearance": "error",
        "scope": "offendingNodeAndEdge",
        "popup": "oncePerMissionSignature"
      },
      "greenWhen": "segmentComplete"
    }
  }
}
```

Это иллюстрация предлагаемой схемы, не полный каталог; координаты взяты для примера, при миграции сохраняются актуальные пользовательские позиции. Радиусы и типы портов должны быть заданы в библиотеке типов. При необходимости правило `extraConnections` разрешает сторонние ветви явно, а не молча игнорирует их.

Для четвёртого спутника после западной тройки:

1. Движок прошёл от west-origin через west-terminal и три разные satellite-роли.
2. Следующая обязательная роль — backbone, принимающая только core.
3. Если реально присоединён satellite, ребро получает `unexpectedSuccessor`, ожидаемый тип core, фактический satellite и точные instanceId/roleId.
4. Этот спутник не засчитывается как следующий корректный шаг. При `appearance=error` он красный; при `appearance=neutral` — нейтральный. Победа запрещена в обоих случаях.
5. Отсутствие продолжения вообще — `incomplete`, а не ошибка неправильного типа. Для него задаётся отдельная политика.

Подсветка корректного префикса и завершённого сегмента различается: `greenWhen=validPrefix` допускает зелёные уже верные шаги; `segmentComplete` зажигает зелёный только после выполнения определённого сегмента. Для текущего запроса рекомендуется второй вариант. Наличие ошибочного продолжения может отменять зачёт сегмента через `requireNoInvalidBoundary`; это явное правило задачи.

Восточная часть может собираться независимо со стороны Б: для её локального прогресса задаётся обратный обход восточного сегмента. Это не создаёт вторую копию ролей и не делает ту же тройку спутников одновременно западной и восточной.

## 5. Несколько начал, равноценные выходы, ветвления

Пример формулировки требования на языке условий v2:

```json
{
  "endpointGroups": {
    "sources": ["source-1", "source-2", "source-3"],
    "exits": ["exit-primary", "exit-backup"]
  },
  "requirements": {
    "delivery": {
      "type": "groupDelivery",
      "sources": { "group": "sources", "quantifier": "all" },
      "targets": { "group": "exits", "quantifier": "any" },
      "targetBinding": "perSource",
      "viaBlueprint": "uplink-template"
    }
  }
}
```

Значение: от каждого из трёх источников нужен допустимый путь хотя бы к одному выходу; разные источники могут выбрать разные выходы. `targetBinding=shared` потребует один общий выбранный выход. `all`, `any`, `atLeast` с явным count позволяют выразить «два из пяти получателей» или «один из нескольких стартов».

Правила общего использования оборудования задаются явно: общий core допустим, а общие спутники — только если разрешены ресурсная ёмкость и разделение потока. Для резервных путей используется `disjointBy=nodes` или `edges` с явно исключёнными общими источником/получателем. Несколько найденных путей сами по себе ещё не доказывают резервирование.

Развилка/слияние хранятся как граф ролей, а не как несколько независимых списков: все ветви согласуют общие bindings в одной оценке. Для альтернатив используются `oneOf` на уровне шаблона; критерий выбора — удовлетворение правил, физическая реализуемость и стабильность уже назначенных ролей.

## 6. Составные условия и единая победа

Условия задаются типизированным деревом данных. Минимальный набор:

- `all`, `any`, `not`, `atLeast` для композиции;
- `segmentSatisfied`, `blueprintSatisfied`, `groupDelivery` для топологии;
- `count`, `allRequiredEquipmentUsed`, `noViolations` для состава;
- `inRegion`, `withinDistance`, `altitudeRange`, `linkMargin` для географии и связи;
- `stableFor` для удержания готовой сети определённое время.

«Сбалансируй высоту» должно ссылаться на измеримое правило: например, покрытие всех требуемых спутниковых рёбер с заданным запасом, либо заданный диапазон высот. «Откалибруй» — удовлетворение всей схемы с запасом связи и/или удержанием. Конкретные запасы и секунды задаёт автор миссии; аудит не изобретает эти числа.

У каждой задачи есть `id`, `condition`, `requiredForCompletion` и `progressMode`: `live` снимает галочку при разрыве, `latched` фиксирует выполненный этап. По умолчанию сетевые задачи live. Не допускаются циклические ссылки условий; `stableFor` использует время симуляции и сбрасывается при нарушении внутреннего условия.

```text
MissionDefinition + RuntimeState + now
                  ↓
        evaluateMission(context)
                  ↓
 bindings / acceptedEdges / nodeAssessments
 objectives / diagnostics / completion
                  ↓
  WebGL + checklist + footer + popups
```

В evaluator нет DOM и Three.js. Автопобеда и кнопка проверки читают один `completion.satisfied`; render не меняет run.status. Завершение выполняет reducer по подтверждённой оценке актуальной revision. Декоративный линк после победы не подаётся обратно в evaluator.

У каждого результата условия есть объяснение: `satisfied/incomplete/invalid/ambiguous`, `reasonCode`, ожидаемая роль, фактические узлы/рёбра, измеренное значение и порог. Галочки ссылаются на те же доказательства bindings, что и зелёные объекты. При нейтральном оформлении ошибки диагностическая причина сохраняется.

## 7. Ошибки и правила обратной связи

В JSON настраиваются отдельно логический эффект и внешний вид:

| Настройка | Примеры |
| --- | --- |
| Логическая классификация | invalid, incomplete, ambiguous |
| Оформление | error, neutral, warning |
| Область подсветки | нарушившая нода и ребро, ошибочный суффикс, весь сегмент |
| Показ popup | never, onConnection, onCheck |
| Повторы | oncePerMissionSignature |
| Зелёный статус | валидный префикс, завершённый сегмент, вся миссия |

Дедупликация popup сохраняет пользовательское требование «один раз за миссию». Ключ строится из missionId, ruleId, идентификатора сегмента и устойчивой сигнатуры неправильного порядка/ожидаемой роли. InstanceId и время не входят в ключ: повторное создание такого же неправильного порядка не вызывает новое окно. Одинаковые типы в другом сегменте различаются по контексту правила.

`onConnection` срабатывает только после возникновения реального присоединённого ребра и готовности involved-ноды. Неподключённый лишний спутник не должен вызывать ошибку четвёртого шага. При исправлении активная ошибка исчезает, отметка «уже показывали» остаётся. Popup и его позиция не участвуют в валидности миссии.

## 8. Редактор

Сохранить существующий географический viewport, камеры по состояниям и единую кнопку сохранения с backup. Добавить четыре авторские области:

1. **Точки и оборудование.** Любое количество фиксированных точек, названия, группы, типы, координаты, радиусы, размеры и независимый инвентарь.
2. **Схема.** Быстрый ввод цепочки, повторы «ровно 3», развилки/слияния, выбор одного из нескольких финишей, совместно используемые роли. Шаблоны создают редактируемый граф.
3. **Задачи и обратная связь.** Конструктор условий, обязательность задач, live/latched, зелёный/красный/нейтральный статус и popup-политики.
4. **Проверка.** Пробная сборка использует тот же evaluator. По клику на ноду видно: какую роль заняла, откуда пришёл сигнал, что ожидается следующим, почему ребро не принято.

Нижний footer текущего вида A→…→Б подходит только линейному шаблону. Для графовой миссии нужны выбираемые ветви/маршруты или компактная схема. Он показывает bindings evaluator, а не сортировку по экрану. Нельзя обещать поддержку нескольких источников только сменой JSON без адаптации этого интерфейса.

## 9. Разбиение реализации и пределы сложности

Предлагаемые модули: `mission-definition` (schema, миграции, валидация), `mission-compiler` (шаблоны в роли и ограничения), `physical-network` (дистанции, видимость, порты), `topology-matcher` (bindings), `condition-evaluator`, `mission-evaluator`, `mission-runtime` (reducer и история), `feedback-resolver`.

Начать с линейных схем, точных повторов, нескольких endpoint-групп и ограниченных развилок. Для последовательности подходит обход состояния «физический узел + следующая роль + использованные instanceId». Для общего графа нужен поиск согласованного назначения ролей с проверкой ограничений. Простого поиска пути недостаточно: он не обеспечивает уникальность объектов, совместный core и отсутствие лишнего шага.

Общий поиск может иметь комбинаторную сложность. Нужны явный бюджет поиска, сокращение кандидатов по типу/зоне/портам, переиспользование последнего binding и диагностика превышения бюджета. Неполный расчёт возвращает `indeterminate`, никогда complete. Проектные лимиты определяются измерениями и показываются автору до сохранения; не вводить очередное необоснованное ограничение «8 объектов».

Расчёт вызывается при изменении позиций/связей, активации, таймера условия или конфигурации. Камера и декоративная анимация не запускают повторное логическое сопоставление. Каждая оценка имеет revision; старый результат не может завершить новую сборку. Движок получает явный context, без глобальной смены каталога между игрой и preview.

## 10. План перехода

1. Зафиксировать описанные баги как тесты требований v2, отдельно от тестов совместимости v1. Определить измеримую калибровку и радиусы концов по игровому балансу.
2. Ввести schemaVersion 2, стабильные id точек, независимый inventory, роли/рёбра, составные условия и политики. Написать мигратор v1→v2 с отчётом изменений поведения.
3. Реализовать физическую сеть с endpoint-узлами и согласованное сопоставление трёх текущих линейных миссий, включая точные повторы. В этот момент убрать зависимость от screenX и разрешённых пар «где-нибудь в маршруте».
4. Перевести цвета, галочки, popup, кнопку и автопобеду на один MissionEvaluation. Заменить визуальную сортировку footer на отображение назначенных ролей.
5. Расширить редактор и единое сохранение v2. Сохранить камеры, геопозиции, тексты, размеры, радиусы и историю backup. Отклонять неизвестную новую версию явно, а не молча отбрасывать поля.
6. Добавить группы источников/выходов, ветвления, совместные роли и резервирование с тестами. Старый evaluator удалить после миграции всех игровых миссий.

Перенос совместимости не должен сохранить обнаруженные ошибки. Для миссии 2 обязательность подключения A/Б включается независимо от отсутствия наземного замыкания. Радиус 6.5 помечается мигратором как прежнее допущение и заменяется выбранным балансом; точное новое значение требует отстройки. Старое поле connectEndpointsOnComplete переносится только в presentation/completionEffects.

Запись v2 стоит дополнить revision/проверкой устаревшей вкладки, последовательной очередью сохранений и заменой через временные файлы. Backup сам по себе не защищает от двух конкурирующих сохранений или частично обновлённой пары конфигов. Это часть надёжного редактора, а не новое условие игровых связей.

## 11. Критерии готовности

- Миссия 2 с собранной внутренней цепью, но без физического подключения к A или Б, не завершается.
- Три спутника занимают три конкретные роли; четвёртый вместо core даёт expected=core/actual=satellite. error/neutral меняет только отображение.
- Лишняя присоединённая нода не обходится «удобным» альтернативным поиском пути, если strict-шаблон запрещает её.
- Западная и восточная части не используют одни и те же экземпляры; общий core явно общий.
- При отсутствии следующей ноды статус incomplete, при двух равнозначных присоединениях ambiguous; оба не равны успеху.
- Перемещение A/Б меняет достижимость; смена камеры — нет.
- Любое количество фиксированных точек поддерживается схемой, evaluator и UI без специальных if для букв.
- Проверены any/all/atLeast, общий и индивидуальный выбор финиша, разделяемый core и непересекающиеся резервные пути.
- Невыполненная обязательная задача блокирует победу; auto и CHECK дают одинаковый результат одной revision.
- Разрыв связи снимает live-галочку; поведение latched и stableFor проверяется отдельно.
- Радиус спутника, физические ограничения и отображаемые волны остаются согласованными; тип surface не блокируется радиопроверкой видимости.
- Одна и та же ошибка с тем же контекстом не показывает popup повторно в текущей миссии, включая удаление и повторное добавление оборудования.
- JSON проходит schema, смысловую проверку и round-trip сохранения с backup без потери камер и географии.
- Превышение бюджета поиска и неизвестный тип условия не приводят к ложной победе.

## 12. Границы этого аудита

Выполнены чтение кода и четыре воспроизводимых диагностических запуска. Визуальный браузерный прогон не выполнялся по правилам проекта. Runtime и игровые JSON в рамках аудита не изменялись. Архитектура описывает конкретную следующую переработку; действующая система пока сохраняет перечисленные ограничения.
