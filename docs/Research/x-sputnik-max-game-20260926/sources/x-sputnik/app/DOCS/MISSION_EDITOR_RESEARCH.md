# Ресерч режима редактора миссий X-SPUTNIK

Дата: 2026-09-04  
Статус: базовый инструментарий реализован; документ синхронизирован с решением о раздельных ракурсах состояний

## Короткий вывод

Для проекта оптимален отдельный локальный экран `editor.html`, работающий на том же vanilla JavaScript + Three.js стеке, что и игра. Редактор не следует встраивать в игровые состояния: так он не затронет пятиэкранную хореографию, прогресс игрока и production-интерфейс.

Минимально полезная версия должна позволять:

- открыть текущий `missions.json`;
- создать, дублировать, удалить и переставить миссию;
- вращать Землю и сохранить стартовый ракурс;
- поставить на Земле маркер миссии, точки A и Б;
- собрать последовательность объектов визуальной цепочкой;
- автоматически получить количество оборудования из этой цепочки;
- настроить задачи, зависимости и замыкание A—Б;
- проверить конфигурацию и сохранить JSON;
- запустить предпросмотр миссии без изменения игрового прогресса.

Главный принцип: **редактор меняет те же данные, которые читает игра, а не поддерживает их вторую копию**.

## Что уже есть в проекте

Текущая архитектура хорошо подготовлена для редактора:

- `public/config/missions.json` уже содержит миссии, координаты, A/Б, маршрут, задачи и зависимости;
- `public/config/missions.schema.json` задаёт строгую структуру JSON Schema Draft 2020-12;
- `src/mission-config.mjs` проверяет смысловые ограничения: уникальность, существование зависимостей, циклы и типы объектов;
- `src/mission-game.mjs` содержит единый каталог оборудования и вычисляет доступное количество каждого типа по числу его вхождений в `mission.route`;
- `src/webgl-field.js` уже умеет проецировать географические координаты на экран, получать текущую камеру и через raycasting преобразовывать указатель в точку на сфере;
- проект не зависит от React или UI-фреймворка, поэтому для MVP не требуется миграция или новая runtime-зависимость;
- текущий `server.mjs` раздаёт статику и намеренно не записывает проектные файлы.

Иными словами, требуется прежде всего удобная оболочка для уже существующей модели данных.

## Предлагаемый интерфейс

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ Открыть  Сохранить  Сохранить как…  ↶ ↷  Проверить  Предпросмотр   ● изменён │
├───────────────┬─────────────────────────────────────┬───────────────────────┤
│ МИССИИ        │                                     │ ИНСПЕКТОР МИССИИ      │
│               │              ЗЕМЛЯ                  │                       │
│ 1 Первый…     │                                     │ Название / описание   │
│ 2 Арктика…    │  Режим: Навигация | Миссия | A | Б  │ Время / successText   │
│ 3 Сеть…       │                                     │ Координаты             │
│               │   выбранные маркеры и подписи       │ Замкнуть A—Б           │
│ + Новая       │                                     │ Зависимости / задачи   │
│ Дублировать   │                                     │                       │
├───────────────┴─────────────────────────────────────┴───────────────────────┤
│ ОБЪЕКТЫ: [терминал] [спутник] [шлюз] [ядро] [интернет]                     │
│ МАРШРУТ: A → [терминал] → [спутник] → [спутник] → [шлюз] → … → Б          │
│ КОЛИЧЕСТВО: терминал ×1 · спутник ×2 · шлюз ×1 · ядро ×1 · интернет ×1   │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Левая панель — каталог миссий

- карточки в порядке `number`;
- создание с чистого шаблона;
- дублирование выбранной миссии как самый быстрый сценарий;
- удаление с подтверждением;
- изменение порядка drag-and-drop или кнопками вверх/вниз;
- статусы рядом с карточкой: корректна, предупреждение, ошибка;
- поиск/фильтр можно отложить, пока миссий мало.

При создании редактор предлагает следующий свободный `number`, генерирует `id` из названия и делает его уникальным. Зависимость от предыдущей миссии можно предложить по умолчанию, но не навязывать.

### Центр — интерактивная Земля

Нужны четыре явно переключаемых инструмента:

1. **Навигация** — drag вращает Землю, колесо меняет дистанцию.
2. **Миссия** — клик ставит `mapPosition` выбранной миссии.
3. **A** — клик ставит `endpoints.A`.
4. **Б** — клик ставит `endpoints.B`.

Такой режим проще и надёжнее, чем пытаться одним жестом угадать, хочет пользователь вращать Землю или двигать маркер. После постановки координаты показываются и в числовых полях справа; ручной ввод остаётся доступным для точной правки.

Для преобразования клика в координаты нужно открыть наружу уже существующую внутреннюю функцию raycast как безопасный публичный метод вроде `pickGeo(clientX, clientY)`. Three.js штатно строит луч из координат указателя методом `Raycaster.setFromCamera()` и возвращает пересечение с объектом через `intersectObject()` — это тот же подход, который уже используется внутри игрового поля. См. [Three.js Raycaster](https://threejs.org/docs/pages/Raycaster.html).

Маркеры следует различать не только цветом, но и подписью/формой:

- позиция карточки миссии — синий флаг;
- A — круг с `A`;
- Б — круг с `Б`;
- выбранный маркер — дополнительное кольцо и координаты рядом.

На первом этапе достаточно click-to-place. Перетаскивание существующих маркеров можно добавить позже, используя тот же raycast. Один drag должен считаться одной операцией Undo, а не сотней промежуточных шагов.

### Правая панель — инспектор

Поля группируются по смыслу:

| Раздел | Поля |
|---|---|
| Основное | `number`, `id`, `name`, `description`, `timeSeconds`, `successText` |
| Карта | `mapPosition.latitude/longitude` |
| Концы маршрута | label и координаты A/Б |
| Поведение | `connectEndpointsOnComplete` |
| Доступность | `unlock.requiresCompleted` как список существующих миссий |
| Задачи | `objectives[]` и их условия |

Зависимости лучше выбирать галочками по названиям миссий, а номера записывать автоматически. Редактор должен сразу запрещать зависимость миссии от самой себя и показывать цикл до сохранения.

### Нижняя панель — конструктор маршрута

Последовательность `route` является единственным источником истины одновременно для:

- количества объектов в правом игровом меню;
- правильного порядка соединения;
- длины собираемой игроком цепи.

Поэтому отдельное редактируемое поле «количество спутников: 2» добавлять не нужно. Пользователь дважды добавляет спутник в маршрут, а сводка автоматически показывает `спутник ×2`.

Управление маршрутом:

- клик по типу добавляет его в конец;
- drag меняет порядок;
- крестик удаляет элемент;
- дублирование элемента доступно одной кнопкой;
- стрелки между слотами всегда показывают фактическую последовательность A → route → Б;
- редактор не придумывает лимит длины маршрута: ограничение допустимо только после появления такого же явного правила в runtime и JSON Schema.

Это быстрее ручного ввода JSON и исключает рассинхронизацию количества и маршрута.

## Задачи миссии

Текущие условия уже достаточно выразительны для визуального конструктора:

- `placed(object, count)`;
- `adjacent(first, second, count)`;
- `allPlaced`;
- `routeCorrect`;
- `networkConnected`.

Для каждой задачи редактор показывает:

- текст задачи;
- выпадающий тип условия;
- только параметры, относящиеся к выбранному условию;
- автоматически создаваемый уникальный `id`, который при необходимости можно изменить.

Кнопка «Создать задачи из маршрута» может подготовить стартовый набор: разместить первый объект, проверить ключевые соседние пары, правильность маршрута и соединение сети. Это шаблон, а не скрытая автологика — результат остаётся редактируемым.

## Стартовый ракурс Земли

Важно различать две настройки:

- географическая калибровка текстуры Земли (`RUSSIA_VIEW.rotation`) — техническая константа сцены;
- стартовый вид пользователя — положение камеры относительно Земли.

Редактор должен менять только второй параметр. Рабочий сценарий:

1. пользователь вращает Землю, переносит камеру, настраивает дистанцию и FOV;
2. нажимает «Использовать текущий ракурс»;
3. редактор сохраняет стартовое состояние;
4. «Вернуться к сохранённому» позволяет проверить результат.

### Формат данных

Ракурс относится не к контенту конкретной миссии, а к визуальному состоянию приложения. Поэтому он хранится в `ui-shell.json` внутри каждого из пяти states:

```json
{
  "states": {
    "MISSION_SELECT": {
      "cameraView": {
        "target": [0, 2.31, 0],
        "rotation": [0, 0, 0],
        "distance": 7.2,
        "fov": 38
      }
    }
  }
}
```

`webgl-field.js` принимает `initialView`, возвращает текущую композицию через `getViewState()` и плавно применяет новый вид через `setViewState()`. Редактор позволяет выбрать `CTA`, `ONBOARDING`, `MISSION_SELECT`, `MISSION_PLAY` или `END`, точно настроить rotation X/Y/Z, target X/Y/Z, zoom и FOV, назначить вид одному state либо скопировать его во все пять states.

Рабочее поле камеры — отдельный preview строго `16:9`, который вписывается в центральную панель без изменения пропорций. В нём масштабируются реальные `1920×1080`-координаты shell: header, frame, footer, inventory, маска Земли, blur/dim и presentation offset берутся из того же `ui-shell.json` и тех же resolver-функций, что runtime. Выбор state сразу меняет не только ракурс, но и оболочку/контент preview: каталог миссий показывается на `MISSION_SELECT`, endpoints A/Б — на `MISSION_PLAY`.

Редактор использует `freeOrbit + preciseOrbit`: три Euler-оси не ограничены, editor-drag не продолжает движение после отпускания, игровое автосмещение Земли при pitch отключено. X/Y управляются ЛКМ, Z — `Alt+ЛКМ` или ПКМ, перенос камеры в текущей экранной плоскости — `Shift+ЛКМ`, zoom — колесом; target, distance и FOV доступны также численно.

`ui-shell.json` поднят до `schemaVersion: 4`; parser принимает версии 1–3, преобразуя старую пару `camera/target` в `rotation/target/distance` и добавляя отсутствующий FOV `38°`. `missions.json` остаётся version 1 и содержит только контент миссий.

## Проверка данных

Нужны четыре уровня проверки.

### 1. Проверка поля во время ввода

- обязательность;
- число и диапазон;
- широта `-82…82`, долгота `-180…180` согласно текущей схеме;
- уникальность `number`, `id` и objective `id`;
- непустой маршрут и список задач.

Ошибка показывается рядом с полем, а не только общей строкой сверху.

### 2. JSON Schema

Сохраняется строгая схема Draft 2020-12 и `additionalProperties: false`. JSON Schema подходит для структурных ограничений, а её validation vocabulary содержит также annotations/metadata, которые можно использовать для подписей и подсказок формы. См. [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12) и [Validation specification](https://json-schema.org/draft/2020-12/json-schema-validation).

В текущем проекте необязательно сразу добавлять библиотеку-валидатор: форма может использовать существующую схему как контракт, а runtime-парсер — как исполняемую проверку. Если в будущем появится импорт произвольных расширений схемы, тогда оправдано подключение полноценного Draft 2020-12 validator.

### 3. Смысловая проверка

Нужно переиспользовать `parseMissionCatalog()` из `mission-config.mjs`, а не копировать его правила. Он уже проверяет неизвестные типы оборудования, ссылки на отсутствующие миссии и циклы зависимостей.

Дополнительные editor warnings, не блокирующие сохранение:

- A и Б почти совпадают;
- несколько карточек миссий накладываются в стартовом ракурсе;
- маркер скрыт на обратной стороне Земли;
- objective ссылается на пару, которой нет в маршруте;
- у миссии нет зависимости, хотя её номер не первый.

### 4. Предпросмотр

Редактор создаёт временный `missionRun` из черновика через ту же игровую модель. Предпросмотр не пишет localStorage основного приложения и не открывает следующие миссии. Это ловит ошибки, которые формально корректны в JSON, но неудобны в игре.

Сохранение блокируется при errors, но не при warnings. В каталоге error и warning имеют разные цвета и знак `!`, а полный текст каждой причины показывается в инспекторе выбранной миссии.

## Сохранение и черновики

### Реализованный путь

Редактор работает с игровыми конфигурациями проекта и не предлагает file picker или download-export. Одна кнопка отправляет каталог и все per-state ракурсы на локальный endpoint `POST /api/editor/save`.

Endpoint привязан к `127.0.0.1`, принимает только same-origin JSON до 2 МБ, повторно проверяет оба контракта runtime-парсерами и затем:

1. создаёт `backups/editor/<timestamp>/` с предыдущими `missions.json`, `ui-shell.json` и manifest;
2. записывает новую версию в `public/config` как канонические исходники;
3. записывает ту же версию в `dist/config`, чтобы следующая загрузка игры сразу получила изменения;
4. при ошибке записи пытается восстановить обе копии из созданного backup.

Это локальный authoring API, а не публичный production endpoint. У открытой вкладки игры конфигурация остаётся в памяти до обновления страницы.

### Автосохранение

Черновик следует автоматически сохранять в IndexedDB после небольшой паузы, но не считать это сохранением проектного JSON. IndexedDB — транзакционное локальное хранилище браузера, подходящее для структурированных данных: [W3C IndexedDB](https://www.w3.org/TR/IndexedDB/).

В верхней панели всегда видны два независимых статуса:

- «Черновик сохранён локально»;
- «Есть изменения в файле».

После сбоя редактор предлагает восстановить локальный черновик и показывает время обеих версий.

## Undo/Redo и состояние редактора

Редактору нужен отдельный immutable state:

```js
{
  catalog,
  selectedMissionId,
  activeMapTool,
  validation,
  history: { past, present, future },
  dirty
}
```

Правила истории:

- текстовый ввод объединяется в одну операцию после паузы;
- добавление/удаление объекта — одна операция;
- перестановка маршрута — одна операция;
- полный drag маркера от pointerdown до pointerup — одна операция;
- выбор панели, hover и вращение без сохранения ракурса в историю данных не попадают;
- «Использовать текущий ракурс» создаёт одну операцию.

## Структура реализации

Предлагаемые файлы:

```text
app/
├─ editor.html
├─ src/
│  ├─ editor-main.js          # сборка UI и события
│  ├─ editor-state.mjs        # actions, history, dirty state
│  ├─ editor-validation.mjs   # errors и warnings
│  ├─ editor-storage.mjs      # IndexedDB draft/recovery
│  ├─ editor-project-save.mjs # backup и запись source/runtime JSON
│  └─ editor-styles.css
├─ public/config/
│  ├─ missions.json
│  └─ missions.schema.json
└─ test/
   ├─ editor-state.test.mjs
   └─ editor-validation.test.mjs
```

Потребуются небольшие изменения существующих модулей:

- `webgl-field.js`: публичный `pickGeo()` и editor-friendly режим без игровых drag-событий;
- `mission-config.mjs`: экспорт чистой функции нормализации/проверки и сериализации runtime-каталога;
- `ui-shell-config.mjs`: проверка отдельного `cameraView` для каждого state и миграция version 1/2/3 → 4;
- `scripts/build.mjs`: второй entry point `editor.html`/`editor-main.js`;
- `check-portable.mjs`: проверка наличия файлов редактора, если редактор должен попадать в переносимую сборку.

Редактор не должен быть ссылкой в игровом интерфейсе. Его можно открывать отдельно по `/editor.html`; для киоска его при необходимости исключают из production-пакета отдельным build flag.

## Самый быстрый план внедрения

### Этап 1 — рабочий MVP

- отдельная страница редактора;
- загрузить игровые JSON проекта;
- список и CRUD миссий;
- инспектор основных полей;
- click-to-place для mission/A/Б;
- конструктор route и вычисляемые количества;
- текущие objective types и dependencies;
- inline errors + `parseMissionCatalog()`;
- unit-тесты чистых state/validation функций.

Это уже полностью заменяет ручное редактирование JSON.

### Этап 2 — удобная ежедневная работа

- единое Save через локальный project endpoint с backup;
- IndexedDB draft/recovery;
- Undo/Redo;
- сохранение начального ракурса;
- warnings по наложению и видимости маркеров;
- клавиатурные сокращения.

### Этап 3 — контроль качества контента

- sandbox preview одной миссии;
- генератор задач из маршрута;
- визуальный граф unlock-зависимостей;
- импорт/экспорт одной миссии;
- проверка миграции старых schemaVersion.

## Что сознательно не стоит делать в первой версии

- не вводить React/Vue только ради редактора;
- не принимать от клиента произвольные пути: endpoint пишет только два заранее заданных игровых JSON;
- не хранить отдельный `inventoryCount`, дублирующий `route`;
- не делать свободное перетаскивание всех трёх типов маркеров до стабильного click-to-place;
- не смешивать editor state с игровым reducer;
- не генерировать JSON строками вручную — хранить объект и использовать `JSON.stringify(..., null, 2)`;
- не разрешать экспорт конфигурации с blocking errors;
- не менять техническую калибровку текстуры Земли из контентного редактора.

## Критерии готовности

Редактор можно считать готовым к использованию, когда выполняются все пункты:

1. Текущий `missions.json` открывается без изменения смысла данных.
2. Новая или дублированная миссия создаётся за несколько действий.
3. Позиции mission/A/Б ставятся кликом на видимой Земле и точно попадают в JSON.
4. Стартовый ракурс сохраняется и воспроизводится после перезагрузки.
5. Изменение route сразу меняет порядок и вычисленное количество оборудования.
6. Дубликаты id/number и циклы unlock показываются до сохранения.
7. Сохранённый файл повторно открывается и проходит runtime-парсер.
8. Undo отменяет целый drag или перестановку одним шагом.
9. Предпросмотр не меняет игровой прогресс.
10. Одна кнопка создаёт backup и синхронно обновляет source/runtime-копии обоих JSON без скачивания файлов.

## Итоговая рекомендация

Использовать отдельный vanilla JS редактор и два уже существующих контракта: `missions.json` для контента и `ui-shell.json` для визуальных ракурсов пяти состояний. Центральный сценарий остаётся прямым: выбрать миссию → выбрать инструмент → кликнуть по Земле → собрать route → проверить → одной кнопкой сохранить миссии и ракурсы непосредственно в проект.

Это использует уже написанную географию, игровую модель и валидацию, не создаёт второго источника истины и даёт быстрый путь от ручного JSON к полноценному контентному инструменту.
