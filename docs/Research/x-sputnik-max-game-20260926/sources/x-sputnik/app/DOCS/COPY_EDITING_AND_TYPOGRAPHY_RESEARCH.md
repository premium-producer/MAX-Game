## 1. Цель

Текст в интерфейсе должен одновременно:

- быть грамматически и пунктуационно корректным;
- читаться как естественный интерфейсный текст, а не буквальный перевод;
- не оставлять короткие служебные слова на конце строки;
- не разрывать связанные конструкции: `№ 1`, `20 %`, `2 мин`, имя с инициалами;
- не переполнять карточки и кнопки на целевых разрешениях;
- одинаково надёжно работать в RU и EN после динамической смены языка;
- оставаться доступным для экранных дикторов и машинной обработки;
- храниться в одном источнике, без ручных копий в HTML и JavaScript.

Орфография, редактура и вёрстка — три разные проверки. Грамматически правильная строка всё ещё может выглядеть плохо из-за переноса; красивый перенос не исправляет неясную формулировку; неразрывные пробелы не должны маскировать неподходящую ширину компонента.

## 2. Основания и источники

Рекомендации собраны из следующих первичных и профильных источников:

- «Грамота.ру» подтверждает: перенос однобуквенного слова сам по себе не нарушает орфографию, но в издательской практике такое слово рекомендуется не оставлять в конце строки: [ответ справочной службы № 232363](https://gramota.ru/spravka/vopros/232363).
- Для знаков номера и процента в русском наборе нужны пробелы: `№ 1`, `50 %`; в компьютерном наборе связанную пару обычно удерживают неразрывным пробелом: [ответ № 233059](https://gramota.ru/spravka/vopros/233059) и [поиск по справочной службе о знаке номера](https://gramota.ru/poisk?mode=spravka&query=%D0%BD%D0%BE%D0%BC%D0%B5%D1%80%D0%B0).
- Академические справочники по русской пунктуации собраны в разделе [«Пунктуация» на «Грамоте.ру»](https://gramota.ru/biblioteka/spravochniki/punktuaciya); правила также требуют различать внешние «ёлочки» и внутренние „лапки“: [сочетания знаков препинания](https://gramota.ru/biblioteka/spravochniki/pravila-russkoj-orfografii-i-punktuacii/o-sochetaniyah-znakov-prepinaniya).
- [Unicode Line Breaking Algorithm](https://www.unicode.org/reports/tr14/) определяет `U+00A0 NO-BREAK SPACE`, `U+202F NARROW NO-BREAK SPACE`, `U+2011 NON-BREAKING HYPHEN` и `U+2060 WORD JOINER` как специальные средства управления разрывами строк.
- [CSS Text Module Level 4](https://www.w3.org/TR/css-text-4/) требует сообщать браузеру язык содержимого для качественной языковой вёрстки и описывает управление переносами, разрывами и пробелами.
- [MDN: text-wrap-style](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-wrap-style) рекомендует `balance` для коротких заголовков и `pretty` для основного текста; [MDN: hyphens](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/hyphens) подчёркивает зависимость автопереносов от корректного `lang` и доступного словаря языка.
- W3C объясняет, что корректный `lang` нужен не только CSS, но и произношению screen reader: [WCAG 2.2, Language of Page](https://www.w3.org/WAI/WCAG22/Understanding/language-of-page). Рекомендации по доступному тексту требуют ясных инструкций, коротких формулировок и содержательных заголовков: [Writing for Web Accessibility](https://www.w3.org/WAI/tips/writing/).
- Microsoft Style Guide рекомендует для английского UI sentence case, глаголы в действиях, короткие формулировки и отсутствие точки или двоеточия в конце заголовков: [Writing tips](https://learn.microsoft.com/en-us/style-guide/global-communications/writing-tips), [Top 10 tips for Microsoft style and voice](https://learn.microsoft.com/en-us/style-guide/top-10-tips-style-voice).
- ICU рекомендует переводить сообщение целиком, а не собирать его из грамматических фрагментов, и оставлять переводчику возможность менять порядок плейсхолдеров: [Formatting Messages](https://unicode-org.github.io/icu/userguide/format_parse/messages/). Ту же проблему для UI разбирает [Microsoft: String concatenation](https://learn.microsoft.com/en-us/globalization/internationalization/concatenation).

Часть решений ниже является не универсальным законом языка, а **house style X-SPUTNIK**. Такие решения явно помечены.

## 3. Базовая модель качества

Каждая строка проходит четыре уровня.

1. **Смысл:** пользователь сразу понимает состояние и следующее действие.
2. **Язык:** фраза естественна для конкретной локали, грамматика и пунктуация корректны.
3. **Типографика:** кавычки, тире, числа, единицы и неразрывные связи набраны правильно.
4. **Вёрстка:** строка не переполняет компонент, не создаёт висячих слов и сохраняет визуальную иерархию.

Нельзя лечить проблему более поздним уровнем. Например, слишком длинную кнопку сначала сокращают редакторски, а не уменьшают ей шрифт до тех пор, пока она поместится.

## 4. Общие правила интерфейсного текста

### 4.1. Одна строка — одна задача

- Заголовок сообщает состояние или цель.
- Описание добавляет причину, условие или пояснение, но не повторяет заголовок.
- Кнопка называет действие пользователя.
- Ошибка отвечает на два вопроса: что произошло и что можно сделать дальше.
- Шаг начинается с действия и использует ту же грамматическую форму, что соседние шаги.

Хорошо:

```text
ЗАПУСТИ СИГНАЛ
Когда все миссии будут выполнены, ты сможешь выйти на связь с главным спутником.
```

Плохо:

```text
СИГНАЛ
Здесь можно будет попробовать выполнить запуск сигнала после выполнения всех заданий.
```

### 4.2. Параллельность

Элементы одного уровня должны иметь одинаковую форму:

- `ВЫБЕРИ МИССИЮ / ПОСТРОЙ МАРШРУТ / ЗАПУСТИ СИГНАЛ` — три императива;
- `CHOOSE A MISSION / BUILD THE ROUTE / LAUNCH THE SIGNAL` — три императива;
- списки задач не должны смешивать существительные, инфинитивы и команды без причины.

### 4.3. Кнопки

- Начинать с конкретного глагола: `НАЧАТЬ`, `ПРОДОЛЖИТЬ`, `ПОВТОРИТЬ`, `ВЕРНУТЬСЯ`.
- Одна кнопка — одно действие.
- Не добавлять точку в конце.
- Не использовать техническое название контрола: не `НАЖМИТЕ КНОПКУ «СТАРТ»`, а `НАЧАТЬ`.
- Не подменять действие состоянием: `ПОДКЛЮЧИТЬСЯ`, а не `ПОДКЛЮЧЕНИЕ`.
- Длинный брендовый CTA допустим как осознанное исключение, но его нужно проверять на целевой ширине в обеих локалях.

### 4.4. Заголовки и регистр

- Смысловой исходник предпочтительно хранить в естественном регистре, а сплошные прописные применять как визуальный стиль через CSS `text-transform`.
- Исключения: зарегистрированное написание бренда, аббревиатура, утверждённый арт-дирекцией display-текст.
- В английском по умолчанию используется sentence case, не Title Case.
- Заголовки и UI labels не заканчиваются точкой или двоеточием. Вопросительный и восклицательный знаки допустимы, если являются частью смысла.

Для текущего проекта уже используется много авторского uppercase. Его нельзя механически понизить без визуального решения; при следующем рефакторинге следует отделить канонический текст от display-регистра.

## 5. Русский язык: редакторский и типографический контракт

### 5.1. Висячие короткие слова

Строгий house rule для всех player-facing поверхностей:

- однобуквенные предлоги, союзы, частицы и местоимения не остаются в конце строки;
- они связываются **со следующим словом**: `в космосе`, `и на Земле`, `я готов`;
- минимальный обязательный список: `а`, `б`, `в`, `ж`, `и`, `к`, `о`, `с`, `у`, `я` с учётом регистра;
- в заголовках, кнопках и узких карточках дополнительно связываются со следующим словом частотные двухбуквенные служебные слова: `во`, `до`, `за`, `из`, `ко`, `на`, `не`, `ни`, `но`, `об`, `от`, `по`, `со`;
- в длинном основном тексте двухбуквенное правило применяется осторожно: чрезмерная склейка создаёт длинные неразрывные фрагменты и переполнение.

Пример:

```text
до нормализации: элементы сети на Земле и в космосе
после нормализации: элементы сети на Земле и в космосе
```

Это правило управляет только допустимым местом переноса. Видимый интервал остаётся пробелом.

### 5.2. Связанные конструкции

Неразрывно набираются:

- знак номера и число: `миссия № 1`;
- число и единица: `5 км`, `2 мин`, `48 кГц`;
- число и знак процента в русском тексте: `40 %`;
- инициалы и фамилия: `А. А. Иванов`;
- сокращение и относящееся к нему слово/число: `рис. 2`, `г. Москва`;
- значение со знаком: `+20 °C`;
- короткие части официального имени, если их разрыв искажает узнаваемость.

Для узкого типографического интервала между числом и знаком может использоваться `U+202F NARROW NO-BREAK SPACE`, но только после проверки Bureau на целевых браузерах. Безопасный default проекта — обычный `U+00A0`.

### 5.3. Кавычки, тире и дефис

- Внешние русские кавычки: `«ёлочки»`.
- Вложенные: `«текст „внутри“ текста»`.
- Дефис `-` соединяет части слова: `по‑русски`; если разрыв недопустим, использовать `U+2011 NON-BREAKING HYPHEN`.
- Тире `—` является знаком препинания: `Миссия выполнена — связь установлена`.
- Знак минуса: `−` (`U+2212`), а не дефис: `−20 °C`.
- Не заменять многоточие тремя случайными точками, если нужен единый знак: `…`.

Проектный стиль для русского тире — пробелы с обеих сторон. Перед тире желательно поставить неразрывный пробел либо неразрывную связь только тогда, когда конкретный layout иначе оставляет тире в начале строки; глобально склеивать большие части предложения нельзя.

### 5.4. Пунктуация

- Полное предложение заканчивается точкой, вопросительным или восклицательным знаком.
- Краткий label, пункт меню, кнопка и заголовок — без точки.
- Все пункты одного списка оформляются одинаково: либо краткие фразы без точек, либо полные предложения с точками.
- Двоеточие используется перед реальным пояснением или перечнем, а не как декоративный финал заголовка.
- Один обычный пробел после знака препинания; пробела перед `, . ! ? : ;` нет.
- Не использовать `!!`, `???` и случайные сочетания знаков вне утверждённого эмоционального текста.

### 5.5. «Ё»

Нужна одна политика на весь продукт. Рекомендуемый house rule:

- писать `ё`, когда без неё возможно неверное чтение, меняется смысл, это имя собственное или утверждённое написание;
- в остальных случаях допускается `е`, но одна и та же сущность во всех строках пишется одинаково;
- словарь терминов фиксирует выбранное написание, чтобы RU copy не расходился между миссиями.

## 6. Английский язык: редакторский и типографический контракт

### 6.1. Не переводить структуру русского предложения

Английская строка передаёт ту же задачу, но строится естественно для английского:

```text
RU: Когда все миссии будут выполнены, ты сможешь выйти на связь с главным спутником.
EN: Complete all missions to connect to the main satellite.
```

Второй вариант короче и прямее буквального `When all missions are completed, you will be able to...`. Для игрового UI это предпочтительно, если не меняет условие.

### 6.2. Голос и синтаксис

- Использовать active voice и конкретный глагол.
- Для инструкций использовать imperative: `Choose`, `Build`, `Launch`.
- Убирать вводные обороты `You can`, `In order to`, `Please note that`, если без них смысл сохраняется.
- Один шаг — одно главное действие.
- Не цеплять много существительных-прилагательных перед существительным; длинную цепочку лучше перестроить.
- Термины `mission`, `route`, `signal`, `satellite`, `network core` должны быть единообразны во всём продукте.

### 6.3. Регистр и пунктуация

- Базовый стиль — sentence case: `Launch the signal`, не `Launch The Signal`.
- Точка ставится у полного предложения, но не у кнопки, label или заголовка.
- Для американского варианта английского house style использует serial comma: `terminals, satellites, and gateways`.
- Английское тире `—` используется без пробелов: `Complete the route—then launch the signal`.
- Типографские кавычки: `“outer”` и вложенные `‘inner’`.
- В человеческом тексте использовать апостроф `’` (`don’t`), а ASCII `'` оставлять синтаксису и идентификаторам.

### 6.4. Переносы в английском

- `a` и `I` не должны оставаться одиноко в конце строки на компактных поверхностях.
- В заголовках и кнопках желательно удерживать смысловые пары: артикль + существительное, короткий предлог + дополнение, имя + квалификатор.
- Нельзя глобально заменять каждый пробел после `the`, `to`, `of`, `in` на NBSP: это создаёт слишком длинные блоки.
- Для заголовков сначала применять `text-wrap: balance`, затем точечно защищать критическую пару.
- Автоматические переносы слов в кнопках и коротких заголовках запрещены; в длинном body copy допустимы только после проверки английского словаря браузера.

## 7. Правильное управление переносами в web runtime

### 7.1. Какие Unicode-символы использовать

| Задача | Символ | Код | Пример |
|---|---:|---:|---|
| Видимый неразрывный пробел | NBSP | `U+00A0` | `№ 1` |
| Узкий неразрывный пробел | NNBSP | `U+202F` | `20 %` после проверки шрифта |
| Неразрывный дефис | NBHY | `U+2011` | `по‑русски` |
| Невидимая склейка | WORD JOINER | `U+2060` | редкие случаи без видимого пробела |
| Мягкая возможность переноса | soft hyphen | `U+00AD` | только словарно проверенные слова |
| Дополнительная точка переноса | `<wbr>` / ZWSP | — / `U+200B` | URL или длинный технический токен |

Для обычных слов нужен NBSP, а не WORD JOINER: слова должны оставаться визуально разделены.

### 7.2. Почему не `&nbsp;` в JSON

`wording.json` является данными, а не HTML. Текущий runtime подставляет большинство строк через `textContent` или экранированную HTML-разметку. Последовательность символов `&nbsp;` из JSON в таком пути будет показана буквально либо экранирована.

Правильные варианты:

- хранить реальный `U+00A0`;
- хранить видимый в diff JSON escape `\u00A0`, который JSON parser преобразует в тот же символ;
- предпочтительно хранить редакторски чистый текст и централизованно добавлять типографические связи после подстановки плейсхолдеров.

### 7.3. Рекомендуемый pipeline X-SPUTNIK

```text
wording template
  → проверка ключа и локали
  → подстановка плейсхолдеров
  → locale-aware typography formatter
  → безопасный textContent / escapeHtml
  → CSS wrapping
  → layout QA
```

Нормализация должна происходить **после** подстановки переменных. Иначе невозможно корректно собрать динамическое `№ {number}` или `{count} объектов`.

Рекомендуемый будущий API:

```js
t(key, variables, { typography: "body" })
t(key, variables, { typography: "heading" })
t(key, variables, { typography: "button" })
t(key, variables, { typography: "badge" })
```

Контекст нужен потому, что заголовок допускает более активное удержание коротких слов, а длинный абзац — нет.

Formatter не должен изменять:

- URL, email, file paths и технические ID;
- SVG/HTML и имена CSS-классов;
- содержимое плейсхолдера, помеченное как уже отформатированное число/время;
- пробелы внутри preformatted или code-поверхностей;
- авторские переносы без явного разрешения.

### 7.4. CSS-профили

Рекомендуемая основа:

```css
.ui-heading,
.ui-card-title {
  text-wrap: balance;
  hyphens: none;
  overflow-wrap: normal;
}

.ui-body,
.ui-instruction {
  text-wrap: pretty;
  overflow-wrap: break-word;
}

.ui-button,
.ui-badge,
.ui-timer {
  hyphens: none;
}

:lang(ru) .ui-body,
:lang(en) .ui-body {
  hyphens: auto;
}
```

Ограничения:

- `balance` применять к коротким блокам, обычно не более шести строк;
- `pretty` считать progressive enhancement: обычный перенос остаётся fallback;
- `hyphens: auto` включать только для длинного body copy после проверки целевого Chromium и шрифта Bureau;
- не использовать `word-break: break-all` для пользовательского текста;
- `overflow-wrap: anywhere` допустим для технического ID в редакторе, но не для фразы игрока;
- не ставить `white-space: nowrap` на предложение, если компонент не гарантирует достаточную ширину;
- ручной `<br>` — крайнее арт-директорское решение, отдельное для каждой локали.

## 8. Локализация и переменные

- RU и EN остаются рядом под одним семантическим ключом.
- Переводится целое сообщение, а не набор фрагментов.
- В обеих локалях сохраняется одинаковый набор именованных плейсхолдеров, но порядок может отличаться.
- Числа, проценты, даты и единицы форматируются через locale-aware API (`Intl.NumberFormat`, `Intl.DateTimeFormat`), а не вручную склеенными строками.
- Для множественного числа нужен plural-aware формат, а не `count + " объектов"`.
- Переводчику нужен контекст: тип поверхности, действие, лимит строк, значение плейсхолдера и связанный screenshot/state.
- Нельзя использовать один ключ для разных смыслов только потому, что русская строка сейчас совпадает.
- Терминология ведётся отдельным двуязычным glossary с preferred term и запрещёнными вариантами.

## 9. Автоматическая корректура

### 9.1. Ошибки, блокирующие сборку

- отсутствует RU или EN;
- различаются плейсхолдеры;
- leading/trailing whitespace, табы или двойные обычные пробелы;
- пробел перед `, . ! ? : ;`;
- `№1` вместо `№ 1` в русском тексте;
- `50%` вместо `50 %` в русском тексте;
- дефис с пробелами вместо тире: `слово - слово`;
- HTML entity (`&nbsp;`, `&mdash;`) в plain-text wording;
- непарные кавычки или скобки;
- встроенный `<br>`/HTML там, где поле не разрешает rich text;
- неизвестный wording key или пользовательский текст, зашитый в player JavaScript/HTML.

### 9.2. Предупреждения для редактора

- прямые ASCII-кавычки в человеческом тексте;
- точка в конце button/heading/label;
- два и более восклицательных/вопросительных знака;
- слишком длинная кнопка или заголовок относительно бюджета компонента;
- непараллельная грамматическая форма соседних шагов;
- канцеляризмы и слабые конструкции: `осуществить`, `произвести`, `имеется возможность`, `you can`, `in order to`;
- одинокая короткая последняя строка;
- потенциально висячее однобуквенное слово после фактического layout.

Лингвистический linter не должен автоматически «исправлять» смысл. Неоднозначные случаи выдаются как warning с ключом, локалью и предложением, а принимает изменение редактор.

### 9.3. Layout-тест

Статический regex не знает ширину строки. Для финальной проверки нужен layout-тест в реальном Bureau и целевом Chromium:

1. открыть каждый из пяти экранов в RU и EN;
2. проверить Full HD и 4K целевые viewport;
3. измерить `scrollWidth > clientWidth` и вертикальное переполнение;
4. получить line boxes слов через `Range.getClientRects()`;
5. сообщить, если строка заканчивается защищаемым коротким словом;
6. сообщить, если последняя строка заголовка слишком короткая относительно предыдущей;
7. сохранить screenshot diff для ручного просмотра.

Автотест сообщает о риске; решение остаётся за редактором и дизайнером, потому что одинаковая геометрия может быть приемлема в body copy и плоха в hero heading.

## 10. Процесс выпуска текста

1. **Автор** формулирует цель и действие без заботы о ручных переносах.
2. **Русский редактор** проверяет смысл, управление, терминологию, грамматику и пунктуацию.
3. **Английский редактор** делает самостоятельную локализацию, а не пословный перевод.
4. **Типографический formatter** добавляет только детерминированные неразрывные связи.
5. **Copy-lint** блокирует объективные ошибки и показывает warnings.
6. **Layout QA** проверяет RU/EN на реальных компонентах и разрешениях.
7. **Редактор + дизайнер** утверждают неоднозначные переносы и длину строк.
8. **Regression tests** закрепляют утверждённые ключевые формулировки.

Каждое изменение wording в pull request или локальном change set должно содержать:

- список изменённых семантических ключей;
- RU и EN рядом;
- причину изменения;
- screenshot обеих локалей для затронутых экранов, если меняется длина;
- результат copy-lint и layout QA.

## 11. Аудит текущей сборки X-SPUTNIK

Исходный аудит перед реализацией на 2026-09-07:

- `public/config/wording.json` содержит 131 запись, у каждой есть RU и EN;
- `src/wording.mjs` уже проверяет полноту локалей и равенство плейсхолдеров;
- язык документа динамически меняется через `document.documentElement.lang = language`;
- player runtime не хранит русский текст непосредственно в `main.js` и `index.html`;
- HTML из wording не исполняется: строки идут через `textContent`/`escapeHtml`;
- явных двойных пробелов, прямых кавычек и слитных русских процентов в текущем словаре не найдено;
- три строки статуса используют `МИССИЯ №1`, `МИССИЯ №2`, `МИССИЯ №3`; их следует привести к `МИССИЯ № 1`, `МИССИЯ № 2`, `МИССИЯ № 3`;
- типографического formatter после interpolation не было;
- copy-lint проверял структуру, но не русскую/английскую пунктуацию и типографику;
- gameplay CSS не задавал системного профиля `text-wrap: balance/pretty` и `hyphens`;
- в служебных редакторах встречается `overflow-wrap: anywhere`; для технических ID это допустимо, но такую политику нельзя переносить на player copy;
- ручные переносы через `\n → <br />` существуют и должны оставаться только для явно арт-директированных ключей.

## 12. Рекомендуемая реализация

### Этап 1. Безопасная корректура данных

- Исправить три `№1/№2/№3` на неразрывные `№ 1/№ 2/№ 3`.
- Добавить copy-lint для объективных ошибок из раздела 9.1.
- Зафиксировать glossary RU/EN и тип поверхности для ключей.

### Этап 2. Locale typography formatter

- Добавить чистую функцию `formatTypography(text, language, profile)`.
- Вызывать её после interpolation и до `escapeHtml`/`textContent`.
- Для RU начать с однобуквенных слов, `№`, `%`, чисел и единиц.
- Для EN начать с `a/I`, числовых связей и типографского апострофа только там, где замена однозначна.
- Не изменять URL, ID, пути и code-like строки.
- Покрыть каждое правило unit-тестом и тестом идемпотентности: повторная нормализация не меняет строку.

### Этап 3. CSS wrapping profiles

- Назначить семантические классы heading/body/button/badge.
- Включить `balance` для заголовков и `pretty` для описаний как progressive enhancement.
- Запретить hyphenation в кнопках, badge и коротких заголовках.
- Проверить Bureau при RU/EN, Full HD и 4K.

### Этап 4. Layout regression

- Добавить автоматическое обнаружение overflow и висячих слов в rendered UI.
- Проверить все пять screen states, карточки миссий, popups и финальный экран.
- Не публиковать автоматическое исправление спорного переноса без ручного утверждения.

## 13. Definition of Done для текста

Строка готова, если:

- смысл и следующее действие однозначны;
- RU и EN звучат естественно независимо друг от друга;
- терминология совпадает с glossary;
- пунктуация и типографские знаки соответствуют локали;
- защищены обязательные неразрывные пары;
- нет висячих однобуквенных слов на фактическом layout;
- нет overflow, обрезки, наложения или недопустимого уменьшения шрифта;
- в кнопках и коротких заголовках нет переноса внутри слова;
- `lang` соответствует активной локали;
- строка прошла schema, copy-lint, unit и layout проверки;
- обе локали просмотрены человеком в финальном компоненте.

## 14. Главное решение

Для X-SPUTNIK не следует вручную расставлять `&nbsp;` по всему JSON и не следует решать переносы только CSS. Надёжная система состоит из трёх слоёв:

1. редакторски выверенный самостоятельный текст RU и EN;
2. небольшой детерминированный locale-aware formatter для действительно неразрывных конструкций;
3. семантические CSS-профили и layout regression на реальных компонентах.

Такой подход устраняет висячие предлоги, не создаёт хрупких HTML entities в данных и масштабируется на новые миссии без ручного исправления каждой строки в каждом месте интерфейса.
