# Третий вид тегов MAX: переиспользование Discovery

Дата: 03.10.2026. Исследование выполнено до интеграции. Область: существующий поток тегов, стеклянная оболочка Discovery без внутренних белых клеток, текстовые таблетки и круглые плашки со смайликами. Новый движок, фоновые эффекты и настоящее преломление не требуются.

## Подтверждённая основа

В проекте уже есть готовая связка `artifacts/ribbon/discovery-arch.js` → `DiscoveryTagEngine` → `DiscoveryBubbles` (`discovery-bubbles.js`). Она содержит общий транспорт, инстансы, оболочку и кант, отдельный foreground текст, группировку по 32 объекта и защиту текста при пересечениях. Это существующий проектный механизм, который пользователь прямо просит переиспользовать. Предлагаемая итерация меняет его вариант отображения, а не создаёт аналог с нуля.

Текст уже растеризуется браузерным Canvas 2D в общем атласе: `tag-atlas.js` использует `measureText`, `fillText`, `THREE.CanvasTexture` и instanced geometry. Three в фактическом Ribbon — **r180** (`vendor/three.core.js`, `REVISION = '180'`), лицензия **MIT**, сохранена в `vendor/THREE-LICENSE.txt`. Версия `three` из `artifacts/max-game/node_modules` здесь не является версией runtime и не должна подменять её при проверке.

[`CanvasTexture` r180](https://raw.githubusercontent.com/mrdoob/three.js/r180/src/textures/CanvasTexture.js) реализует именно загрузку Canvas в GPU, включая начальный `needsUpdate`. [Лицензия r180](https://raw.githubusercontent.com/mrdoob/three.js/r180/LICENSE) разрешает адаптацию с сохранением copyright/license. [Официальный пример Canvas Textures](https://threejs.org/manual/pages/canvas-textures.html) описывает обновление после изменения содержимого; атлас неизменных надписей не нужно рисовать каждый кадр.

В [практическом обсуждении Three от 29.08.2020](https://discourse.threejs.org/t/writing-2d-text-onto-a-surface/18264) CanvasTexture прямо рекомендован для заранее неизвестного текста на поверхности, автор вопроса подтверждает найденный подход. Это подтверждает механизм, но не качество конкретных смайликов в нашем Electron.

LumiCells upstream в проекте имеет commit `1007717d72cfd9d768d4b9a3f7fc80a126e49c51`, metadata `UNLICENSED`; разрешение пользователя на полное использование и адаптацию сохранено в `vendor/lumicells/permission.json`. Discovery — проектная интеграция, её нельзя выдавать за неизменённый upstream-компонент LumiCells.

## Что необходимо учесть при адаптации

1. **Убрать клетки полностью.** Сейчас оболочка и cell ink смешиваются в одном fragment, а `glowFragment` отдельно добавляет свет клеток. Недостаточно поставить только `brightness=0` или спрятать один mesh: MAX должен пропускать field update и cell glow draw, а оболочка рисоваться без cell coverage. Общий label pass сохраняется. Это позволяет использовать уже существующий материал оболочки без нового blur/RT на каждый объект.
2. **Таблетка и круг.** Существующий SDF rounded rectangle уже задаёт форму; для таблетки радиус равен половине фактической высоты, для emoji ширина равна высоте. В нормализованных по высоте координатах это радиус `0.5`. Сейчас aspect в fragment вычисляется через `columns/rows`, поэтому MAX без сетки следует передавать фактический aspect позы либо поддерживать строго равное ему значение. Количество рядов не должно менять круглость emoji.
3. **Цвет смайлика.** Discovery label shader читает только `texture2D(uText, at).a` и рисует белый текст. Цветной emoji в таком тракте превратится в белый силуэт. Для emoji необходимо брать RGBA атласа, сохранять RGB и умножать на alpha ровно один раз перед существующим premultiplied blending. Белый текст можно оставить текущим путём. Атлас уже объявлен `SRGBColorSpace`; не выполнять дополнительный произвольный gamma decode. [Three Color Management](https://threejs.org/manual/pages/color-management.html) описывает разделение цветовых текстур и линейных вычислений.
4. **Размеры текста.** [Canvas `fillText`](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/fillText) использует текущие font/alignment/baseline; `maxWidth` способен уменьшать или сжимать текст. Для круга лучше заранее выбрать font size и измерить glyph bounds, а не получать деформированный смайлик принудительным растяжением. До создания атласа дождаться используемых web fonts.
5. **Стабильность.** Выбор emoji/text производится один раз по устойчивому ID/seed или сохранённому каталогу; не выбирать новый контент при каждом frame. Существующий транспорт, число слотов, speed spread и защита текста сохраняются. Переключение visual не должно сбрасывать transport phase. Safe Zone для emoji — его локальная читаемая область, а не пустая строка с нулевой шириной.

## Emoji и переносимость

Минимальная локальная реализация — браузерный `fillText` с явным системным emoji font stack, включая `Segoe UI Emoji` на Windows. [Microsoft подтверждает](https://learn.microsoft.com/en-us/typography/font-list/segoe-ui-emoji), что этот шрифт поставляется с Windows 10/11, и отдельно описывает лицензирование распространения. Использовать установленный шрифт можно без копирования файла в проект; его наличие в ОС **не означает** разрешение включить TTF в переносимый комплект. Новую шрифтовую зависимость и её упаковку в этой итерации не вводить.

Рисунок, поддержка Unicode/ZWJ и метрики emoji зависят от ОС и шрифта. [Issue node-canvas #614, 2015](https://github.com/Automattic/node-canvas/issues/614) содержит реальный случай: emoji отсутствовал в серверном node-canvas, но работал в обычном HTML Canvas. Это не текущий баг Chromium и не аргумент заменять браузерную растеризацию; это причина проверять атлас именно в рабочем браузере, а не доказывать его CPU-тестом Node.

[CSSWG issue #9291](https://github.com/w3c/csswg-drafts/issues/9291) фиксирует сложности определения emoji fallback/variation selectors. Вывод для MVP: небольшой проверенный набор распространённых односимвольных emoji; не обещать одинаковую графику на всех ОС. Если нужна побайтная воспроизводимость рисунка на разных машинах, следующая итерация должна исследовать и закрепить лицензированный локальный набор готовых emoji-изображений. Самостоятельно рисовать заменители либо молча добавлять удалённый CDN не требуется.

## Решение и границы уверенности

Выбран путь **существующий Discovery shell/instance pipeline + CanvasTexture r180/Canvas 2D для контента**. Готовый механизм решает растеризацию и GPU-доставку, существующий Discovery решает оболочку, композицию и движение. Новая внешняя библиотека здесь дублировала бы уже работающий механизм; её установка не нужна.

Подтверждено чтением кода: библиотека/версия, shared atlas, premultiplied material, отдельные field/glow/label passes и текущая потеря RGB в label shader. Предлагаемые capsule radius, emoji sizing и пропуск cell passes — узкая адаптация параметров готового renderer, ещё не подтверждённая live-результатом этим исследованием.

Нужная малая проверка интеграции: три visual варианта доступны отдельно; MAX содержит таблетки и истинные круги; нет белых клеток и их glow; emoji сохраняют внутренние цвета и не имеют прямоугольного alpha-фона; текст читабелен; переключение не сбрасывает движение; Discovery и LumiCell не меняются. Проверить фактическую страницу, ошибки консоли, сохранение выбранного visual, reload и активный worker. Свечение букв, blur фона и новые цветовые эффекты не добавлять. Итоговые кадры/технические результаты сохранить отдельно в `artifacts/reports/`; художественная приёмка пользователя остаётся открытой до отзыва.
