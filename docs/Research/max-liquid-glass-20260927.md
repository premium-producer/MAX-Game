# Liquid Glass для стены MAX: реализации и оптимизация

Дата: 27.09.2026. Задача: заметные стеклянные сферы в едином пространстве экрана, видимые только через игровые панели. Исследованы первичные документация, репозитории и авторские разборы. Сторонние демо не запускались на GPU стенда; сравнительных замеров их FPS нет. Оценка применимости ниже — инженерный вывод, а не независимый бенчмарк.

## Что выбрать

Для нынешней архитектуры рекомендуется собственный небольшой screen-space shader поверх уже существующей GPU-текстуры фона. Использовать общую композицию из трёх линз и маску панелей; менять маску при переключении two/single. Не создавать материалы, сцену или снимок фона отдельно для каждого квадрата. Готовые проекты полезны как оптические и архитектурные референсы; установка дополнительного React-рендера или полного редактора стекла здесь не оправдана.

## Сравнение готовых подходов

| Решение и первичный источник | Возможности и ограничения | Применимость к MAX |
|---|---|---|
| [Liquid Glass Studio](https://github.com/iyinchao/liquid-glass-studio) | MIT, SDF, refraction, Fresnel, управляемый glare, multipass Gaussian blur; README заявляет WebGL2/WebGPU. В TODO остаются отдельные WebGPU/editor/HDR/UI пункты, поэтому полноту backend нельзя выводить из заголовка. | Самый близкий референс для плоского shader-прохода. Перенять разделение маски, нормали, отражения и фона; не переносить dispersion и весь редактор. |
| [drei MeshTransmissionMaterial](https://raw.githubusercontent.com/pmndrs/drei/master/docs/shaders/mesh-transmission-material.mdx) | Transmission/thickness/IOR/roughness, общий `buffer` или `transmissionSampler`, регулируемые samples/resolution. Авторы предупреждают о дополнительном рендере сцены; backside увеличивает стоимость. [Лицензия MIT](https://github.com/pmndrs/drei/blob/master/LICENSE). | Подходит для настоящих 3D-объектов с окружением. Для двух экранных масок избыточен. Полезный принцип — один общий buffer; не выделять его каждой сфере. |
| [Three.js MeshPhysicalMaterial](https://threejs.org/docs/pages/MeshPhysicalMaterial.html) | Физический материал с transmission, IOR, thickness; документация отмечает повышенную стоимость пикселя и рекомендует environment map. | Кандидат при возвращении к объёмной сцене. Применение материала само по себе не решит незаметность стекла на гладком фоне и не обеспечит быстрый вывод. |
| [rdev/liquid-glass-react](https://github.com/rdev/liquid-glass-react) | MIT, готовый React-компонент с преломлением, blur, elasticity. README предупреждает о частичной поддержке Safari/Firefox и нестабильности shader-mode. [Код](https://github.com/rdev/liquid-glass-react/blob/master/src/index.tsx) показывает SVG displacement: shader-mode генерирует карту, а не выполняет непрерывный WebGL-рендер всей сцены. | Удобнее для DOM-кнопок. Не является прямой заменой проходу между нашим Ribbon RT и GPUAtlas. Добавляет другой путь композитинга; аберрацию нужно отключать. |
| [kube: Liquid Glass in the Browser](https://kube.io/blog/liquid-glass-css-svg/) | Авторский разбор профиля линзы, карты смещения и specular. Автор называет прототип экспериментальным: изменение размеров/формы требует перестройки карты, SVG backdrop ограничен Chromium. | Хорош для понимания фаски и контраста края. Electron совместим по семейству движка, но работоспособность конкретного OSR/Spout пути этим не доказана. |

Ни одному репозиторию не приписывается подтверждённая стабильность на нашем 4096×1280 стенде. Популярность проекта и красивое демо не заменяют проверки интеграции. Сторонний код и зависимости в этой итерации не копировались/не устанавливались.

## Почему текущее стекло почти исчезало

По локальному коду до изменения: линзы создавались заново на основе размеров каждой панели; two получал одинаковый мотив дважды, single — другую композицию. Радиальная нормаль внутри линзы была слабой, а выраженное преломление концентрировалось в узкой полосе края. Широкие гладкие потоки почти не меняются при малом UV-смещении. Белый блик дополнительно подавлялся под меню, оставляя едва видимые дуги. Пять выборок размытия сглаживали и без того плавный фон.

Это не означает, что нужен ещё более сильный общий bloom. Он может размыть границы и ухудшить текст, не проявив объём. Нужны разные оптические признаки: изгиб фонового потока, тёмная сторона фаски, светлый контур, широкое отражение движущегося окружения. В [докладе Apple](https://developer.apple.com/videos/play/wwdc2025/219/) материал также описывается как система преломления, освещения, теней и адаптации читаемости. Это источник принципов, не доступный WebGL SDK. Рекомендации Apple о назначении системных controls не подменяют клиентскую композицию MAX.

## Предлагаемая оптика

1. Три круга в глобальных координатах 4096×1280. Положение/радиус/фаза одинаковы в two и single; одна сфера пересекает промежуток между квадратами. Маска скрывает внешние части, но не меняет геометрию.
2. Более выпуклая нормаль и заметное преломление внутри круга, с ограничением смещения по доступному halo. Один IOR, без разделения RGB.
3. Движущиеся широкие отражения условного студийного света, рассчитанные аналитически по нормали. Цвет — только интерполяция разрешённых MAX cyan/violet; не радужная иризация. Это художественная модель окружения, а не ray tracing отражений сцены.
4. Затемнённая кромка рядом со светлой усиливает ощущение толщины. Белые glints скрываются под текстом; слабые цветные переливы остаются. Текст/иконки рисуются после стекла и не преломляются.
5. Общая анимация по существующим часам сервиса: пауза останавливает её, reduced motion фиксирует время. От переключения маски анимация не стартует заново.

Применяются max.glass.limit, max.glass.dispersion, max.glass.highlights, max.overlay.layering/paint и проектная палитра. Три декоративных Glass Shape укладываются в лимит четырёх; игровые сигнальные кольца — отдельная механика. Не менять исходный фон стены и не возвращать пикселизацию.

## Оптимизация и границы доказательств

- Сохранять один existing renderer, один reusable HalfFloat input и существующий GPUAtlas. Не захватывать DOM/canvas для каждой линзы.
- На гладком фоне убрать пятивыборочное размытие: один исходный и один смещённый lookup внутри маски вместо шести суммарно. Это уменьшение texture fetch в коде; фактическое ускорение зависит от GPU/компилятора и не измерено отдельно.
- Отбрасывать стеклянный проход для тайлов, полезный crop которых не пересекает маски с запасом тени. Сами фоновые тайлы не отменяются. В действующей раскладке pass count стекла уменьшается с шести до четырёх.
- Не добавлять HDR environment map, raymarch, backside или отдельную цепочку bloom ради текущих трёх линз. Аналитические отражения требуют арифметики, но не дополнительных текстур/буферов.
- Один текущий input 2176×1208 RGBA16F — около 20.05 MiB. Это оценка выделения, не полный GPU memory budget приложения.
- Главные оставшиеся кандидаты оптимизации всей стены — избыточная площадь остаточных тайлов, DOF гладкого фона и цепочка OSR/present. Изменение стекла не закрывает эти задачи; см. [диагностику](../../artifacts/reports/max-fps-diagnostic-20260927/README.md).

Следующий эксперимент при отдельном разрешении на нагрузочный прогон: фиксировать разрешение, сцену, клиентов и фон, сравнить glass on/off; измерить GPU-проход и полный frame-time отдельно. Проверить швы тайлов, текст, движение на LED и нижнюю границу FPS. До этого не обещать 60 FPS и не объявлять выбранный вариант быстрее всех библиотек.
