# MAX BFM — подключение прохождения

03.10.2026. Используем существующие Mission SessionPort, каталог и `sharedTaskMarkup` из MAX. В каталог/правила/клиентские тексты изменений нет. BFM renderer получает snapshot и отправляет только разрешённое actionId с screenId/revision.

Опора на готовые механизмы: [HTMLImageElement.decode](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode) готовит изображение до включения в DOM; [ViewTransition.finished](https://developer.mozilla.org/en-US/docs/Web/API/ViewTransition/finished) завершает нативный переход; [updateCallbackDone](https://developer.mozilla.org/en-US/docs/Web/API/ViewTransition/updateCallbackDone) отделяет изменение DOM от конца анимации. Browser API не имеет отдельного npm-пакета/лицензии; существующая BFM адаптация и её provenance сохраняются. Нового собственного анимационного движка нет.

Практический опыт: в исследовании BFM Mirror 07 зафиксирован конфликт одновременных snapshot/entrance и повторное появление. Поэтому обновление кадра внутри одного задания использует только native dissolve; отдельный entrance запускается при смене задания. Исследование расписания обосновывает сохранение стабильных DOM-оболочек. Источники и SHA — [первое исследование](max-bfm-presentation-20261003.md). В MAX неоднократно наблюдались пустые телефоны: старый кадр теперь сохраняется до decode всех изображений именно входящей DOM-разметки, включая QR. Ошибка не считается готовностью, есть явный retry; поздняя загрузка отменённого экрана не применяется.

Порядок: общий backend подтверждает scan → BFM раскрывает иконки → показывается подготовленное задание → команды ACT → подтверждённый result → следующий task → completed/incomplete с каталоговым QR. Таймер/автоматические переходы принадлежат backend. Renderer не опрашивает автоматический переход до показа подготовленного экрана; минимальное время его видимости берётся из descriptor. При скрытии страницы владелец ввода освобождается, автопереходы останавливаются.

Область итерации — один универсальный адаптер прохождения. Он обслуживает все шесть каталоговых миссий, но пользовательская проверка начинается с полного блогера и двух веток канала. Пробелы контента показываются как missing и не превращаются в успех. Режим server, drag и сложные безопасные маршруты перемещения не добавляются. Ring→task использует существующий BFM dissolve, не заявляется физически непрерывным полётом объектов.
