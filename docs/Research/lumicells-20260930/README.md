## Устройство

| Слой | Фактическая роль | Польза для нас |
|---|---|---|
| `src/schema` | Типы, ограничения, defaults, presets, экспорт, JSON Schema и пути параметров; схема используется для GPU macros и панели | Согласованные настройки/API/панель, без нескольких расходящихся таблиц |
| `core/controller` | CPU clock, tween, modulator, события, координаты, палитра, качество; выдаёт FrameInputs | Художественное управление отдельно от renderer и интерфейса |
| `core/engine` | Собственный WebGL2: MRT field, маленькие glow-текстуры, stamp, composite и отдельные lift-копии | Перенос дорогих расчётов в клеточное разрешение |
| `core/dom` + facade | Canvas, pointer, отслеживание элементов, visibility, lifecycle, общий ticker внутри страницы | Хорошо для браузерного фона; для наших рабочих источников нужен внешний clock/ввод |
| React/Element/demo | Обёртки и редактор; React19 — необязательная peer dependency | Core не требует React или Three.js; редактор не нужен в production-worker |

Это не готовый модуль TouchDesigner/Spout/LAN. Каждый Engine владеет отдельным WebGL-контекстом, общий RAF работает внутри страницы, а не синхронизирует разные компьютеры.

## Как получается картинка

**Форма и наличие клеток отделены от энергии.** Режим возвращает три значения: intensity, envelope, accent. Envelope управляет разреженностью, intensity — свечением, accent — локальной окраской. В sphere широкое тело не сводится к тонкой линии. На периферии вероятность присутствия падает быстрее, чем яркость оставшихся клеток: остаются редкие читаемые квадраты вместо одинаково тусклой сетки. Плавное изменение hash-эпох не пересоздаёт случайный рисунок каждый кадр.

Это важное отличие от нашего native-plane: сейчас одно activation одновременно задаёт размер и `f+f²` света. Увеличивая ширину, мы неизбежно меняем сразу плотность, размер и яркость. Для дальнейшей настройки полезно разделить эти каналы, сохранив исходный NlK3Wt-материал как контроль.

**Основная сетка не состоит из настоящих 3D-кубов.** Stamp один раз рисует SDF скруглённого тела, внутреннее ослабление эмиттера, маску горячего центра, направленную фаску и веса ореола. Composite читает этот маленький образец. Нормального материала с физическими переотражениями здесь нет. Lift отдельно рисует до128 инстансных quad: наклон с перспективой, имитация тени и сияния, но без экструдированных граней куба. Значит, объёмное ощущение можно получать гораздо дешевле полной сетки 3D-мешей; наличие инстансинга не означает, что вся сетка геометрическая.

**Яркость и насыщенность не тождественны белизне.** Цвет идёт через палитру LUT; горячий оттенок ограничен центральной маской клетки, край и halo остаются насыщенными. Hot определяется до усиления редких клеток, чтобы одиночная клетка на периферии не становилась белой. Цветовое смешивание и финальный tonemap устроены иначе, чем у чистого NlK3Wt; прямое включение всей оптики Lumicells изменит утверждённый нами подход.

**Три масштаба света:** тесный halo из соседей, bloom из клеточной эмиссии, широкая haze из уменьшенной текстуры. Bloom threshold имеет мягкое колено; энергия учитывает площадь скруглённой клетки и зазор. Это не размытие готовых карточек/текста. Но haze, цветные пятна подложки и финальный tonemap всё равно присутствуют в авторском look: автоматически переносить их на native-фон нельзя.

## Какие режимы нам подходят

| Режим | Что делает по коду | Наш возможный сценарий |
|---|---|---|
| `sphere` | Широкая полая оболочка, отверстие, асимметрия, свет, вращающийся шум | Стела/Discovery: живой круг с неоднородной периферией; форма не обязана оставаться кольцом |
| `pulse` + API `pulse()` | Бегущие Gaussian-кольца, ширина учитывает шаг клетки; события затухают | Тап, выбор, посадка элемента, локальный расходящийся импульс |
| `wave` | Пересечение плоских и круговой волн, плавный domain warp; гребни изгибаются/сливаются | Длинные волнообразные разрезы на общем заднем домене |
| `flow` | Пороговый движущийся fBm с вращением октав | Небольшая модуляция; как основа фона может снова дать отвергнутые «острова» |
| `ripple`, `vortex` | Круговые волны/спиральные функции | Дополнительные событийные состояния после отдельной художественной оценки |
| `life`, `rain` | Автомат и падающие столбцы | Технические примеры, не основной look стенда |

`flow` здесь — процедурная функция, **не Navier–Stokes fluid solver**. Контур посетителя нельзя заменить набором light-influence прямоугольников без потери формы/динамики. Наш solver и локальный dye/halo сохранять; подавать их в световое поле отдельным каналом. Имеющиеся64 influences/16 pulses/128 lifts — фиксированные пределы API, не лимит количества клеток; для масок людей нужен отдельный texture-input адаптер.

## Производительность и крупные полотна

Главная оптимизация: сложные режимы/noise выполняются один раз на клетку в MRT. В нашем native-plane функция формы повторяется для каждого фрагмента клетки в полноразмерном проходе; итог одинаков на всей клетке, но GPU вычисляет его много раз. При шаге32px это примерно1024 одинаковых вычисления поля на клетку, без учёта краёв. Клеточное поле не отменяет финальную заливку экрана, но убирает повтор сложной математики.

Stamp кеширует одинаковую форму. Glow-фильтры работают на клетках; haze в¼ линейного размера. Итоговая композиция делает один lookup объединённого glow. Отключённые режимы ограждены uniform-ветками, glow-pass пропускается при нулевых strengths. Upload параметров/LUT делается по dirty-флагам, Frame UBO отправляет только используемые диапазоны; ресурсы выделяются с запасом и гистерезисом размеров. GPU timer получает асинхронные результаты и исключает disjoint.

Stamp не является прямой заменой нашему shader: тело основной клетки Lumicells имеет фиксированный размер по gap, а у нас размер непрерывно зависит от activation0…0.95. Для кеширования нужен sample-space образец с масштабированием, возможно LUT по размеру/фаске; проверить AA и отсутствие изменения рисунка при масштабировании. Кеширование всего материала также может убрать нужный внутренний перелив. Начинать с поля, а не с полной замены фаски.

Стандарт Lumicells ограничивает площадь canvas: maxPixels default4.2MP, допустимый config максимум12MP; coarse pointer cap2.4MP, software0.5MP. Auto может снизить scale до0.5, low убирает halo/фаску. При превышении аппаратной длины geometry уменьшает обе стороны пропорционально. **Полноценного tiled output для огромного полотна в изученном engine нет.**

У нас задний домен7168×1280 =9.175MP; left3.932MP и right5.243MP. Уже полный фон и правая часть превышают default4.2MP. Лента10240×512 =5.243MP, арка5120×512 =2.621MP, стела1080×1920 =2.074MP. Пять рабочих источников суммарно19.113MP/кадр, около1.147млрд выходных пикселей/с при60FPS, до дополнительных проходов/передачи. Это арифметическая оценка, не GPU-бенчмарк. Для наших Spout выходов нельзя использовать default auto-downscale.

README приводит авторские замеры на RTX5090 и заявляет ориентацию на60+FPS. Они не являются нашей проверкой: неизвестны все параметры замера и подтверждение фактического drawingBuffer без budget/downscale. GPU timer движка не измеряет Electron capture, Spout, MAX foreground, просмотрщик и TD. Следовательно, ускорение нашего полного тракта пока гипотеза.

## Как применить у нас

Рекомендация: сначала перенять архитектурные принципы в существующий renderer, а не подключать всю библиотеку вторым canvas/context с собственным RAF.

1. **Изолированный эксперимент на стеле.** Три выходных канала поля: энергия, coverage, accent; отдельно response размера0…0.95. Сохранить чистую фаску/цвет NlK3Wt и локальный fluid. Сравнить широкую форму, редкую периферию, тонкое ядро в известных фазах без фоновой дымки. Production не переключать по факту удачного маленького примера.
2. **Клеточный field-pass.** Вычислять форму один раз на глобальный cell ID. Shared seed, master time, единицы шага клетки; локальные импульсы и маски идут в общем пространстве. Затем existing shader рисует материал из поля. Не создавать отдельную сцену света по имени источника.
3. **Заднее полотно.** Расчёт в7168×1280 до3072+4096 crop. Центр, hash, палитра и clock от полного домена; независимый host-centered Controller для каждой половины создаст новый стык. Для фильтров одинаковое полное поле или корректный padding; lift/pulse события имеют общий ID/startTime/seed. На LAN нельзя надеяться на локальный Math.random/RAF; Life и другие stateful режимы требуют master-state или детерминированных шагов.
4. **Оптика только отдельно.** Native-профиль оставить без фонового haze/bloom/тонмаппинга. Если пользователь выберет внешний look Lumicells, создать обратимый новый профиль и отдельно сравнить яркость/насыщенность; не добавлять всё поверх clean shader. Локальный физический halo остаётся независимым.
5. **Доставка и измерения.** Полноразмерный final→Spout, сниженные preview после final. Производительность измерять раздельно для field, material, optional glow, foreground и capture/Spout, без auto-снижения финального разрешения. Heavy-прогон только с отдельным согласием.

Schema-generated UI, сравнение поля/клеток/halo и фиксированные seed/time особенно полезны для нашего арт-дир процесса. Tune задаёт виртуальные60Hz и seed; это механизм повторяемого кадра, а не доказательство реальных60FPS. Тесты clock, kernels, upload, lifecycle и config показывают осмысленное покрытие; тесты этого upstream здесь не запускались.
