# MAX: сборка пути по сценарию миссии

Дата: 29.09.2026. Статус: исследование и предложение; игровая реализация, сохранения и публикация не изменены. Основной адресат — клиентская редакция. Применение новой механики к первой, сравнительной странице отдельно не предполагается.

## Вывод

Путь стоит представлять компактной схемой миссии. Число иконок определяет плотность, а зависимости между заданиями — форму: квадрат для истории блогера, дерево для Цифрового ID, кольцо независимых возможностей общения, развилка с выбором одного инструмента для бизнеса. «Открыть MAX» входит в число видимых узлов, но не считается выполненным заданием.

Нужны три независимые сущности: сценарий заданий, расположение на поле и движение между позициями. Форма не должна добавлять новые обязательные задания или превращать независимые действия в последовательные.

## Основания и границы

- Новое указание пользователя: убрать постоянное расширение ряда вправо; MAX сначала появляется в центре, затем может двигаться вверх; для ID центральная метка «Создать Цифровой ID», ниже одновременно три плюса «Открой свои возможности».
- Ранее утверждено: старт «Открыть MAX», затем выбор иконок, полная сборка, «Путь намечен», задания. Нажатие добавления открывает выбор, не телефон. Сохраняются все пять заданий общения, одна бизнес-ветка, отдельные состояния и прогресс двух редакций.
- Клиентские источники: [сценарий миссий](../../artifacts/max-game/incoming/Пользователь_VK_MAX13.md), [исходный DOCX](../../artifacts/max-game/incoming/max-client-wording-20260923.docx). Актуальная интерпретация — [EDITIONS](../../apps/max-game/docs/EDITIONS.md). Сюжетные анимированные сцены остаются заглушками «АНИМИРОВАНАЯ СЦЕНА ???»; анимация интерфейса от этого ограничения отделена.
- В этой работе изучены код и материалы. Живое прохождение, измерение плотности на стене и пользовательское тестирование новой схемы не проводились. Предложенные интервалы анимации и положения — начальные параметры для прототипа.

## Что реально работает сейчас

| Место | Фактическое поведение | Что потребуется для новой схемы |
|---|---|---|
| `journey-route-layout.mjs: routeLayout` | Принимает количество, флаг следующего шага, размеры. Все центры имеют один Y; ряд каждый раз центрируется | План по миссии, узлам и постоянным местам, а не только по количеству |
| `journey-main.js: planningLayout / arrangeRoute` | Сопоставляет центры объектам по порядку массива | Сопоставление по semantic ID / slot ID |
| `nextRoutePoint`, `data-route-next` | Один следующий плюс, последняя точка массива | Несколько одновременно доступных мест с независимыми ID |
| `journey-state.mjs: PICK / PLACE` | Picker хранит x/y, PLACE добавляет выбранный step | Хранить идентификатор выбранного места, валидировать его допустимые задачи |
| `planningSteps / unlocked` | При сборке проверяется размещение prerequisite, при выполнении — его завершение | Сохранить разделение двух этапов |
| `journey-links.mjs: nearestLinks` | Минимальное дерево по расстоянию; роли миссии не участвуют | Для новой схемы задавать смысловые пары отдельно от геометрии |
| `journey-client.mjs: clientContent` | Сфера включена в аккаунт; отдельный sector удалён из клиентского пути | Бизнес состоит из MAX, аккаунта и одного выбранного инструмента |

У блогера в текущем JSON нет `requires`: квадрат сам по себе не введёт порядок выполнения. У ID три задачи требуют `create-id`, у бизнес-инструментов требуется `account`. Общение не имеет межзадачных зависимостей.

## Предлагаемые композиции

### 1. Стать блогером — квадрат из четырёх узлов

Четыре узла включают MAX и три задания. Можно использовать квадрат, повёрнутый в ромб: MAX сверху, канал справа, общение снизу, статистика слева. При невысокой зоне — более плоский квадрат 2×2. Это один компактный обход по часовой стрелке, без расширения ряда.

```text
                  MAX
                   ↓
   Статистика                  Канал
        ↑                        ↓
           Общение с подписчиками
```

Смысловой маршрут: MAX → канал → общение → статистика. Обратную связь статистика → MAX не рисовать: квадратное расположение не означает замкнутый сценарий.

После вступления MAX уходит в верхнюю позицию; справа появляется следующий плюс. Каждая новая иконка занимает своё место; следующий плюс появляется дальше по контуру. Рекомендация — направлять сборку в порядке клиентской истории. Это новая UX-рекомендация: сейчас пикер разрешает выбрать любой из трёх объектов. Во время сборки по-прежнему открывать пикер, даже если на данном этапе остался один допустимый вариант. Не вводить жёсткие блокировки выполнения блогера только из-за геометрии; если понадобится обязательный порядок заданий, зафиксировать это отдельным изменением `requires`.

### 2. Цифровой ID — дерево 1 → 1 → 3

```text
                     Открыть MAX
                          │
                 Создать Цифровой ID
                    ╱     │     ╲
                 Отель  Льгота  Возраст
```

Последовательность интерфейса:

1. Нажатие центральной кнопки представляет MAX: появление, удержание примерно 0,5 секунды, затем плавное движение вверх.
2. На месте исходного центра появляется именованная метка «Создать Цифровой ID». Это ещё не размещённое/выполненное задание. Отличать её контурным состоянием и подписью действия; не показывать галочку или значок задания.
3. Нажатие метки открывает выбор с единственной иконкой «Создать Цифровой ID». Так сохраняется правило пользователя о пикере и исключается неожиданный телефон. Выбор ставит настоящую иконку в центральную позицию.
4. Одновременно становятся видны три нижних плюса, каждый с подписью «Открой свои возможности». Они равноправны. Для навигации с клавиатуры — разные доступные имена «Выбрать возможность 1/2/3».
5. Любой плюс открывает оставшиеся варианты: отель, льгота, возраст. Выбранная иконка занимает именно нажатое место; повторный выбор уже размещённого варианта исключён. Поэтому порядок нижних иконок зависит от выбора человека и сохраняется.
6. Когда заполнены все три места, появляется существующий попап «Путь намечен». После «Продолжить» сначала выполняется создание ID. Остальные три задания до этого показывают понятное состояние ожидания «Сначала создай Цифровой ID».
7. Выполнение создания разблокирует все три применения одновременно. Выполнять их можно в любом порядке; миссия завершается после всех трёх.

**Важное различие:** три плюса появляются после постановки ID при сборке, а три задания становятся доступными после выполнения ID при прохождении. Постановка не выдаёт готовый документ и не засчитывает задание. Вариант «сначала пройти ID, затем только строить ветки» смешивает сборку и прохождение, поэтому для первой итерации не предлагается.

Линки: MAX–ID, ID–отель, ID–льгота, ID–возраст. Между нижними узлами связей нет: их близость не означает зависимость.

### 3. Общение — кольцо из шести узлов

MAX занимает верхнее место, пять заданий — остальные места по окружности или эллипсу. Все пять сохраняются: звонок, сообщение, группа, стикер/реакция, история. Голосовое/видеокружок и стикер/реакция остаются вариантами внутри своих заданий, а не дополнительными иконками.

Сборка идёт по контуру: после каждой постановки следующий плюс появляется в следующем свободном месте. Открывается выбор всех оставшихся возможностей; пользователь назначает им места. Один плюс за раз снижает визуальный шум в сравнении с пятью одинаковыми плюсами сразу. Для ID три одновременных места объясняют развилку; для общения такое одновременное раскрытие необязательно.

При прохождении все пять задач независимы. Не рисовать направленную цепочку, обещающую обязательную последовательность. Предлагаемые смысловые связи — от MAX к возможностям, тонкие кривые с разведёнными выходами; отдельной яркой обводки всего кольца не нужно. MAX сверху на контуре, не дополнительный седьмой узел в центре. При недостаточной высоте кольцо превращается в сетку 2×3 с теми же местами и смыслом.

### 4. Бизнес — основание и выбор одного инструмента

```text
                  Открыть MAX
                       │
                Бизнес-аккаунт
                       │
             Выбери один инструмент
             /         |          \
           Канал      Бот       Витрина
```

Три нижних варианта — содержимое выбора, а не три обязательных места на поле. После MAX именованное место аккаунта открывает пикер. После его постановки появляется один плюс «Выбери инструмент продвижения», открывающий три варианта. После выбора на поле остаётся только выбранная ветка. Итог — три узла, компактная композиция с MAX сверху и аккаунтом/инструментом ниже. Сфера бизнеса выбирается внутри задания аккаунта.

Прохождение: сначала подключение аккаунта, затем выбранный инструмент. Не переносить сюда поведение ID «заполни все три»: это изменило бы клиентский сценарий. Если впоследствии пользователь меняет инструмент через существующую навигацию, завершённые задания сохраняются, а готовность текущего пути пересчитывается для новой ветки.

## Раскладка, движение и выбор

Рекомендация — заранее резервировать итоговые места миссии и раскрывать их по сценарию. Уже размещённые объекты не переезжают при каждом новом выборе. Перестроение нужно при изменении размера зоны или смене ветки, с сохранением текущей позиции и скорости.

Первое появление сохранить по существующему механизму: около 240 мс раскрытия, 500 мс удержания, затем пружина к миссионной позиции. Это презентация MAX, не новое видео. Следующий доступный шаг проявляется после вступления. Новый плюс: мягкое появление из 88% масштаба, ориентир 350–500 мс; несколько плюсов ID получают одно событие раскрытия, а не зависят друг от друга. Точное время — настройка прототипа, а не обещание одинаковой длительности пружины.

У нескольких мест должны быть постоянные ключи, например `id-opportunity-1/2/3`. Нельзя переиспользовать для них один motion-state `route-add`: это даст телепортации и смешение скорости. Выбранный объект летит непосредственно в назначенное место, его связи учитываются уже во время полёта по текущим координатам. Отмена меню отменяет pending placement; занятые места и прогресс не меняются.

Пикер раскрывается в ближайшей свободной области. Защищать плитки, полные подписи, бейджи, «Назад» и запас парения. Проверять также траекторию полёта: свободная конечная точка не гарантирует свободный путь. При препятствии — плавная дуга через свободный коридор; если места нет, компактное меню в свободной части UX-полосы. При открытом выборе остальные плюсы временно не принимают ввод; один picker на зону. Отмена возвращает фокус на исходное место.

Для reduced motion — конечные позиции и появление без перелёта/всплеска, без задержки доступа к следующему шагу. Отключаемость необязательного движения соответствует [W3C, Animation from Interactions](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions).

## Ограничения стены и адаптация

Порядок приоритетов: доступность действий → читаемость подписей → отсутствие пересечений → узнаваемая схема → геометрически идеальный квадрат/круг.

Сейчас host мастера занимает физическую UX-полосу 1–1,8 м (Y615…1020, около405 логических пикселей). Свободное перемещение игровых объектов разрешено в 0,8–2,2 м. Поэтому обещать идеальный круг или три полных ряда с длинными подписями без измерения нельзя. Новые плюсы, метка и меню должны оставаться в UX-полосе; нельзя просто масштабировать весь интерфейс до нечитаемого размера.

Перед реализацией измерить реальные bounds плитки и подписи, запас hover/bob и кнопку «Назад». Для блогера допустим квадрат 2×2 вместо ромба, общения — эллипс или 2×3. Для ID сначала проверить компактные три уровня; если они не помещаются, расположить MAX и ID на верхнем уровне, три применения — ниже, сохранив связи дерева. В просторном standalone оставить исходную пирамиду. Это явный компромисс для узкой физической полосы, а не утверждение, что три уровня уже проверены.

«Назад» остаётся левее/выше композиции насколько позволяет полоса1–1,8м; физические ограничения важнее относительного «выше MAX». Зарезервировать левый отступ, иначе верхняя вершина вытолкнет кнопку за экран. Попап задания матовый, локальный; не пересобирать композицию при ответах и не скрывать оболочку до завершения миссии/явного закрытия.

Во время сборки узлы придерживаются шаблона. После «Продолжить» свободный drag сохраняется. Ручное перемещение не меняет зависимости и не переставляет другие узлы; возвращение к миссии не сбрасывает пользовательские координаты. При выходе за дальность волокно плавно гаснет, но новая смысловая связь с ближайшим чужим узлом не создаётся.

## Выбор технического подхода

| Подход | Плюс | Риск здесь |
|---|---|---|
| Форма только по числу иконок | Простой квадрат/кольцо | Пять узлов ID и варианты бизнеса теряют смысл зависимостей |
| Свободная физическая раскладка | Органическое движение | Дрейф мест и непредсказуемая посадка/читабельность |
| Универсальный graph-layout | Подходит для большого изменяемого графа | Дополнительная зависимость и настройка для всего четырёх малых сценариев |
| Сценарные шаблоны + локальное избегание | Стабильность, компактность, управляемое раскрытие | Нужно измерить подписи и подготовить адаптивные варианты |

Рекомендуется последний вариант. Официальный [обзор React Flow](https://reactflow.dev/learn/layouting/layouting) описывает разные компромиссы Dagre, D3 и ELK и необходимость учитывать размеры узлов; он не обосновывает автоматическую установку этих библиотек в MAX. Решение оставить текущий renderer и небольшие шаблоны — вывод этого исследования для четырёх конкретных миссий.

Предлагаемый контракт будущего layout:

```text
input: mission + edition + placedNodes + slotAssignments + phase + measuredBounds
output: positionsByNodeId + visibleSlots + semanticEdges + protectedBounds
slot: id, role, allowedSteps, revealWhen, label, position
```

`revealWhen` для сборки и `requires` для выполнения — разные условия. Для бизнеса добавить смысл группы «один из», для трёх применений ID — «все». Размеры и доступная область вычисляются по конкретной зоне.

Точки будущей реализации: новый модуль шаблонов и расчёта; интеграция в `planningLayout/arrangeRoute/nextRoutePoint`; slot ID в reducer и сохранениях; несколько motion-state следующего шага; выбор смысловых связей вместо MST для клиентской схемы. Старый MST остаётся доступным для первой редакции. Фазы волокон и существующий WebGL clock/renderer сохранить, новые render targets не требуются.

Миграция: добавить версию раскладки/назначение мест; завершённые задачи и answers не менять. Ранее сохранённый путь в playing оставлять с его координатами до явного нового построения; для незавершённой сборки назначить свободные места существующим узлам детерминированно. Не повторять стартовую презентацию на restore. Редакции и две игровые зоны независимы.

## План прототипа и критерии приёмки

Первый пилот — ID: он проверяет верхний старт, именованный центральный шаг, три одновременных места, независимые ветви и настоящую зависимость. Затем блогер, общение, бизнес. До изменения игры — геометрический прототип на размерах standalone и single/two мастера.

Для реализации проверить: состав всех четырёх миссий, три возможных первых выбора ID, любой порядок его ветвей, все бизнес-альтернативы по одной, отсутствие дублей, отмену во время полёта, restore/resize, сохранение ответов, независимость зон, отсутствие пересечений включая подписи, отсутствие ложных связей, reduced motion. Открытие шага сборки никогда не показывает телефон. После сборки задания сохраняют существующие правила прогресса. Базовая браузерная проверка — одна вкладка; тяжёлые проверки только по отдельному разрешению.

Открытые вопросы для визуальной приёмки прототипа: помещаются ли три уровня ID в физическую полосу; насколько читаемы связи общения от верхнего MAX; удобен ли направляемый порядок сборки блогера. Эти вопросы не блокируют исследование и не выданы за уже проверенное решение.
