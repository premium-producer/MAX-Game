# MAX: диагностика удержания LiDAR

06.10.2026. Пользователь сообщает о корректном положении курсора на ладони без срабатывания в обычной ручной миссии. Старый launch journal подтверждает native presented и ошибки связи, но не хранит первый down, mapped inside, принятие native contact и попадание в DOM tile. Он не доказывает успешное игровое нажатие.

Повторно используется установленный electron-log5.4.4/MIT; новая библиотека или система хранения не создаётся. Готовый file transport реализует запись и ротацию, существующий diagnostic HTTP — ограничения событий и loopback/same-origin доступ. [Прежнее исследование](max-launch-diagnostics-20261005.md) содержит version/license, upstream docs/source и реальный опыт Teams for Linux. [Официальная документация transport](https://github.com/megahertz/electron-log/blob/master/docs/transports/file.md). Возможности проверены на реально установленном cached5.4.4, не по предположению о новых версиях.

Добавлены ограниченные координаты/rect/phase/contact identifiers и события границ контакта. Mapped/native move пишется максимум раз в секунду при неизменном состоянии, DOM progress — максимум раз в250мс при изменении. Кадровых таймеров, новых WebGL-контекстов, записи raw OSC, снимков/токенов и отладки на production-стене нет. Native journal имеет отдельного владельца MAX-LIDAR-NATIVE; фиксированный sibling читается прежним readRecent, произвольные пути не принимаются.

В коде подтверждены два механизма: down вне ладони затем move внутрь не начинает controller.down; down вне mapped bounds превращается в cancel, затем native отвергает move без down, хотя cursor overlay рисуется независимо. Вход нового контакта и наведение существующего контакта — разные события. Это подтверждение механизма, а не доказанная история конкретной старой попытки. Координатного двойного Y-offset не найдено: input/overlay используют2/1282 по output plan.

Наблюдение DOM сохраняет actual trusted events, hit bounds, focus/visibility/readiness/progress, не вмешиваясь в событие. Fetch observer сохраняет исходные promise/Response и не читает bodies. Полную семантику подтверждает наблюдатель существующего canonical response в Node gateway: `SCAN_PENDING`/`SCAN_CONFIRMED` берутся из state.scanned только при совпадении sessionId; HTTP200 сам по себе не объявляется успехом. Некоторые замкнутые renderer inputActive guards остаются непрозрачными без отдельного события самого контроллера. Сначала собрать реальный случай, затем исправлять механизм удержания в отдельной короткой итерации через существующий controller/contact/backend clock; не обходить owner/generation guards фиктивным HOLD.
