# MAX BFM — координатная разметка

Пользователь уточнил: комфортная зона начинается на высоте1м от пола. Показать сетку, углы, начало/конец стены и область LiDAR.

Использованы существующие данные: [карта оборудования](equipment-pixelmaps-20260929/README.md), [исследование LiDAR](max-lidar-touch-20261001/README.md), circle-model.mjs (SCREEN_METRES/heightToPixel/FLAT_SCREEN). Общая задняя стена7168×1280, стык3072, правый экран4096×1280. Сетка256×256 соответствует кабинетам; это не текущий размер декоративных LumiCells.

Физический ноль — пол. По модели LED занимает0,488…3,013м; 1м соответствуетY1020,519, 1,8м — Y614,992. Верх1,8м — существующий UX-ориентир, пользователь сейчас подтвердил только низ1м. Плоский участок X2192,025…4096 — проектная область для оптической завесы. Подтверждённого калибровочного polygon нет; UI прямо пишет об отсутствии калибровки. Дальность270°/10м не используется как якобы измеренное покрытие стены.

Рендер разметки — стандартный статический SVG(pattern/viewBox/rect/text), без нового движка, RAF и датчиков. Геометрическое преобразование взято из существующего проекта. CommonMapBackground переиспользуется; viewport iframe ограничен тем же aspect4096:1280, что и игра, чтобы вся правая стена и её углы были видны вместе с сеткой. Оценки по модели не заменяют исполнительный обмер. Игровой интерфейс не перераскладывается и ввод не ограничивается этой разметкой.

[Техническая проверка](../../artifacts/reports/max-bfm-pixel-map-guides-20261003.md).

Уточнение пользователя по скриншоту: зелёная полоса принята как граница LiDAR и игры. BFM_PLAY_AREA объединяет X2192,025…4096 и Y614,992…1020,519; аппаратной калибровкой это не становится. Стандартный CSS transform равномерно вписывает существующий дизайн1543×950 в область; без новых анимационных механизмов. Центр3144,0125/817,7553 = высота1,4м. Цена такого сохранения дизайна — масштаб0,42687 (поле658,66×405,53). Читаемость требуется оценить пользователю; адаптивная перекомпоновка с сохранением крупных целей отдельно не выполнена.

## Приближение для локальной разработки

По запросу03.10: используем готовый браузерный механизм [CSS transform](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/transform) с [transform-origin](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/transform-origin), а не новый camera/drag engine. Источник описанного практического опыта — [исследование BFM/AIMIRROR/X-SPUTNIK](max-bfm-presentation-20261003.md), в частности общий DOM для отображения и hit-target вместо разных координат preview/commit. Стандарт широко доступен; новых npm-зависимостей или лицензируемых библиотек не добавляется. Исходная BFM версия зеркала0.7.14, build-only esbuild0.28.2 MIT.

`bfmViewportPlacement` — только адаптация существующих физических координат к CSS translate/scale: LiDAR область центрируется с24px отступом, остальная стена может выходить за viewport. Браузер отвечает за преобразование DOM и hit testing; pointer capture/rect остаются существующими. Объекты внутри transformed ancestor не становятся независимо fixed: HUD явно переводится в видимые логические координаты. Проверка полной сетки сохраняется в режиме wall. Более крупный iframe увеличивает площадь GPU-отрисовки; сохранение FPS не подтверждено. Применимость к live iframe и читаемость требуют фактического браузерного кадра; auto-review пока отклонил его открытие. [Проверка интеграции](../../artifacts/reports/max-bfm-lidar-viewport-20261003.md).

Уточнение UI03.10: общий stage теперь вписывается по высоте телефона, а не950px сцены. Опора — тот же native CSS transform и browser layout measurement ([MDN offsetHeight](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/offsetHeight), [CSS transform](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/transform)). Документация подтверждает hidden ancestor→нулевая высота: incoming раскрывается в синхронном update перед измерением. Используется дробная computed CSS height border-box, чтобы не округлять высоту устройства. Практический опыт BFM сохранять геометрию и выполнять изменения внутри native callback описан выше; новых библиотек/лицензий нет. Не вводится новый camera solver. [Фактический браузерный результат](../../artifacts/reports/max-bfm-phone-height-20261003.md) подтверждает один телефонный экран; динамическая высота и PC требуют отдельной приёмки.

Коррекция по отзыву03.10: DOM-measured scale только после активации отвергнут. Сохраняем готовый native CSS/BFM механизм, но применяем один authored scale к общему stage до SessionPort.start; переходы не влияют на него.540px — измеренная базовая высота прошлого кадра, не новый физический алгоритм. Фоновые координаты прежние; размеры разных экранов не нормализованы отдельным механизмом. [Проверка реализации](../../artifacts/reports/max-bfm-fixed-ui-20261003.md).
