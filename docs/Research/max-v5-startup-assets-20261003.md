# MAX v5: подготовка ресурсов до ввода

Запрос: подлагивания раскрытия, постановки в ряд и соединения с телефоном; все ресурсы игры подготовить при запуске. По коду установлены пробелы: warmSharedAssets загружает первые2 screens/task и возвращает allSettled без строгой готовности; UI растеризует CanvasTexture/парсит SVG при первом visit; UI prepareGPU прогревает только contextGlass/introBurst; phone upload остаётся в render. Это подтверждённая отложенная работа, но не GPU-профиль конкретного подвисания.

Готовое решение: существующий Three.js0.185.1 (MIT), [ImageLoader/LoadingManager](https://threejs.org/docs/pages/ImageLoader.html), [WebGLRenderer.initTexture/compileAsync](https://threejs.org/docs/pages/WebGLRenderer.html), плюс native [HTMLImageElement.decode](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode). Библиотека выполняет загрузку/учёт/компиляцию/передачу текстур; собственный loader или compiler не разрабатывается. Сохраняются реальные UI paint/markup и cache: прогрев вызывает тот же путь, который будет использовать игра, под стартовым loading, без backend-команд и новой визуализации.

Реальный описанный опыт [Three maintainer: first-render decode/upload](https://discourse.threejs.org/t/how-to-improve-texture-first-render-performance/10436/2), [ограничения одного compileAsync](https://discourse.threejs.org/t/reduce-first-render-lag-renderer-compileasync-is-not-doing-anything/86191): предварительная компиляция не загружает все текстуры/геометрию. Поэтому decode → штатный Canvas/SVG cache → initTexture → compileAsync → предварительный render на уже существующем target. Последний шаг подготавливает geometry buffers, не выводится пользователю. Программы/текстуры остаются закреплёнными до dispose, чтобы renderer не выбросил cache перед настоящим входом. Новые RAF/RenderTarget не добавляются.

Объём актуального каталога:16 tasks,57 уникальных экранных ассетов; исходная RGBA без mipmaps≈148MiB. QR/логотипы отдельно, недостающий контент остаётся явно отсутствующим. Не загружаем все исторические130 ассетов, которые сценарии не используют. Финальный raster расход зависит от native CSS размеров/scale и числа текстовых строк; memory/FPS без GPU-прогона не заявляются. Больше работа/память при старте взамен отложенной работы во время игры. Динамический таймер/feedback/изменённый viewport могут создавать новые строки/размерные cache entries; предзагрузка не гарантирует отсутствие всех причин stutter. HTTP/Node проверяют доставку и порядок, реальный GPU и исчезновение задержек оценивает пользователь.
