## До первой правки

Получить от интегратора конкретную задачу: ID, результат малого шага, владельца, базовую ревизию, список разрешённых файлов, пересекающиеся зависимости и критерии проверки. Одна задача не выдаётся двум пишущим агентам. Исследование/проверка могут выполняться независимо, без второй реализации.

Работать в назначенном worktree/ветке D. Проверить фактический путь, branch, diff и origin; в исходном D сейчас есть несохранённые изменения других задач. Новый worktree от HEAD не включает их автоматически. Если задача зависит от такой правки, интегратор должен подготовить точный исходный набор или завершить prerequisite; начинать со старого HEAD и объявлять его текущей сборкой нельзя. Не переносить весь dirty checkout и не делать stash/reset/clean ради подготовки среды. Git commit/push/PR/merge остаются отдельными действиями по разрешению.

Worktree и branch не изолируют порты, БД, браузерные хранилища, TD, Spout и GPU. Не писать в чужой checkout и не запускать несколько экземпляров на общих данных. Штатные старты старого мастера проходят по startup skill; не обходить их самостоятельным запуском Electron. Статус нового F-мастера и ошибки его launcher не исправлять в рамках компонентной задачи.

Root другого чата не получает права менять F. Компонентный агент может читать контракты F и готовить локальный адаптер/fixture в D; запись в F, изменение его TODO, запуск/остановка8782 и применение разрешены только назначенному ведущему агенту мастер-проекта. Эти документы не являются приглашением начинать сразу все перечисленные задачи.

## Разделение ответственности

Мастер принимает бизнес-решения и сохраняет сессии, наборы тегов/тем, политику состава контента, пакеты, очередь, версии и подтверждённые этапы. Компонент принимает состояние и показывает его. Визуальные часы/позы/флюидные кадры считаются локально; локальный эффект не должен самостоятельно освобождать Стеллу, повторно выбирать контент или завершать миссию.

Игра MAX сохраняет собственную игровую механику за своим SessionPort; мастер управляет назначением/очередью. Это не требование переписать весь игровой backend в DBOS. Стелла в целевой master-интеграции передаёт команды пользователя и отображает принятый snapshot; текущий standalone preview может иметь старую логику, но её нельзя незаметно активировать при ошибке master API.

Существующий endpoint/event/schema использовать только после чтения текущего контракта и кода. Если для эффекта нужен новый payload/ACK — оформить предложение с примером, смыслом и совместимостью; не изобретать endpoint, который мастер якобы уже обслуживает. Согласие на архитектуру не равно применённому коду.

Для визуальных таймингов отделять наблюдаемое состояние, покадровую анимацию и смысловой маркер. Повторный snapshot/reconnect не должен повторять побочный эффект. Не менять установленные имена/семантику markers ради удобства: например новый признак появления всего пакета не подменяет текущий emission_complete без проверки интегратора.

## Источник истины и перенос

Каждая передача указывает основной исходник компонента. Разрабатываемый в D общий компонент получает исправления там; F принимает версию и содержит master-адаптер. Если ошибка исправлена на стороне F, интегратор возвращает общую часть в D до следующего переноса. Существующий canonical MAX/F и неприменённый early-plan candidate учитывать отдельно: сравнить provenance, не копировать историческую папку поверх новой.

Никакой автоматической двусторонней синхронизации. Не переносить целиком node_modules/venv/apps, пользовательские JSON, SQLite/WAL, фото посетителей, секреты или чужие изменения. Не объявлять весь компонент готовым по одной странице preview. Local/production и TD/native — конфигурации, а не две расходящиеся реализации.

## Общие файлы и проверки

Общие `engine.js`, `worker.js`, `server.mjs`, module registry, root dependency lockfiles, shared styles и contracts выдаются одному владельцу на итерацию. Не считать отсутствие текстового конфликта доказательством совместимости. Сборки, меняющие общие runtime-папки, выполняются последовательно владельцем, даже если source worktrees раздельные.

В общей итерации документы ARCHITECTURE/DESIGN/BACKLOG/WORKLOG сводит назначенный координатор по отчётам исполнителей. Это выполняет требование ведения документов без конкурентной записи нескольких агентов. В самостоятельной непересекающейся задаче агент обновляет назначенные документы сам. Статусы master-задач находятся только в F/TODO; в D — ссылки и компонентные работы, без второй копии master-бэклога.

Для изменения механики обязательны готовое решение/официальный источник/опыт применения согласно AGENTS; результаты исследования — docs/Research. После файловых изменений перед сборкой — `python artifacts/web/tools/check_project_duplicates.py`. Проверки выбираются по затронутому компоненту, а не запускаются все подряд.

Техническая проверка включает соответствующие syntax/types/tests и короткую проверку действия/перехода/reload/console в назначенной вкладке. Визуальная — фактический источник → build → обслуживаемая страница/выход и сопоставимый кадр. Пользовательская художественная приёмка — отдельный статус. Для документационной правки достаточно проверки ссылок/согласованности; запуск GPU не требуется. Тяжёлые прогоны и запись видео — только в рамках отдельного разрешения.

## Формат передачи интегратору

Отчёт — `artifacts/reports/<task-id>-handoff.md`; не новый бэклог. Приложить конкретные доказательства без персональных данных. Шаблон:

```text
Task ID / владелец / дата:
Результат малого шага:
Source repository / worktree / branch:
Base commit и исходные dirty зависимости (если есть):
Head commit или SHA256 каждого передаваемого source-файла:
Изменённые файлы / новые ассеты / исключённые runtime-данные:
Основной исходник и учтённые F-адаптации:
Потребляемый контракт F: путь + версия + SHA прочитанной редакции:
Предлагаемые изменения контракта (если нужны; ещё не implemented):
Библиотеки/версии/лицензии; команды установки/сборки:
Настройки/defaults; что сохраняется из настроек оператора:
Совместимость сохранённых состояний и отмена/reload/reconnect:
Проверки: команды, результат, адрес/версия экземпляра, console:
Кадры фактического результата и пределы визуальной проверки:
Технически проверено / визуально сверено / принято пользователем:
Известные ограничения и требуемый шаг интегратора:
F/runtime/production этим агентом не изменялись:
```

Передавать небольшую законченную правку. Интегратор сверяет актуальный F baseline и контракт, просматривает diff, собирает компонент и проверяет общий сценарий на изолированных данных. Только затем отдельно применяет принятую версию. При недоступном endpoint, неподтверждённом renderer ACK или непроверенной миграции указать ограничение, а не объявлять интеграцию готовой.
