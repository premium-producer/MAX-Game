## 1. Основное решение

Единица редактирования — экран задания со списком независимых переходов. Каждый переход имеет стабильный ID, тип, активность и назначение. Зоны на изображении, кнопки под устройством и автопереход могут работать одновременно и вести в разные экраны **того же задания**.

| Переход на одном экране | Условие | Назначение, например |
| --- | --- | --- |
| Зона 1 | Нажатие внутри прямоугольника | Экран 2 |
| Зона 2 | Нажатие внутри другого прямоугольника | Экран 3 |
| Кнопка «Назад» | Нажатие под устройством | Экран 1 |
| Кнопка «Другой вариант» | Нажатие под устройством | Экран 8 |
| Автопереход | Экран показан 0,5 секунды | Экран 4 |

Количество зон и кнопок не связано с количеством исходных действий каталога. В первом выпуске на экран предусмотрен один автопереход с собственным назначением. По умолчанию он выключен; при включении задержка — **0,5 с**. Это время ожидания, а не скорость анимации устройства. В форме — секунды, в данных — целое число миллисекунд; положительное значение обязательно, нулевые цепочки переходов запрещены.

## 2. Интерфейс редактора

Сохраняется существующая страница миссий/заданий и крупное окно изображения. Новый сложный редактор графов для первой версии не нужен.

Справа в крупном окне:

1. **Экран:** «Экран активен», «Финальный экран задания», номер и название. Номера служат подписями; связи используют ID, поэтому перестановка не ломает назначения.
2. **Справка:** режим «Наследовать / Свой текст / Скрыть», поле текста и предпросмотр итоговой справки. Общую справку можно редактировать на уровне миссии и задания.
3. **Зоны на изображении:** строки «☑ Зона 1 → Экран 2», действия «Показать», «Изменить область», «Дублировать», «Удалить» и кнопка «+ Добавить зону». Несколько зон могут вести на один экран. На изображении — пронумерованные рамки; выбранная выделяется, отключённые доступны в редакторе приглушёнными.
4. **Кнопки под устройством:** строки с галочкой, редактируемым текстом, назначением, порядком и удалением; «+ Добавить кнопку». Предпросмотр показывает их под изображением, отдельно от зон. Кнопки сохраняют принятую центровку и ограничение ширины смартфона; множество кнопок переносится в дополнительные строки.
5. **Автопереход:** «☑ Автоматически перейти», «Через 0,5 с», «Куда → Экран …». Его включение не скрывает зоны и кнопки. В предпросмотре виден обратный отсчёт; в самой игре новый индикатор не навязывается.

Выбор назначения содержит миниатюру, номер и название каждого экрана текущего задания, а также явное «Завершить задание». Отдельная команда «Открыть назначение» позволяет проверить связь. Поддерживаются переходы вперёд, назад и повторный вход на тот же экран.

Галочка активности сохраняет настройки и исключает переход из игры. Удаление убирает переход из документа и имеет «Отменить»; это **не возврат к исходному действию**, как сейчас. Для исходных действий сохраняется tombstone, чтобы они не возникли снова при компиляции. «Восстановить исходное действие» — отдельная явная операция. Удалять файлы изображений этот интерфейс не будет.

Редактор по умолчанию не исполняет переходы: нажатие на изображение редактирует область. «Проверить задание» запускает отдельную тестовую сессию с черновиком; выход и сброс теста не меняют разметку или игру посетителя.

## 3. Модель данных v3

Новый документ — полный редактируемый сценарий, полученный из базового каталога и миграции разметки. Это не массив единственных overrides по паре screen/action.

| Сущность | Основные поля |
| --- | --- |
| Документ | schemaVersion:3, sourceContentRevision, missions, tasks; серверная revision отдельно от содержимого |
| Миссия | missionId, helpText |
| Задание | taskId, startScreenId, helpText, screens |
| Экран | screenId, assetId, assetSha256, enabled, final, help, interactions, deletedSourceActionIds |
| Общие поля перехода | interactionId, enabled, kind, target, sourceActionId?, semanticRef? |
| Зона | kind:hotspot, name, rect:[x,y,w,h] в исходных пикселях |
| Кнопка | kind:button, label, order |
| Автопереход | kind:timer, delayMs:500 |
| Назначение | {kind:screen, screenId} либо {kind:complete-task} |

Справка разрешается по цепочке **свой текст экрана → текст задания → текст миссии**. Режим hide явно скрывает справку; inherit отличается от пустой строки. Исходный screen.instruction мигрирует в собственный текст экрана, поэтому существующие пояснения не меняются. Тексты — plain text, не HTML и не исполняемые выражения.

Переходы — данные, без пользовательских скриптов. ID новых переходов создаются один раз через crypto.randomUUID и сохраняются при изменении зоны/подписи/назначения. В Annotorious annotation.id равен interactionId. Добавление, изменение и удаление используют его существующие API; замена всего списка выполняется только при открытии экрана, чтобы не сбрасывать выделение во время перетаскивания.

Смысловые действия существующего backend сохраняются отдельно: неправильный ответ, выбор private/public, выбор инструмента бизнеса, пропуск, завершение. Мигрированный semanticRef — ссылка на разрешённый исходный эффект, не произвольный код из редактора. Новая зона/кнопка по умолчанию выполняет обычную навигацию; при дублировании смыслового действия редактор явно показывает наследуемый эффект. Перенаправление не должно молча превращать неправильный ответ в правильный или терять выбор ветки. Для protected-действий изменение назначения проходит доменную проверку; неподдерживаемая комбинация объясняется до применения.

### Финал и отключённые экраны

Флажок «Финальный экран задания» предлагает «Завершить задание» как назначение новых переходов этого экрана. Само появление картинки не завершает задание. Явные назначения других переходов сохраняются: с финального экрана можно иметь кнопку «Назад» и отдельную кнопку завершения. Назначение финала не переписывает все связи незаметно. Миграция прежнего final сохраняет его ранее скомпилированные complete-task outcomes. В первом выпуске сохраняется ограничение одного отмеченного финального экрана на задание.

Отключение экрана показывает входящие связи. Черновик сохраняется с предупреждением, но применить его нельзя, пока активные связи или startScreenId указывают в выключенный экран. Для произвольного графа не угадываем, какой экран должен стать следующим. Это заменяет прежний ограниченный автоматический обход единственной ветки.

## 4. Исполнение и готовые механизмы

| Слой | Ответственность |
| --- | --- |
| Annotorious 3.9.3 | Создание и редактирование нескольких прямоугольников |
| JSON Schema / Ajv 8 | Проверка формы v3 без молчаливого удаления/приведения полей |
| Graphlib 2.2.4 | Готовые алгоритмы достижимости и компонент циклов для проверки маршрутов |
| Компилятор контента | Детерминированное преобразование данных в каталог и конфигурацию переходов; диагностика связей и эффектов |
| XState 5, pure transition | Выбор перехода и проверка guards внутри задания; реально исполняет граф, не декоративная зависимость |
| MAX SessionApplication | Владелец команды, доверенное время, сериализация, CAS, receipts, транзакция и смысловые эффекты миссии |
| Renderer | Показ единого подтверждённого view, зоны нажатия, кнопки, декодирование и подтверждение показа |

Выбранный кандидат XState — проверенный API ветки5, исходник5.20.2; точный пакет фиксируется после небольшой проверки совместимости. Механизм **pure transition** вызывается внутри существующей транзакционной обработки MAX. Отдельного живого actor со своей авторитетной копией прогресса рядом с backend нет. Состояние задания хранится в едином mission model; adapter восстанавливает library snapshot из подтверждённых данных, вычисляет переход и фиксирует его вместе с receipt. В preview используется тот же скомпилированный механизм.

До commit разрешены только детерминированные вычисления proposed snapshot и описаний effects. Запуск actions XState, отправка событий наружу и показ нового экрана до записи запрещены. Наружные уведомления отправляются после commit; повтор команды возвращает прежний receipt без повторного эффекта. Для v3 nested channel adapter сохраняет доменные проверки/ответы, но не выбирает маршрут независимо: единственное решение target принадлежит XState. Старый nested navigation остаётся только у legacy rules adapter. FE-01 обязан подтвердить паритет смысловых проверок и отсутствие двойного выбора/emit при rollback и retry.

Доверенное приложение доставляет событие истечения времени через существующий host-clock/poll. Не создаём новый frontend setTimeout→nextScreen. Не полагаемся на сохранение внутренних XState after-таймеров: у upstream описан дефект восстановления delays. XState отвечает за решение перехода, существующий host — за время и хранение. Проверка минимальной интеграции до UI обязательна: если pure transition/replay не проходят контрактные проверки, это архитектурный блокер, а не повод незаметно писать свой аналог.

Доменная проверка графа остаётся предметной логикой приложения: библиотека JSON Schema не доказывает достижимость финала, а XState не знает правил MAX. Обходы/компоненты графа выполняет Graphlib, приложение задаёт политику допустимости. Это явно ограниченный адаптер/валидатор данных, не новый движок исполнения.

### Одна победившая команда

ACT и AUTO_SCREEN несут стабильный interactionId/actionId и относятся к **screenEntryId** — конкретному посещению экрана. Одного screenId недостаточно для A→B→A. Сохраняются commandId, sessionId, contentRevision, expectedRevision, runId и владелец ввода. Формат команды и rulesRevision нужно версионировать; это ещё не существующий API.

Порядок: проверить владельца и контекст → проверить активность/тип взаимодействия → вычислить переход XState → выполнить разрешённые смысловые эффекты → атомарно записать состояние и receipt → показать новое состояние. При конкуренции кнопки, зоны и таймера побеждает первый **успешно зафиксированный** переход. Другие команды старого входа отвергаются, не переназначаются следующему экрану. Ошибка записи не переводит UI вперёд. Двойное нажатие и поздний callback не засчитывают два экрана.

Перекрывающиеся активные зоны с разными исходами блокируют применение; с одинаковыми исходом и эффектом допускаются, но одно нажатие порождает одну команду. Скрытые/неактивные зоны не участвуют в hit testing. Внешние кнопки остаются вне силуэта устройства.

### Откуда считать 0,5 секунды

Таймер запускается после подтверждённого показа картинки и завершения основного появления устройства. Парение и декоративные анимации не задерживают запуск. Новый proposed SCREEN_PRESENTED контракт связан с contentRevision/runId/screenEntryId и текущим owner/lease. Renderer передаёт факт готовности, не собственное время; timestamp назначает host. Повторный ACK того же входа таймер не перезапускает. Ошибка ассета оставляет загрузочную ошибку и не завершает экран автоматически.

Дополнительно host выдаёт presentationAttemptId для каждого подключения/поколения renderer. Disconnect, reload/reconnect, takeover и потеря lease аннулируют прежний ready и останавливают таймер. Только ACK текущего presentationAttemptId возобновляет сохранённый остаток; ACK старого окна игнорируется даже при том же screenEntryId. Между физическим обрывом и его обнаружением действует измеряемый lease/heartbeat timeout: мгновенную остановку недоступного host соединения не обещаем. Этот предел входит в recovery-проверку, а не скрывается UI.

У каждого входа: ready, remainingMs/deadline в доверенных часах, paused. При потере владельца/паузе время останавливается. После reload текущая картинка снова готовится, затем продолжается сохранённый остаток; повторное подтверждение не обнуляет его. После простоя нет цепочки «догоняющих» переходов. Self-transition создаёт новый screenEntryId и новый отсчёт. Текущая точность checkpoint до5с неприемлема для обещания восстановления500мс: требуются запись таймерного остатка при pause/commit и явно измеренный recovery-контракт. При аварийном обрыве безопасная политика — повторный показ неполностью подтверждённого экрана, без скрытого прохождения; приёмка отдельно проверяет это поведение.

## 5. Сохранение, проверка и применение

Автосохранение черновика остаётся серверным, с expectedRevision, последовательной записью и atomically; IDB — аварийная копия. Изменения рамки сохраняются после законченного жеста, текст — с debounce и обязательным flush при уходе с поля/экрана. В UI различаются «Сохраняется», «Сохранено», «Не сохранено», «Конфликт другой вкладки». Потерянный ответ сверяется по чтению server revision/document hash до повторной записи. Чужие изменения не затираются.

Разделяются две проверки. **Сохранение черновика** допускает незаполненное назначение и временно оборванный маршрут, сохраняя структурно корректные данные. **Применение к игре** требует полного графа. Поэтому добавление пустой кнопки не блокирует сохранение остальных изменений.

Перед применением проверяются: ID/asset SHA/границы зон; положительные задержки; назначения только внутри задания; start активен; доступные действия на каждом достижимом экране; путь к завершению; сохранность смысловых эффектов; отсутствие ссылок в удалённые/выключенные экраны. Непосещаемые экраны и циклы показываются в отчёте. Замкнутый компонент без пути к завершению блокирует применение; автоматический цикл с ручным выходом требует явного подтверждения предупреждения и проверки в preview. Не запрещаем все обратные переходы, нужные пользователю.

«Применить к игре» создаёт immutable contentRevision + rulesRevision и перечень изменений из подтверждённой server draft revision. Пока проверяется кандидат, новые правки сохраняются в черновик; они не попадают в уже подготовленную версию. Новая версия назначается следующим запускам. Идущая миссия остаётся на прежних правилах и контенте до завершения. Публикация редактора сама по себе не публикует игровой каталог. Существующие сохранения и receipts не удаляются.

Для этого нужен явный registry пакетов content+rules: нынешний Application замкнут на одном каталоге и сам многоверсионность не обеспечивает. Сессия закрепляется за одним пакетом на весь срок; её restart/replay/receipt lookup всегда используют этот пакет. Новый запуск на новой версии создаёт новую sessionId, старую не переписывает; assignment и восстановление разрешаются через сохранённую привязку session→package, а не через current pointer. Переключать rules внутри журнала старой сессии нельзя. Координатор запусков/адаптер F должен явно поддержать этот контракт до применения публикаций к мастеру.

## 6. Миграция и интеграция

v1/v2→v3 проходит на копии с резервом и отчётом: сначала полный базовый каталог, затем принятые overrides/flags. Сохраняются точные rect, placement, исходные action IDs, тексты, SHA и значения final/enabled. Отсутствие override означает исходное действие, а не отсутствие кнопки. automaticMs исходного effective-каталога превращается в отдельный timer с прежним исходом; ручные действия, скрытые старым auto-режимом, не включаются молча. Новый default500 не заменяет сохранённые задержки1100/1600/0; нулевые legacy-auto требуют явного решения перед применением v3, оригинал остаётся исполняемым старым runtime.

Смена схемы согласована с сервером: старый клиент не может записать v2 поверх v3. Импорт старого экспорта предлагает миграцию и сравнение; отсутствие записей в частичном импорте не означает удаление. Существующая отдельная channel coreCatalog получает те же action IDs и outcomes либо заменяется только после отдельной доказанной совместимости; оставлять два разных графа нельзя. Старые редакции Site/WebGL продолжают использовать старый rules adapter.

Работа выполняется в D. Pinned vendor вручную не редактируется: изменение готовится в исходном backend и выпускается новой проверенной версией. В F передаётся ограниченная delta с manifest/SHA/контрактами ведущему интегратору; его SQLite assignment/receipt/slot изменения сохраняются. Assignment accepted не является SCREEN_PRESENTED. Сервер Selectel, local v5 и canonical F не объявляются автоматически совместимыми после одной локальной сборки.
