# Панель управления MAX: режимы и независимая сцена

06.10.2026. **Изолированный кандидат, не установлен на стенд.** Реализованы «Стандартная игра», «Только фон» и независимая сцена с существующими ассетами игры. Загрузка новых файлов, прямой операторский ID→видео и полный набор четырёх режимов остаются следующими этапами [согласованного плана](../../../docs/Research/max-control-panel-plan-20261006.md). Существующий сценарий Стелла→ID→видео сохранён отдельно.

## Владение состоянием

MASTER хранит `max-presentation-control-v1` в существующей registry SQLite через DBOS. Панель — новый раздел существующего fleet operator UI. MAX_RIGHT применяет режим через существующую игровую оболочку, сохраняя общий фон и подготовленный renderer. Нового игрового backend или WebGL-контекста нет.

- `desiredMode`: `standard` / `background` / `assets`.
- `effectiveMode`: последний подтверждённый режим либо `null`, пока применение не подтверждено.
- `revision`: версия выбора оператора; CAS при изменении.
- `modeEpoch`: поколение применения, меняется при выборе/переподключении renderer/перезапуске MASTER.
- `phase`: `pending` / `active`; `lastAckAt` — время последнего принятого ACK, не показатель текущей сетевой связности.

Переключение свободной стены закрывает новые MAX admissions до подтверждения renderer. При активном запуске, очереди, занятой Стелле или незавершённом общем сценарии переключение отклоняется. Очередь и сессии не удаляются. Уже принятый запуск при выбранном standard может продолжить восстановление. VK admissions не блокируются новым MAX gate.

Первичная миграция подразумевает подтверждённый исходный стандартный режим. Это соответствует снятому baseline MAX_RIGHT. Для стенда с явно выбранным прежним `backgroundOnly=true` миграцию нельзя применять без сохранения этого выбора. Существующие таблицы/разметки/медиа/секреты остаются на месте. Старый show workflow сохранён внутри standard; включение и bind show запрещены на фоне или пока применение standard не подтверждено. Переключение из включённого show требует штатного выключения существующим управлением.

## API и границы доступа

Оператор:

```text
GET  /fleet/v1/max-presentation
POST /fleet/v1/max-presentation
     {commandId, expectedRevision, mode}
GET  /fleet/v1/max-presentation/catalog
POST /fleet/v1/max-presentation/settings
     {commandId, expectedRevision, assetsSettings}
```

Существующие loopback Host/Origin/CSRF проверки остаются обязательными. Открытие страницы и polling выполняют только GET. Если ответ команды потерян, оператор может повторить её с тем же commandId. Перезагрузка панели сама не выбирает режим.

Доверенная роль MAX_RIGHT:

```text
GET  /production/max/presentation
POST /production/max/presentation/attach
     {rendererBootId, expectedEpoch}
POST /production/max/presentation/ack
     {rendererBootId, revision, modeEpoch, mode}
```

Эти маршруты проходят существующую mTLS/role/lease проверку. Шлюз связывает rendererBootId с dataset, node, host boot, lease и generation; клиент не может подтвердить режим от старого владельца. До и после внутреннего запроса проверяется текущий binding. Внутренние attach/ack MASTER требуют существующий `X-Local-Control`; секрет читается сервером из существующего хранилища и не передаётся панели или renderer.

MAX local adapter обслуживает `/bridge/context`, `/bridge/presentation/attach` и `/bridge/presentation/ack` с собственными Host/Origin/player credential проверками. Ответы POST нормализуются из `{accepted, reason, state}`. Ошибка MASTER не превращается в локальный самостоятельный выбор режима.

## Применение в renderer

### Независимые ассеты

Панель содержит выбор изображения устройства из существующих 70 экранов и список из 18 типов иконок. Можно добавить до восьми экземпляров иконок, назначить сторону, порядок от устройства наружу и активность каждого экземпляра. Кнопки «Показать/скрыть устройство» и «Показать/скрыть иконки» независимы. Скрытие устройства сохраняет его виртуальные размеры: иконки остаются выровненными относительно того же центра.

Изменение ассета, списка или порядка создаёт локальный черновик. «Применить сцену» сохраняет его с глобальным CAS `revision`; открытие панели ничего не отправляет на стену. Переключатели видимости работают с сохранённой сценой. При неприменённом черновике сначала нужно применить его или вернуть сохранённые значения. Конфликт другого оператора сохраняет черновик и требует явного повторного применения. Потерянный ответ повторяется с исходным `commandId`.

`assetsSettings` содержит `deviceAssetId`, `deviceVisible`, `iconsVisible`, `icons:[{instanceId,assetId,side,enabled}]`. Порядок массива сохраняется отдельно для каждой стороны; `instanceId` сохраняет движение экземпляра между командами. `settingsRevision` увеличивается только при изменении настроек. При активном assets также увеличивается `modeEpoch`, очищается подтверждение и ожидается новая сцена. Настройка неактивного режима не меняет текущий показ. Пустая сцена с обеими видимостями false допустима.

Устройство находится в центре правой поверхности MAX (2048,640 в локальных 4096×1280). Используются существующие WebGL foreground, оболочка устройства, текстуры иконок, maath и единый игровой tick. Линки в независимой сцене отсутствуют. Иконки плавно перестраиваются при изменении пропорций устройства. Если ряд не помещается, вся композиция пропорционально уменьшается, сохраняя обычные отношения размеров и промежутков. Скрытие и повторное появление используют текущую величину и скорость анимации.

Независимая сцена не создаёт игровую сессию, задания, прогресс или QR. Доступны только ID локального каталога, произвольные URL/файлы команда не принимает. MAX_RIGHT применяет авторитетные настройки; host ожидает подтверждение child с совпадающими revision/modeEpoch/settingsRevision и готовностью сцены, после чего отправляет MASTER ACK.

Миграция расширяет CHECK режимов только таблицы max_presentation внутри существующей SQLite транзакции. Все прежние поля и receipts сохраняются; добавляются настройки сцены и settingsRevision. Перезапуск MASTER, как прежде, требует свежего ACK renderer.

`background` скрывает foreground и отключает его видимость/ввод, сохраняя подготовленную оболочку и глобальное поле стены. Возврат в standard использует существующие ресурсы. Действующие автоматические назначения сохраняют прежнюю синхронизацию с этапами tags/ribbon/wall.

ACK ожидает применение политики, fade и следующий кадр. Таймаут/отмена прерывает ожидание кадра и разрешает следующий polling; поздний результат не подтверждает старое поколение. Готовность `about:blank` не подтверждает загруженный auto iframe. Завершённый auto возвращается к подготовке обычной оболочки.

ACK подтверждает применение политики игровым представлением. Он не является подтверждением Spout/TD/физического LED или художественной приёмкой.

## Передача и применение

Кандидат и сборщики точечной поставки находятся в `artifacts/workspace/tasks/max-control-panel-20261006/`. Первый этап сохранён в `delta/` и `max-control-panel-slice1.zip`. Для текущей сцены используются `build-assets-delta.py`, `verify-assets-delta.py`, отдельный `delta-assets/` и `max-control-panel-slice2.zip`. Это совокупный кандидат двух этапов; сборщики ничего не загружают и не устанавливают. Они обновляют SHA-каталог изменённых UI-модулей и пересобранного игрового bundle. Ассеты повторно не включаются.

Интегратор сверяет каждый `expectedPreviousSHA256` с текущим файлом, сохраняет резерв и применяет обе части согласованно. MASTER backend, его control gateway и MAX adapter/host должны соответствовать одному протоколу. Секреты, данные, игровые ассеты, звук, TD и фон не входят в поставку. Новые изменения другого исполнителя требуют повторной сверки; нельзя просто перезаписать изменившийся baseline.

Порядок физической проверки после согласованной установки: свободная стена → только фон → подтверждение → стандартная игра → новый штатный запуск; отдельно проверить отказ переключения во время игры. Браузерная проверка агентами сейчас запрещена пользователем.

Технические доказательства и ограничения: [первый этап](../../../artifacts/reports/max-control-panel-slice1-20261006.md), [независимая сцена](../../../artifacts/reports/max-control-panel-slice2-20261006.md).

## Цикл двух экранов — установлен 06.10.2026

В режиме «Независимые ассеты» включите «Цикл двух экранов», выберите первый и второй экран, задайте ожидание статичного ассета и нажмите «Применить сцену». Два экрана должны различаться. Ожидание допустимо от0.5 до3600секунд, по умолчанию5секунд. Цикл повторяется до выключения; статичный экран ждёт после готовности устройства, видео играет целиком до ended, затем начинается следующий экран. Видео звучит через MASTER/Dante5–6, local browser muted сохраняется. Вне цикла одиночный ролик по-прежнему зациклен сам.

На стенде цикл уже включён: «Главная с фото · Нет льгот»5с → «Первый TV · 30 секунд» со звуком → повтор. Два существующих логотипа и текущий размер600px сохранены. Эти значения заменяют первоначальную сцену предыдущего раздела. Обновите страницу пульта для появления новых полей.

Параметры `assetsSettings`: optional `cycleEnabled=false`, `cycleAssetIds` из двух разных ID каталога, `staticWaitSeconds=5`. Существующий CAS/commandId и применение сцены сохраняются; открытие панели не меняет режим. При скрытии устройства видео приостанавливается, таймер статичного экрана отменяется; при показе видео продолжается, статичный экран начинает полный интервал. Изменения иконок не сбрасывают цикл.
