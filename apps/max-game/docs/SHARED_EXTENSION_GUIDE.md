# MAX — развитие общего backend

02.10.2026. Этот контракт относится к новым модулям `artifacts/max-game/src/{contracts,core,content,application,migration,development}`. Старые страницы пока сохраняют собственную механику. Подключение Site/WebGL к общей сессии требует отдельного переноса: наличие комплекта не активирует renderer.

## Добавление задания

1. Добавить смысловые `taskId`, `screenId`, `actionId` в `content/mission-catalog.mjs`. Числовой индекс экрана не является идентификатором прогресса.
2. Описать инструкции, изображения, размещение действия и исход. Справа инструкция остаётся информацией; действия выполняются в устройстве. Горизонтальные экраны имеют `deviceKind: 'pc'`. Отсутствующий контент обозначается `missing`; пропуск не засчитывает выполнение.
3. При смене правил обновить `MISSION_RULES_REVISION`; при изменении сценария или контента — `contentRevision`. Сохранённая сессия проверяет обе версии. Не переинтерпретировать старые команды под новым каталогом.
4. Добавить CPU-сценарии в тесты миссии: правильный и неверный ответ, повтор команды, восстановление, недоступный будущий этап. Не менять анимационные фазы ядра.

## Замена ассета или инструкции

Ассеты лежат в исходном `public/assets/`; в `mission-assets.mjs` указывается `assetId`, относительный путь, размеры, MIME и SHA-256. Каталог ссылается на assetId. Сборщик сверяет исходные байты с SHA: изменение файла требует обновления описания и версии контента. Manifest включает `catalogHash` всего задания, поэтому изменение инструкции также меняет `contentHash`, даже если изображение прежнее.

Будущий renderer читает один descriptor и общий manifest. Он подготавливает изображение/GPU и анимирует переход; подтверждённый screenId и зачёт меняет только SessionPort. Вне ядра допускаются разные устройства и материалы без копирования правил.

## Подключение визуализации

Новый адаптер размещается в `src/adapters/`, использует только SessionPort и descriptors. Он отправляет команды с ID, исходным screenId и expectedRevision; не импортирует reducer или PersistencePort и не пишет completion/answers/localStorage. При переключении сначала освобождается прежний владелец ввода. Пока общих адаптеров нет: исторические renderer не проверяются как новые и продолжают работать отдельно.

`node artifacts/max-game/scripts/check-shared-boundaries.mjs` проверяет зависимости чистых слоёв и владение прогрессом в новых адаптерах. Это статическая проверка заданных границ, не полный анализ JavaScript. CPU-тесты подтверждают фактическое поведение.

## Fixtures

`createChannelFixture({branch, at})` создаёт подтверждённый public/private сценарий через настоящие команды ядра. `createMissionFixture({missionId, scanned})` даёт одну из шести миссий до/после сканирования. Session IDs начинаются с fixture; пользовательские профили не читаются, fixture не пишется в production-хранилище. Это данные для разработки существующего визуала, отдельного UI-стенда нет.

## Явный импорт

`createSharedSessionExport({record,catalogs,missionCodec})` проверяет подтверждённые receipts. `createExplicitImportArtifact` принимает только явно выбранные sourceProfileId/source и новый targetSessionId. Подтверждённый shared-export с совместимыми версиями восстанавливается через reducer с заменой sessionId; старые stages и недоказанные результаты остаются в полном `archive`. Новый сценарий начинает безопасный незавершённый этап без выдуманных ответов, выполнения или сканирования.

Для миссий используется `createMissionImportCodec(MISSION_CATALOG)`. Существующие числовые профили Site/Legacy не имеют здесь утверждённой таблицы соответствия: они сохраняются в архиве, не превращаются в фиктивные команды.

`applyExplicitImport({artifact,catalogs,missionCodec,persistence,archivePort})` повторно проверяет артефакт и сначала вызывает долговременный `archivePort.saveOnce(targetSessionId,artifact)`. SQLite PersistencePort предоставляет этот ArchivePort через `saveOnce`; этот порт обязан вернуть `created`/`existing-identical` и отвергать ID с другим содержимым. Только затем вызывается `PersistencePort.createImported(sessionId, record, {importId})`, который в одной транзакции создаёт сессию и долговременный claim её принадлежности импорту. `getImportTarget(importId)` подтверждает claim перед признанием повтора. Существующий чужой профиль не перезаписывается и не становится результатом импорта даже после повторной попытки с уже сохранённым архивом. Совпадение игровых данных само по себе не доказывает принадлежность импорту. Повтор доказуемой операции возвращает duplicate.

Эти функции не читают старые browser keys и не подключены к публичному HTTP-маршруту импорта. Хост явно выбирает источник и долговременный ArchivePort. Ручные координаты пока архивируются: известного соответствия старых layout-версий нет; временные сдвиги никогда не импортируются. Добавлять перенос координат можно только с утверждённым соответствием nodeId/единиц/layoutVersion.

## Комплект

Штатная сборка `node artifacts/max-game/scripts/build.mjs` включает `shared/src/**` и `shared/manifest.json`, сохраняя прежние страницы. Общие изображения находятся в штатном runtime `assets/`, manifest имеет `assetBase: '../'`.

Для отдельного переносимого комплекта backend: `node artifacts/max-game/scripts/build-shared-backend.mjs`. Выход — `artifacts/workspace/dist/max-shared-backend`; manifest содержит версии, хеши модулей/контента, шесть миссий, задания и ресурсы. `assetBase: './'` включает оригинальные ресурсы. Комплект не содержит DB, пользовательские профили и секреты и не включает новый renderer. Изменённые пользователем файлы результата защищены проверкой предыдущего manifest.
