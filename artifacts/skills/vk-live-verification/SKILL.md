# Проверка результата на работающем стенде

Перед запуском, остановкой или проверкой мастера читать [vk-master-startup](../vk-master-startup/SKILL.md); использовать единые батники apps/STARTUP.


Цель — подтвердить результат по тому пути, которым его получает пользователь. Отдельный fixture доказывает работу компонента, но не применение обновления к работающему источнику.

## Сначала определить, что именно меняется

- Начать с последних записей WORKLOG и текущего запроса. Ограничение применять только к указанному пользователем объекту: запрет самодельного градиента не разрешает перекрашивать оригинальную рамку. Если требуется оригинальный ассет, выбрать его по assetId/SHA; процедурную замену не выдавать за подключённый оригинал.
- До изменения сформулировать наблюдаемый результат: например, «в потоке левой стены три обводки красная/синяя/красная», а не «шейдер компилируется». Для брендинга применять профильный брендовый skill.
- Установить фактический URL/режим и цепочку доставки. Stand Service в `dev` отдаёт `artifacts/`, в `run` — `apps/`. 3D-просмотрщик получает WebRTC-поток от отдельного долгоживущего источника. HTML, исходник на диске, загруженный JS и текущий видеопоток могут относиться к разным версиям.

## Довести изменение до нужного потребителя

1. Править исходники, обновить затронутые runtime-комплекты штатными сборщиками. Сохранить пользовательские JSON и чужие изменения. Проверить не только наличие нового файла, но и его импорты/ресурсы в потребителях общего модуля.
2. Выполнить подходящие проверки кода по AGENTS. Fixture использовать для быстрой диагностики, цвета, пропорций и компиляции. Результаты тестов не заменяют видимую проверку принятого критерия.
3. Для запущенного Stand Service прочитать `/api/state`: `mode`, назначения поверхностей, нужные `instances[].id/status/generation/frame/error`. Проверить, что HTTP отдаёт ожидаемые модули и ассеты; при сомнении сравнить хеши с текущей сборкой. Не сохранять полный state с `csrf` в отчёт и не выводить токены.
4. Если задача включает применение к текущему стенду, штатно обновить **только затронутые источники**. В `run` пересборка файлов сама по себе не обновляет уже загруженные модули. Перезагрузка просмотрщика также не перезапускает источник. Использовать существующую команду перезапуска источника; API и UI описаны в [инструкции применения сборки](../../../apps/video-wall/docs/BRAND_INTEGRATION.md#применение-сборки-к-запущенному-стенду). Для общего модуля проследить все активные зависимости, а не фиксированный список ID. В `dev` проверить результат hot reload, не предполагать его успешность.
5. Проверить смену `generation` при перезапуске, `running`, продвижение кадров и отсутствие ошибки. Новая generation доказывает смену процесса, но сама по себе не доказывает правильный визуал.
6. В одной вкладке коротко проверить реальный путь пользователя. Для проблемы потока — его presentation; для UV, геометрии, материалов и цветопередачи просмотрщика — сам 3D-просмотрщик. Посмотреть результат, пропорции и консоль. По возможности сохранить снимок с URL/instance и временем в `artifacts/reports/`. Не подменять фактический снимок картинкой из fixture.

Штатное применение уже запрошенного исправления не требует повторного подтверждения само по себе. Скилл не даёт отдельного разрешения на остановку чужих ресурсов, публикацию или тяжёлые тесты. Соблюдать ограничения AGENTS по GPU и записи видео. Обновлять источники последовательно, сохраняя незатронутые. Если новый источник ошибается, диагностировать ошибку и сохранить штатный fallback; не повторять перезапуск бесконечно и не перезапускать весь мастер как универсальное средство.

## Что считать завершением

В отчёте различать три факта: **собрано**, **применено к источнику**, **видимый результат проверен**. Указывать только подтверждённые стадии. «110 тестов прошли» не означает «рамка соответствует референсу». Сравнить наблюдаемый результат с критерием первого шага после последней значимой правки.

Если сервис недоступен или пользователь запросил только сборку, закончить доступную часть и явно указать: «Сборка проверена отдельно; применение к работающему стенду не проверено». Не обещать, что обычная перезагрузка страницы решит проблему без проверки цепочки. Не запускать полноценный стенд или нагрузочный прогон только ради отметки.

Обновить WORKLOG: что изменено, какой фактический путь проверен, результат и ограничения. Обновить затронутую действующую документацию; техническую сверку не называть художественным утверждением.

Пример установленного дефекта: [старый процесс после обновления рамок](../../reports/vk-video-frame-live-20260927/README.md). Причина в том случае — рабочий источник, а не кэш браузера; не переносить этот диагноз на новые случаи без проверки.
