# MAX — экспорт финального контента

Отдельный локальный плагин для карты, собранной MAX Content Builder и исправленной в Figma. Читает макет, ничего не создаёт и не изменяет. Имена фреймов и старые данные каталога не назначают контент.

## Запуск

1. Откройте `Start-Server.bat` в этой папке. Используется общий локальный Frame Archive на http://localhost:47831; мастер стенда не нужен.
2. Figma → Plugins → Development → Import plugin from manifest… → `manifest.json` из этой папки.
3. Выделите **общий контейнер финальной карты или одну/несколько миссий**. Можно выбрать всю текущую страницу, но тогда попадут все подходящие карты, включая старые.
4. Запустите **MAX — экспорт финального контента**, нажмите **«1. Прочитать карту»**.
5. После чтения показана сводка: число миссий → число заданий в каждой → число экранов по каждому заданию. Иконки без экранов перечисляются отдельно и не считаются заданиями. Для каждого задания рядом показаны «экранов: N, визуалов: M». Визуалы считаются среди оставшихся прямых кандидатов, включая лишние при неоднозначности; отдельно видны готовые строки и пробелы. Равенство общих чисел само по себе не скрывает проблемную строку. Проблемные строки входят в число экранов с пометкой «требуют разбора», а не считаются готовыми. Предупреждения и отдельные визуалы доступны в раскрывающемся списке. Сверьте порядок, тексты и список пробелов. Нажмите **«2. Экспортировать / продолжить»**. Итоговый путь появится внизу.

Сам плагин поставляется обычной папкой. Нужны соседние `max-material-collector` и `pdf-export` для общего сервера/пересборки; ZIP не используется. Токен Figma, облачный API и MCP не нужны.

## Правила чтения

- Вложенные совпадения структуры внутри уже найденной миссии не становятся новыми миссиями, в том числе при выборе внутреннего фрейма.
- Миссия: вертикальный контейнер с горизонтальным рядом игровых иконок. Каждая колонка: иконка/вложенный текст сверху, вертикальный Auto Layout с кадрами ниже.
- Порядок миссий, иконок, кадров и текстов — порядок `children` внутри структуры, без сортировки по координатам, числам или именам слоёв.
- Иконка сохраняется отдельным PNG и исходными растрами/структурой; весь вложенный текст иконки хранится рядом в JSON. Семантический game ID не угадывается по пикселям.
- Кадр: горизонтальная пара «область визуала → справка». Слева берётся единственный внутренний графический фрейм, а не вся плашка со служебной подписью. Справа собираются **все видимые текстовые слои**, включая вложенные, с точными переносами/пробелами и стилями.
- Самостоятельные подписи этапов и названия слоёв не становятся инструкцией. Старые инструкции и старые screen/task IDs из pluginData не подставляются.
- Скрытые узлы исключаются. Видимые жёлтые/зелёные/красные карточки автоматически не удаляются: цвета не являются новым сценарием. Необходимость убрать конкретный материал решается в финальном макете или флажком в списке экспорта.
- Несколько возможных визуалов / отсутствие визуала / неподдержанная структура отмечаются в списке и `contentMap` как пробелы с nodeId. Из них не создаётся выдуманный экран. Поправьте структуру до одного внутреннего визуального фрейма и прочитайте карту снова.
- Изменение справки, иконки, визуала или порядка после скана блокирует продолжение соответствующей записи и требует повторного чтения. Страница назначения фиксируется при скане.

## Результат

Одна датированная папка в `artifacts/DESIGN/figma-exports/`:

```text
YYYY-MM-DD_HH-MM-SS/
  catalog.json       # общий JSON: карта, порядок, контент и пути файлов
  export.json        # подтверждения, SHA и журнал сохранения
  texts.json
  coverage.json
  index.html
  01-Миссия/01-Иконка/001-Экран/
    screen.png       # только внутренний визуал
    preview.png
    screen.json      # content + instruction.blocks + пути
    texts.json       # тексты с contentRole: visual / instruction
    figma.json       # структура визуала, если включена
    images/          # исходные растры, если включены
    screen.svg       # если включён SVG
```

`catalog.json.source.contentMap` — миссии → иконки → экраны, индекс и nodeId каждого, текущий текст иконки и все блоки справки. `catalog.json.screens` — успешно выгруженные визуалы с `content.kind` (icon/screen), индексами, `instruction.blocks` и `pngFile`. Связь — `visualNodeId = screens[].id`. В `context` также сохранена полная карта для проверки идентичности продолжения. Пробелы карты не превращаются в успешно экспортированные экраны. После снятия флажка запись остаётся в карте, но отсутствует среди выгруженных `screens`; JSON сохраняет фактический список `requested`.

PNG по умолчанию 1×; предел стороны существующего экспортного тракта — 4096 px. Вложенные исходные растры сохраняются отдельными файлами без повторного сжатия. Файлы шрифтов и видео не выгружаются, текст в растре/кривых не распознаётся. `coverage.json` общего сервера не назначает новые задания: здесь связь определяется новой картой, а не старым справочником Collector.

## Глубина аудита

«Прочитать карту» останавливает поиск на найденной миссии. В области «экран задания» выбираются только непосредственные дочерние визуалы, без чтения их внутренних слоёв и свойств компонентов. По уточнению пользователя прямой дочерний блок с точным именем «Действия внутри устройства» исключается как кнопки, даже без pluginData. Это единственное именованное исключение для экрана; остальные названия не назначают контент. Текстовые слои игнорируются при выборе визуала. Служебные actions/final-back/hotspot также исключаются по данным Builder. Несколько прямых визуалов остаются неоднозначностью. Текстовые блоки справки по-прежнему читаются полностью.

Общий полный скан страницы и глубокий fingerprint не запускаются в аудите этого плагина. При нажатии «Экспортировать» выполняется полная проверка содержимого для безопасного продолжения и чтение исходных ассетов; PNG/SVG формирует нативный exportAsync. Изменение только внутреннего визуала до старта экспорта попадёт в новый fingerprint; изменение справки/порядка требует повторного чтения карты. Старый Collector сохраняет прежний режим.

## Сохранение и продолжение

Повторно используется существующий тракт MAX Material Collector / Frame Archive: один визуал → передача → SHA-256 → запись/чтение с диска → ACK → следующий. Повтор после сбоя продолжает подтверждённые неизменившиеся файлы. «Новая выгрузка» создаёт новую папку. Отмена останавливает очередь; уже начатый нативный `exportAsync` Figma может завершиться позже. Макет лучше не редактировать во время экспорта. Общий ZIP/PDF и большой JSON со встроенными изображениями не создаются.

Выгрузка не публикуется, не меняет игру/мастер и не объявляется автоматически принятой клиентской версией.

## Разработка

```powershell
node artifacts/DESIGN/figma-plugins/max-content-exporter/build.mjs
node --test --test-isolation=none artifacts/DESIGN/figma-plugins/max-content-exporter/exporter.test.mjs
```

`map.cjs` — адаптер структуры; runtime, серверный клиент, SHA и сервер переиспользуются из текущего сборщика материалов. Все созданные выходы тестов — в `artifacts/workspace/tests/`.

[Исследование](../../../../docs/Research/max-content-exporter-20261003.md) · [Проверка](../../../reports/max-content-exporter-20261003.md).

Подготовка Content Exporter показывает номер визуала и число проверенных слоёв. Глубокая проверка при экспорте уступает event loop каждые64 слоя и обрабатывает «Остановить». Подготовка не означает сохранение: дисковое подтверждение по-прежнему показывается отдельным счётчиком. Внутреннюю операцию Figma exportAsync невозможно прервать этим способом.
