# MAX — общий backend миссий и контент (этапы 9–10)

02.10.2026. Проверяется исходная headless-реализация. Мастер, браузер и действующие игровые страницы не запускались и не переключались.

## Реализация

- `artifacts/max-game/src/content/mission-catalog.mjs`: 6 миссий и 17 общих заданий. Версия `missions-20261002-v1`. Исходные инструкции/контент перенесены из принятой карты `artifacts/max-game/design/site-game-content-map-20261002.md`; прежние числовые stages не являются новым контрактом.
- Канал сохраняет 10 экранов и две ветки из уже проверенного Channel Catalog. Mission Core композирует имеющийся чистый Game Core через переданный `task.coreCatalog`; конкретный каталог ядро не импортирует.
- Комментарии: 91755 → 91944 → 91998 → 91854 (ответ подписчику, не первый комментарий автора). Статистика: 91497 → 91501, без экрана прав администратора.
- Создание ID: SVG 01/02/03/05/06/11/12/13. Минцифры и PIN исключены; отказы не продвигают. Опциональная биометрия допускает «Не сейчас». Все три применения — отдельные пары фотографий и отдельные задания.
- Все пять узлов общения сохранены. Голосовое и видео следуют последовательно в одном задании. Промежуточные подтверждённые автоматические состояния не требуют дополнительной кнопки.
- Бизнес: платформа → сфера → выбор одного инструмента → канал, бот или мини-приложение. Две тестовые миссии используют те же задания; в тестовом бизнесе ID отсутствует.
- `mission-assets.mjs` хранит переносимый manifest оригинальных PNG, 8 SVG ID и официальный финальный QR. Оригиналы не изменялись. Контракт допускает оба формата и проверяет SHA, размеры, ссылки, геометрию и достижимость.
- `mission-core.mjs`: меню, выбор, scan, task, result, completed/incomplete/expired; версии правил и контента, общий revision и idempotent receipts. Завершение задания подтверждается допустимым действием; повтор и устаревший экран не создают второй зачёт. Result допускает следующий шаг через 800 ms доверенного времени.
- `mission-session.mjs`: SessionPort поверх обязательного PersistencePort. Контакты/их последовательности/незавершённое удержание остаются временными. Down начинает удержание, move вне зоны/up до 800 ms/cancel/потеря владельца отменяют. Up внутри зоны ровно на 800 ms засчитывает удержание. Сканирование подтверждается внутренней командой, которую клиент отправить не может. Повторная последовательность контакта сбрасывается при смене владельца/миссии.
- Таймер 180 секунд — смысловое состояние backend. Потеря владельца сохраняет остаток, resume компенсирует также result/automatic-screen timing. Return menu сохраняет шаг и остаток; restart начинает миссию заново, reset удаляет весь игровой прогресс. Подтверждённый финал останавливает таймер и содержит официальный QR. Возврат после result не требует повторного зачёта.
- Раскладка хранится отдельно: `layouts:{layoutRevision,positions,receipts}`. CAS только по `expectedLayoutRevision`, игровой revision не растёт. Разрешены известные task IDs и `open-max`, только базовые `{x,y}`; временные shift/phone poses не принимаются. Сброс игрового прогресса сохраняет независимую раскладку.
- Snapshot скрывает внутренние task receipts. Descriptor содержит ресурсы, информацию справа, действия внутри устройства, ближайшие ресурсы подготовки, граф и финальный QR. ID-ребра идут от создания ID к каждому применению независимо; порядок демонстрации не превращён в зависимость функций друг от друга.

## Хранение и восстановление

Record v2: `{schemaVersion:2,mission:MissionModel,layouts,clockCheckpointAt}`. Snapshot/receipt записываются атомарным commit до публикации или ответа. Ошибка записи сбрасывает cache; после потери ответа retry читает сохранённое подтверждение и не делает второй commit. Восстановление проверяет смысловые receipts, не анимационные кадры и не legacy stages. Неизвестные/подменённые данные не создают успешных ответов.

При холодном чтении ownerActive прежнего процесса отзывается и pause сохраняется **до выдачи snapshot**. Политика времени: pause ставится на последний подтверждённый `clockCheckpointAt`, серверный простой не расходует игровой бюджет. Активный backend сохраняет checkpoint не чаще одного раза за 5 секунд в существующем pollTime и при каждой принятой смысловой команде; игровой revision от отдельного checkpoint не растёт. При аварии может откатиться не более 5 секунд неподтверждённого времени. После нового lease deadline и время автоматических фаз сдвигаются на продолжительность паузы; 180 секунд заново не выдаются. Нельзя восстановить старый lease из сохранения. После холодного чтения требуется новый владелец ввода; незавершённое удержание не восстанавливается. Анимационный resume не запускается backend сам: renderer получает resumeRequired и текущий смысловой шаг.

Если commit подтверждения удержания не удался, незавершённый контакт отменён; человек повторяет удержание после восстановления соединения. Это явное поведение, без подстановки успешного scan. Разные Session Application экземпляры не предназначены быть одновременными владельцами одной сессии; CAS предотвращает перезапись устаревшего writer.

## Пробелы исходных материалов

Группа, стикеры/реакции, финал истории и некоторые бизнес-экраны отсутствуют либо не подтверждены. Это явно отражается в меню/descriptor. Доступные бизнес-скриншоты сохранены как контекст, но неверный экран не выдается за завершённое действие. Пропуск продолжает просмотр и записывает skipped; итог остаётся incomplete. Новая логика не обещает успешное прохождение отсутствующего клиентского контента.

Для остальных заданий используется разрешённый запасной вариант — одна смысловая кнопка под изображением, либо варианты ответа внутри устройства. Точные hotspot-геометрии всех оставшихся экранов потребуют сверки при подключении renderer; сейчас не выдумываются по именам файлов. Существующие hotspots канала сохранены.
