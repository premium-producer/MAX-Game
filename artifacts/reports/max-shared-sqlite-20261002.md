## Контракт и долговременная запись

`await createSqlitePersistencePort({databasePath, busyTimeoutMs:5000})` требует явный абсолютный путь. Возвращает `load(sessionId)`, `create(sessionId, record)`, `commit(sessionId, expectedVersion, record)`, `saveOnce(importId, artifact)`, `createImported(sessionId, record, {importId})`, `getImportTarget(importId)`, `backup(destinationPath)`, `close()`.

`load` возвращает `{version, record}` либо null. `create` возвращает 0, `commit` — expectedVersion + 1. Ошибки существующей/отсутствующей записи и CAS: SESSION_EXISTS, SESSION_NOT_FOUND, STORE_CONFLICT. Не сериализуемые/нефинитные JSON, невалидные IDs и версии отвергаются. Driver поддерживает известные envelope `{schemaVersion:1,game,layouts}` и `{schemaVersion:2,mission,layouts}`; неизвестная версия отвергается. Смысл модели проверяется Application/Core. Новые поля mission model и базовых координат не обрезаются.

Одна строка `max_sessions` содержит store version и полный JSON SessionRecord вместе с GameState и command receipts. `BEGIN IMMEDIATE` + CAS + `COMMIT` обеспечивают атомарность; ACK отправляется только после успешного commit. WAL и synchronous=FULL включены. Ошибка транзакции вызывает rollback. Store version не смешивается со смысловой game revision и будущей layoutRevision.

Это реализация атомарного PersistencePort, а не нормализованных отдельных таблиц processed_commands/completion_receipts из целевой архитектуры. Receipt ledger пока хранится внутри authoritative record; повторный зачёт предотвращает ядро и сохранённый ledger. Отдельные индексы/таблицы можно добавить позже без изменения порта. Не добавлялись event sourcing движения, внешняя зависимость или fallback к браузерному прогрессу.

Все DatabaseSync/SQL вызовы выполняются только в storage worker. Host получает асинхронные сообщения и не открывает DB. В worker запросы сериализуются, включая async online backup. Factory подтверждает готовность только после открытия, проверки схемы и подготовки statements. Недоступный node:sqlite/backup даёт SQLITE_UNAVAILABLE; более новая storage schema — UNSUPPORTED_STORAGE_SCHEMA без перезаписи metadata. Ошибка worker отвергает pending promises. `close` сразу запрещает новые запросы, дренирует принятые запросы и ждёт завершения worker; принятый commit не отменяется.

## Backup

`backup` использует [официальный SQLite online backup Node API](https://nodejs.org/api/sqlite.html#sqlitebackupsourceDb-path-options). Копируется согласованный snapshot, включая уже подтверждённые WAL записи; простого копирования активного sqlite-файла нет. Destination должен быть новым, source и существующая копия не перезаписываются. Новые локальные записи ждут окончания backup. Пользователь должен использовать возвращённую копию только после успешного await; при сбое неполный новый destination сохраняется для диагностики, прежние копии не затрагиваются. Подключение backup к эксплуатации/переносу выполняется host-слоем отдельно.

## Явный архив импорта

`saveOnce` реализует DurableArchivePort: новая запись возвращает created, идентичная existing-identical; другое содержимое под тем же importId даёт IMPORT_ID_REUSED. Полный JSON исходника/artifact хранится в отдельной `max_import_archives` таблице. Canonical compare игнорирует порядок object keys, сохраняя значения и порядок массивов. Запись atomic и create-only. Архив переживает worker restart и входит в online backup; ключи старых профилей не читаются этим драйвером. Реальный applyExplicitImport подтверждённого канального экспорта прошёл create/reopen/retry. Доказательство принадлежности существующего target и политика конфликтов принадлежат migration/application слою.

`createImported` записывает новую session и provenance claim в `max_import_targets` одной транзакцией. Перед этим обязательно существует immutable archive, его targetSessionId и record должны совпадать с активацией. FK включены; session и claim имеют уникальные IDs. `getImportTarget` возвращает подтверждённый target или null. При конфликте session insert claim не появляется: совпадение текущего state и наличие архива сами по себе не доказывают принадлежность. Migration layer проверяет этот claim при повторе; чужой идентичный свежий target остаётся конфликтом и на второй попытке, и после worker restart. Clock checkpoint mission record проходит opaque JSON storage и проверяется Application.
