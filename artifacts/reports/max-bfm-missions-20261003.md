# MAX BFM — подключение прохождения, 03.10.2026

## Реализация

- BFM теперь продолжает после раскрытия: задания → результат → следующее задание → финал с QR. Прежняя остановка владельца/таймера после раскрытия удалена. Восстановление открывает подтверждённый экран; рестарт проходит через существующий session facade.
- Использованы прежние Mission SessionPort, MISSION_CATALOG и sharedTaskMarkup. Backend, каталог, ассеты, инструкции и правильные ответы не переписаны. В sharedTaskMarkup добавлен необязательный resultText с прежним default; только BFM передаёт отдельное сообщение о пропуске, чтобы missing не назывался выполнением.
- Горизонтальные устройства — PC; горячие области и кнопки внутри/под устройством; справа только справка. Градиенты кнопок, логотип, шрифт и GPU-фон сохранены.
- Декодируются изображения именно входящего DOM-фрагмента до commit. Старый экран сохраняется при ожидании/ошибке. Индикатор после800ms, timeout12s и retry. AbortController + generation защищают рестарт/меню от позднего decode/transition callback.
- Native BFM transition поддерживает refresh уже открытого экрана; смена скриншота внутри одного task не запускает повторный component entrance. Оболочка устройства и справки сохраняется при том же device kind. Ввод включается после finished и актуальной готовности, старый pointer token не переносится на новый экран.
- Автоматические этапы/ADVANCE_RESULT по-прежнему выполняет backend. Presentation gate не опрашивает автопереход, пока кадр не показан, и выдерживает descriptor automaticMs на видимом кадре. Hidden освобождает владельца, а не догоняет скрытое время.

## Подтверждения

- PASS14 CPU-тестов: `bfm-start`, `bfm-missions`, `webgl-shared-ui` с `--test-isolation=none` (~126ms). Полные пути шести миссий через настоящий Session application/facade + BFM markup; blogger public/private; stale answer; ранний отпуск/повтор/рестарт; отмена decode; refresh/cancel transition; QR; честный incomplete при missing.
- DOM decode/ViewTransition в CPU проверены через заглушки. Настоящее браузерное отображение, native animation и физический touch этими тестами **не доказаны**.
- PASS syntax пяти затронутых runtime/build-модулей, duplicate guard.
- PASS esbuild:82 модуля. Guard запрещает старые motion/reference solver зависимости. Builder сверяет120 уникальных общих runtime-ассетов с SHA каталога; не перезаписывает их.
- PASS [HTTP/SHA124 ресурсов](max-bfm-missions-http-20261003.json): HTML/JS/CSS/provenance +120 ассетов, включая QR и PC. После финальной корректировки обновлена проверка четырёх файлов нового renderer; каталоговые ассеты не менялись.
- Сборщик пишет только `apps/max-game/bfm-design/`. Мастер, TD, предыдущие bundles и deployment не менялись. Браузерные вкладки/тяжёлый GPU-прогон/видео не запускались.

## Ограничения и приёмка

В communication/business/business-test есть пропуски исходного общего каталога: просмотр завершается как incomplete, отсутствующие задания не засчитываются. Контент не выдумывался. Local profile сохранён; server/смена renderer и drag ещё не реализованы в BFM. Ring→task — native dissolve BFM, а не обещание безопасных физических траекторий; художественная доводка движения остаётся отдельным этапом.

Сначала пользователь проверяет блогера:1) ладонь → «+» в телефоне;2) публичный канал, комментарии и статистика → QR;3) рестарт и повтор/продолжение. Остальные миссии затем малыми группами. [Исследование](../../docs/Research/max-bfm-missions-20261003.md) · [TODO](../../apps/max-game/docs/TODO.md).
