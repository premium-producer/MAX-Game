# Guided Reveal: аудит и исправление входа телефона

Дополнение 30.09.2026 по медленному экрану ID: после пользовательского вопроса добавлен ограниченный prewarm текущего и следующего SVG создания ID. Он декодирует изображение, растеризует CanvasTexture 360×800 и вызывает `renderer.initTexture` через тот же renderer до открытия следующего шага; при готовности подготовленный `<img>` переходит в телефон. Ранее добавленный loading остаётся fallback. `node --check` двух JS, duplicate guard, 27 CPU-тестов и сборка MAX (326 файлов/91 модуль) прошли. Время до первого кадра и видимый эффект на машине пользователя не измерены; пользователь проверяет локальную страницу. Другие миссии пока не получили prewarm.

Дополнение 30.09.2026: три кадра пользователя из «Стать блогером» показали пустой телефон при первом открытии и корректный скриншот только после перезагрузки/повторного входа. Поэтому прежняя браузерная проверка цифрового ID ниже **не подтверждает исправление первого входа во всех миссиях**. Найдена гонка в `journey-webgl-ui.mjs`: полный `rebuild()` очищал ожидающий `refreshPart()` и удерживал старую пустую группу телефона. Ожидающий refresh теперь исключает её из удержания. Синтаксис, duplicate guard и локальная сборка прошли; визуальный статус остаётся открытым до проверки пользователем. Мастер не затрагивался.

30.09.2026. Пользовательский кадр цифрового ID на 2:50 показывает уже достигнутую связь, но ни телефона, ни справки. В исходниках `phone-enter` мог ждать `gpuReadyKey` без верхней границы; это подтверждённый дефект контракта, хотя точный потерянный callback в пользовательской сессии не зафиксирован. Исследование и источники: [phone render pipeline](../../../docs/Research/max-phone-render-pipeline-20260930.md).

Исправлено в исходниках: GPU-отметка больше не управляет семантической фазой; декодированные изображения загружаются в существующий renderer через `initTexture` до видимого кадра; ошибочный/зависший кадр заменяется текстом внутри устройства после 2 секунд активного ожидания. Для `phone-enter` есть защитный предел 4 секунды на визуальную посадку, не расходуемый drag/паузой. Отложенный commit проверяет текущий ключ кадра, отменённый переход снимает pending и повторяется. Кнопки и справка остаются привязаны к актуальному шагу/токену. Рамка/содержимое продолжают использовать общую presence.

Проверка: `node --check` изменённых JS, 52/52 целевых CPU-теста (включая цифровой ID и пропавшее подтверждение посадки на 30/60/120Hz), duplicate guard PASS, MAX build 326 файлов/91 модуль, check-local PASS. В одной браузерной вкладке service и обычный review цифрового ID показали телефон, кадр360×800, справку и действие «Создать QR»; клик открыл следующий кадр «Документы с Госуслуг». Обычный review дошёл до `task`: `sceneVersion=mediaReadyKey=gpuReadyKey`, presence≈1, изображение360px и справка видны, ошибок консоли нет. После финальной локальной сборки с размером устройства для fallback перезапущен только `max-wall-right`: generation изменилась с `f318105d-…` на `773c5b21-…`, статус running, кадры продвигаются, `Check.bat` PASS в dev; presentation ранее показал меню миссий из потока. Пользовательская сохранённая сессия и физический TD не проверены; этот кадр не доказывает отсутствие всех возможных GPU-сбоев.

Открыто: fault-injection декодирования/GPU upload в браузере и физический TD/Spout; художественная оценка плавности входа пользователем. Полное исчезновение canvas при потере WebGL-контекста не покрывается локальным текстовым fallback.
