# Готовый установщик небольших обновлений

Использовать повторно при следующих разрешённых обновлениях MAX и Стеллы. Историческое имя каталога `deploy-sound` сохранено; установщик принимает обычные изменения `launcher/` и `www/` обоих приложений. **Не создавать отдельный установщик под каждый новый патч.**

Обычные задачи заканчиваются локальной сборкой и необходимой проверкой. Следующие команды с доступом к стендам выполнять только после отдельного запроса пользователя на установку. CHUWI недоступен в списке целей.

## Локальная подготовка

Создать небольшой JSON-список поставки, например:

```json
{
  "id": "UI-20261027-2",
  "release": "C:/KDW-Stand/releases/KDW-Stand-20261027-RC4-1",
  "base": "production/KDW-Stand-20261027-RC4-1",
  "previousPlans": ["docs/verification-sound-deploy-20261027/plan.json"],
  "files": ["apps/max-game/www/admin/index.html"]
}
```

Это пример, не автоматически разрешённый выпуск. `previousPlans` — последовательность **успешно установленных на выбранных ПК** патчей после исходной сборки. После очередной установки добавлять её `plan.json`, а не снова сравнивать с чистой RC4.1. Если версии двух ПК разошлись, для них нужны разные базовые цепочки; запрещено обходить несовпадение хешей.

```powershell
python ops/production-build/deploy-sound/prepare-patch.py --spec PATH_TO_SPEC.json --output .cache/patches/UI-20261027-2
```

Подготовка локальная. В архив попадают только изменённые файлы, план и существующий `install.ps1`. Неизменённые файлы пропускаются, цепочка базовых хешей проверяется. Каталог пакета не перезаписывается. `prepare.py` оставлен для истории первого звукового патча; для новых пакетов использовать `prepare-patch.py`.

## Разрешённая доставка

```powershell
python -X utf8 ops/production-build/deploy-sound/deploy.py preflight max-game-pc stela-pc --package-dir .cache/patches/UI-20261027-2
python -X utf8 ops/production-build/deploy-sound/deploy.py apply max-game-pc --package-dir .cache/patches/UI-20261027-2
python -X utf8 ops/production-build/deploy-sound/deploy.py status max-game-pc --package-dir .cache/patches/UI-20261027-2
# После complete на первом ПК:
python -X utf8 ops/production-build/deploy-sound/deploy.py apply stela-pc --package-dir .cache/patches/UI-20261027-2
python -X utf8 ops/production-build/deploy-sound/deploy.py status stela-pc --package-dir .cache/patches/UI-20261027-2
```

Роли с 27.10.2026: `max-game-pc` → DESKTOP-64J4BMN / DR7, `stela-pc` → DESKTOP-DBD624H / DR2. Старые физические aliases `stella` и `max_right` соответственно сохранены для журналов и совместимости; они больше не обозначают текущую роль приложения. Проверка роли отклоняет несовпадение hostname. Отчёты продолжают использовать физический alias, чтобы сохранять цепочку патчей.

Выбирать только нужные ПК. Один preflight и один итоговый отчёт на ПК; читать промежуточный status только если установка действительно ещё выполняется. Обычный файл передавать через `put`. `--resume` — только для частично загруженного **того же неизменного** архива, после обрыва. Проверка SHA256 обязательна в любом случае.

Установщик сохраняет app.json, настройки, пользовательские данные и текущий режим вывода; хранит резервные копии заменённых файлов и откатывает их при ошибке. Останавливает и перезапускает только приложения, перечисленные в плане. Если приложение было остановлено, поднимает его только server-only для проверки и админ-панели. После готовности обоих Spout-слоёв восстанавливает ARM, если ввод был включён до обновления; выключенный оператором ввод не включает. При активном посетителе или разговоре откладывает установку.

Итоговые отчёты и копия плана: `docs/stand-patches/<ID>/`. Использовать их для следующей базовой цепочки только при `phase=complete` на целевых ПК. Не пересоздавать пакет после preflight: его план привязан к проверке по SHA256.

## Границы

Этот путь предназначен для кода и web-ресурсов установленных MAX/Стеллы с существующими health/operator/sound API. Изменение Electron, нативных DLL, протокола запуска, удаление файлов и миграции данных требуют отдельного рассмотрения; их нельзя маскировать обычным патчем. Расширять существующий инструмент только при таком новом требовании или обнаруженной ошибке, не переписывать при очередном изменении интерфейса.

Проверенный на production установщик использован в SOUND-20261027-1. Параметризация для последующих ID и отдельных компонентов проверена локально; нового удалённого прогона ради этой доработки не выполнялось.

## Постоянное разрешение на прерывание сессий — 27.10.2026

Пользователь явно указал: «Всегда игнорируй запушеные сессии». При отдельно запрошенной установке на production использовать `interruptVisitors: true` (prepare-patch.py теперь выставляет его по умолчанию) в spec/plan без повторного запроса подтверждения. Разрешено кратко прерывать активные сессии для перезапуска обновляемого приложения. Это не разрешение на автоматическую доставку локальных правок. CHUWI не обновлять; проверки hostname, базовых SHA, резервного копирования, сохранения настроек и восстановления приложения обязательны. Перезапускать только изменяемые приложения.


## Сохранение ввода лидара — 27.10.2026

По прямому требованию пользователя не оставлять ввод отключённым после обновления. Установщик сохраняет armed из preflight и восстанавливает его штатным API после готовности обоих слоёв; проверяет armed=true и active=true. Порт, калибровку и enabled не менять. На остановленных/server-only экземплярах ввод не включать.



## Автоматический ввод MAX — 27.10.2026

Новая локальная версия MAX больше не использует ручной ARM. Поле armed=true и старый API оставлены для совместимости; команды DISARM и output-arm.json не блокируют касания. Восстановление ARM в установщике остаётся совместимостью со старыми установленными сборками. Новая версия автоматически принимает касания после готовности контента, независимо от готовности фона. Стенд обновляется только по отдельному запросу пользователя.
