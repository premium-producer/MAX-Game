# Локальная реализация WebGL-активностей MAX

Дата: 27 октября 2026 года. Обновлений стендов в рамках этой работы нет.

## Что реализовано

- Посты и товары используют общий GPU-слой: падающие карточки, клеточный след, ожидание подтверждения, перелёт фотографии, появление содержимого в телефоне и уход оставшихся карточек после достижения цели.
- Содержимое телефона также рисуется через WebGL: шапка, фотография бизнеса, лента, реакции, подписчики, витрина, цены и рейтинг. Счётчики используют подготовленные глифы, без повторной растеризации всей карточки.
- Один существующий renderer/canvas и один вызов update в общем кадре. Отдельная THREE.Scene изолирует игровые материалы от перестроения интерфейса маршрута; дополнительный проход использует тот же GPU-контекст и камеру.
- Геометрия и ввод используют координаты viewport. Hit-test учитывает порядок карточек, поворот, скругления и маски последнего отрисованного кадра. Контакт, начавшийся вне карточки, может выбрать её при входе. Повтор одного контакта не отправляет команду снова; смена сессии/экрана/повторный вход инвалидируют старое поколение.
- `START_POSTS`, `START_STORE`, `PUBLISH_POST`, `PICK_PRODUCT` и завершающие действия остаются штатными. Подписчики, рейтинг и опубликованные записи берутся из подтверждённого snapshot. Ожидание подтверждения ограничено 15 секундами, автоматической повторной отправки нет.
- Изображения и текст подготовлены до запуска активности. Загрузка текстур ограничена двумя на кадр с мягким бюджетом 2 мс. Лимит банка — 64 MiB с учётом mipmaps. Перелёт использует ту же фотографию, что исходная и сохранённая карточки.
- При выходе ресурсы освобождаются после короткого затухания. При потере WebGL-контекста ввод активности закрывается до восстановления её ресурсов; прогресс игры не сбрасывается.
- Ручная прокрутка ленты сохраняется; новые публикации не принуждают к автоматической прокрутке. Кнопка «Новые публикации» возвращает к последним записям. Витрина прокручивается к заполненным ячейкам, а не к пустым шаблонам.
- DOM остаётся для обычных кнопок, полей, клавиатуры и неподвижного семантического списка. Падающих DOM-карточек и DOM-клонов фотографий в GPU-режиме нет.
- Порты, ARM, enabled, настройки калибровки, маппер и транспорт лидара не изменены.
- Поглощённые GPU-слоем касания передаются штатному production-таймеру с исходным `isTrusted`, чтобы активный посетитель не считался бездействующим. Сохранены ограничение частоты и удаление подписки при завершении.

## Включение

Добавить `activityRenderer=webgl` к URL локальной игры. Пример пути:

```text
/webgl-v5/client.html?backend=local&view=pixel-map&activityRenderer=webgl
```

Для старого варианта — `activityRenderer=dom` либо отсутствие параметра. До аппаратной приёмки стандартный запуск остаётся прежним. Переключатель читается при загрузке приложения; менять renderer в середине активной игры не следует.

`activityDebug=1` включает диагностические координаты в `data-activity-frame`. Без него покадровый JSON не записывается. Сводные `data-activity-metrics` обновляются раз в секунду и содержат время CPU-update, интервалы кадра, число карточек/перелётов, байты и загрузки текстур. После освобождения банка записывается `status: released`, `bytes: 0`.

## Проверка

```powershell
npm run build:max
npm run check:generated
npm run test:max
npm run test:activity:webgl
```

Браузерная проверка сама поднимает временный локальный сервер и использует memory-сессии. Она не подключается к production-стендам, не меняет рабочие профили и не занимает порт ввода лидара. Нужен установленный Chromium для Playwright.

174 unit-теста MAX прошли, включая новые проверки hit-test, полёта, прокрутки, переносов, памяти, поколений ввода, повторных контактов, ограниченных GPU-следов и production-таймера активности. Сборка и проверка generated entry прошли.

`browser.json` содержит результат реального прохождения: хорошие/плохие публикации, достижение цели канала, набор рейтинга магазина, resize, восстановление GPU-контекста, освобождение ресурсов, выбор карточек в банках цветов/автомастерской и сохранённый DOM-режим. PNG показывают игровой и завершённый состояния.

Измерения относятся к локальному Chromium. `frame.p95` — интервал общего кадра, `update.p95` — CPU-часть контроллера активности; это не измерение задержки или GPU-времени приёмника Spout. Пики подготовки и восстановления учитываются отдельно при аппаратной приёмке. Реальный Electron, два Spout-потока и физический ввод лидара на стенде в этой работе не проверялись.

В проверенном локальном прогоне: CPU-update p95 до 0,3 мс, интервал кадра p95 16,7–16,8 мс; память текстур банков около 29,8–35,3 MiB. Эти числа не являются обещанием производительности на стенде.

Обязательная команда `npm run test:audit:all` также была запущена: проверки до браузерного этапа прошли, включая сохранение профиля сборки и retention. Общий браузерный этап завершился ошибкой из-за 17 ответов HTTP 409 в сценариях `stela-audience` и `stela-result`. Полный аудит не считается зелёным. Исходники Стеллы в этой работе не изменялись; ошибка не скрыта и не подавлена. Отдельный браузерный набор WebGL-активностей MAX прошёл без ошибок. Последующее добавление передачи контакта production-таймеру проверено финальной сборкой и 174 unit-тестами.

## Изменённые точки подключения

Основная реализация: `apps/max-game/source/client/src/activity-webgl/`.

Подключение: `kdw-posts.mjs`, `kdw-interactions.mjs`, `journey-webgl-ui.mjs`, `kdw-card-clock.mjs`, `kdw-native-touch.mjs`, `kdw-production.mjs`. Проверка готовности добавлена через `adapt-stand-main.mjs`; generated entry собран штатно. Старый DOM-рендерер и frozen stand-base сохранены. `kdw-preview.mjs` получил выбор бизнеса только для изолированного предпросмотра; production удаляет параметр `interaction` как прежде.

Подготовка карточек выполняется Canvas 2D один раз, а не на каждом кадре. Банк удерживается целиком в пределах лимита и освобождается целиком при выходе; дополнительный LRU для десяти карточек не понадобился. Общие quad-буферы и материалы переиспользуются, клеточный след собирается в ограниченные instanced-пакеты.
