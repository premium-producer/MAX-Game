# Быстрые итерации на стенде

## Обязательный режим работы

Уточнение пользователя от 27.10.2026 имеет приоритет над прежним порядком доставки:

- Все обычные правки выполняются **локально**. Завершение разработки не запускает публикацию, загрузку, установку или проверку по SSH
- Доступ к стендам и доставка накопленных изменений — только по конкретной просьбе пользователя: «вносим на стенд», «обнови стенд» либо явный запрос удалённой диагностики. Прежнее разрешение на прошлый выпуск не распространяется на следующие правки
- Рабочие цели — только production MAX (`max-game-pc`, DESKTOP-64J4BMN / DR7) и Стелла (`stela-pc`, DESKTOP-DBD624H / DR2). **CHUWI исключён** из обновлений и проверок до нового явного указания пользователя
- Точки запуска на рабочих столах хранить только в `kdw-startup`: актуальные Start/Admin/Stop для MAX и Стеллы, старые версии — в `kdw-startup/old`. Не создавать новые россыпи ярлыков RC-версий на рабочем столе при обновлении. Сами батники внутри релиза сохранять на месте: их относительные пути зависят от расположения
- Интернет на площадке нестабилен. Готовить и проверять пакет локально; передавать только изменённые компоненты и файлы, используя уже установленный runtime и ресурсы. Не заставлять стенды скачивать зависимости и полные релизы для небольшой правки
- Объединять накопленные правки в одну поставку. Выбирать кратчайший доступный проверенный транспорт; GitHub не является обязательным промежуточным шагом доставки
- После команды на установку: один сводный preflight на целевой ПК, передача с проверкой хеша, установка с откатом, один итоговый отчёт. При обрыве сохранять проверенные данные и возобновлять передачу там, где транспорт это поддерживает; не перезагружать успешно доставленные файлы
- Не открывать новый цикл SSH ради дополнительной уверенности или оформления отчёта. Аппаратную проверку, невозможную локально, отмечать как отложенную до разрешённого обновления

Разработка должна занимать основную часть работы; доставка — отдельный короткий этап по запросу. Таблица ниже описывает проверки **после такого запроса**, а не автоматические действия после каждой правки.

Правило работы после аудита 27.10.2026: сначала определить затронутый компонент и проверяемый результат, затем выполнить минимальный достаточный цикл. Полный выпуск обоих приложений не является обязательным этапом каждой правки.

## Текущее назначение ПК — 27.10.2026

По прямому указанию пользователя роли переставлены:

| Роль | Физический ПК | Пользователь | Новый alias роли | Исторический SSH alias |
|---|---|---|---|---|
| MAX | DESKTOP-64J4BMN | DR7 | `max-game-pc` | `stella` |
| Стелла | DESKTOP-DBD624H | DR2 | `stela-pc` | `max_right` |

Источник соответствия — `ops/production-build/stand-roles.json`. В новых командах `deploy-sound/deploy.py` и `deploy-rc2/remote.py` использовать aliases ролей. Исторические aliases остаются идентификаторами физических машин; старые отчёты не переименовывать и не трактовать как текущие роли. Старые RC2/RC3/RC4 сценарии не использовать для нового развёртывания по их историческим названиям приложений.

Обе сборки и шесть актуальных ярлыков остаются на обоих ПК. Смена роли не меняет hostname Windows, ключи SSH, порты, аудиоустройства, профили и режим запущенных приложений. Стелла на DR2 получает доступ к уже подключённому Logitech BRIO; отсутствие микрофона на DR7 теперь относится к ПК игры MAX. Проверка аудио от 27.10 до перестановки хранит прежние подписи.

Изменение отображаемых ролей в Producer Desk поручено чату «ДОСТУП ПО SSH» (01a17bc0-74eb-7530-8858-00af3fc088f8); факт выполнения проверяется по его результату.

## Выбор проверок

| Изменение | Сборка и проверка | На стенде |
|---|---|---|
| Текст, CSS, расположение | Только затронутое приложение; конкретный экран и отсутствие overflow | Один целевой ПК, снимок/проверка экрана |
| Событие или звук Стеллы | Только Стелла; сценарий события и фактический старт/выход аудио, а не только HTTP 200 | Запуск Стеллы в разрешённом режиме, один итоговый отчёт |
| Игровая логика | Затронутая ветка и связанные тесты | Один сценарий на целевом ПК |
| Общий протокол, launcher, AEC, Spout, OSC | Связанные тесты; общий аудит при затрагивании нескольких подсистем | Проверка нужного оборудования, остальных ПК — после первого успешного результата |
| Секреты, калибровка, настройки | Валидация и сохранность профиля | Чтение результата без переустановки кода |

До первой установки новых функций проверить все критерии из запроса. Для звука — реальное воспроизведение; для сети — адрес, порт и Firewall; для запуска — переход из server-only. Ошибки этих проверок исправлять до публикации и массовой установки.

После успешной проверки повторять её только при изменении соответствующего кода, ошибке или конкретном новом риске. В отчёте отмечать версию/хеш проверенного компонента и допустимость повторного использования результата.

## Доставка

1. Определить изменённые файлы и компоненты. Не менять версию и не перезапускать второй компонент только ради одинакового номера.
2. Для рабочей итерации передавать пакет изменений с базовым манифестом, SHA256 и возможностью отката. Полные архивы готовить для контрольного выпуска/нового ПК, а не перед каждым патчем.
3. GitHub остаётся хранилищем исходников и контрольных релизов. Малый оперативный патч допускается передать по уже проверенному SSH; обязательной предварительной загрузки сотен мегабайт в GitHub нет.
4. Если CDN не передаёт данные с приемлемой скоростью, две короткие попытки, затем резервный транспорт. Не повторять пятиминутный цикл на каждом ПК.
5. Сначала один целевой ПК; при успехе и необходимости — остальные параллельно. Не трогать работающий второй компонент без необходимости.
6. Сохранять настройки, секреты и данные; проверять базовую версию, пакет, изменённые файлы и состояние приложения после запуска. Не ослаблять проверку подлинности SSH и защиту от остановки активной игры ради скорости.

## SSH и отчёты

- Перед работой — один сводный preflight на ПК; собрать нужные версии, состояние, активную игру и свободное место одним запросом
- Установка и необходимые проверки должны выполняться одним удалённым заданием с журналом этапов
- Состояние читать по изменению/завершению; резервный опрос — с увеличением интервала, без отдельных запросов ради каждого файла
- После выполнения — один сводный отчёт на ПК. CSV/FPS и другие тяжёлые материалы — только при изменении соответствующей подсистемы или диагностике
- Не выполнять повторный SSH-аудит уже подтверждённого состояния для оформления документации

## Что уже изменено, а что ещё требует реализации

В `ops/production-build/deploy-rc4/collect.py` сбор пяти отчётов и health объединён в один SSH-запрос вместо шести; SFTP-загрузка метрик отключена по умолчанию и включается `--metrics`. Для двух production-ПК обычный сбор требует 2 SSH-запроса вместо 12 и не скачивает CSV. В stage/apply/collect/task разрешены только production-цели; stage/apply/collect требуют явного списка ПК, без автоматического обхода всех устройств.

В `download.ps1` предел одной попытки снижен с 75 до 20 секунд, попыток — с пяти до двух; добавлен контроль низкой скорости, размер части уменьшен с 8 до 1 МиБ. Существующий apply.py использует резервный SSH при ошибке загрузки. Это локальные изменения инструментов, без повторной установки на стенды.

**Готовый установщик использовать повторно:** `ops/production-build/deploy-sound/install.ps1`. Он уже применён на обоих production-ПК. Для нового обновления менять только JSON-список файлов, ID и подтверждённую базовую цепочку; пакет готовит `prepare-patch.py`, а `deploy.py --package-dir ...` выполняет прежний порядок preflight → apply → status. [Команды и ограничения](../ops/production-build/deploy-sound/README.md).

**Не создавать новый установщик и новый цикл доставки при каждой правке.** Расширять существующий инструмент только при конкретной ошибке или новом требовании: миграции данных, изменении runtime/нативных DLL/протокола запуска. Для обычного текста, интерфейса и кода повторно использовать механизм резервного копирования, проверки хешей и отката. Параметризация следующих патчей проверяется локально; не отправлять тестовый патч на стенды ради подтверждения порядка.

Перед сборкой следующего патча учитывать уже установленные патчи: исходный RC4.1 плюс подтверждённые `plan.json` в порядке установки. План SOUND-20261027-1 сохранён в `docs/verification-sound-deploy-20261027/plan.json`. Не считать установленный код снова чистой RC4.1. Если ПК имеют разные цепочки, готовить дельты для их фактических баз.

Отчитываться о **полном времени обновления**, отдельно указывая подготовку, передачу и установку. Несколько секунд передачи не выдавать за длительность всей задачи.

Бюджет для небольшой готовой правки: ориентир 5–10 минут на локальную проверку и доставку при доступном ПК. Это целевой бюджет, не измеренная гарантия и не оценка разработки новой подсистемы. Если цикл выходит за бюджет, сначала определить блокирующий этап, а не запускать ещё один полный выпуск.

Собирать длительности этапов отдельно: build, test, package, transfer, install, health. Отделять время активной работы, ожидания и повторного выполнения. Без такой телеметрии не приписывать всю задержку сети.
