# Восстановление MAX и Стеллы — локальная реализация 27.10.2026

Обновление статуса: по отдельному разрешению пользователя итерация **установлена на обоих production-ПК** патчем [RESILIENCE-20261027-1](../stand-patches/RESILIENCE-20261027-1/README.md). Работают API/админки с логированием; графический вывод, ранее остановленный, не включался. Ниже сохранён отчёт локальной реализации и предварительного аудита. CHUWI не использовался. Резервный показ и контроль приёмника в TouchDesigner остаются за заказчиком.

## Что изменилось

- Общий `runtime-main.cjs` запускает supervisor, API и графический worker отдельными процессами Electron. Supervisor и API отключают собственное аппаратное ускорение; графика остаётся в отдельном worker. API продолжает обслуживать обмен, звук и админку при завершении графического процесса.
- Существующий профиль `data/profile` остаётся у единственного графического worker. Новые API/supervisor получают отдельные каталоги профиля. Перед заменой API прежний worker завершается; новый стартует после готовности API. Профиль и подтверждённые данные игры не удаляются.
- Контроль IPC-heartbeat, 5 секунд до обнаружения зависшего процесса, до трёх автоматических перезапусков за 5 минут с задержками 1/3/10 секунд. Исчерпание бюджета даёт `degraded`, сохраняя панель supervisor. Ручной повтор ограничен одной попыткой в минуту для каждой роли.
- `Stop` сохраняет `data/runtime-desired.json: stopped`. Watchdog уважает эту запись; обычный явный запуск снова разрешает работу. Отдельное состояние `outputEnabled` сохраняет режим админки без сцены.
- Графический worker удерживает Windows от автоматического сна на время работы через `powerSaveBlocker`; это не изменение схемы питания и не защита от явного выключения/системного сбоя.
- MAX: ошибочный размер, отсутствующий handle и неосновной widget имеют отдельные причины отказа. Один плохой кадр пропускается. Заимствованная текстура освобождается после GPU fence; при исключении во время native submission удерживается до завершения worker. Мост имеет собственную last-good texture, до трёх незавершённых операций на слой.
- Фон получает собственный requestAnimationFrame; IPC передаёт только настройки, не управляет частотой отрисовки; свежесть кадров и живость content-renderer проверяются независимо. Статичный слой периодически инвалидируется, чтобы отсутствие изменений страницы не выглядело как остановка GPU. При восстановлении renderer предоставляется 15 секунд на загрузку.
- Сбой/reload renderer отзывает прежний ARM новым `bootId`. Старый `output-arm.json` не может автоматически включить игру. После восстановления оператор проверяет картинку и включает ARM заново.
- Ошибка вывода не открывает блокирующий системный диалог. Неперехваченные исключения и rejected promises записываются и завершают соответствующий дочерний процесс для управляемого восстановления.

## Панели и журналы

В админках есть ссылка «Состояние и восстановление». Путь `/__kdw/runtime/panel` позволяет восстановить вывод, перезапустить API, остановить приложение и скачать техническую диагностику.

| Приложение | Основной API | Независимая панель supervisor |
|---|---|---|
| MAX | `http://127.0.0.1:18752` | `http://127.0.0.1:18852/__kdw/runtime/panel` |
| Стелла | `http://127.0.0.1:18751` | `http://127.0.0.1:18851/__kdw/runtime/panel` |

Панели доступны только на локальном интерфейсе. Проверяются Host/Origin; изменения требуют POST с JSON. Основная панель зависит от API, независимая остаётся доступной при его отказе. При завершении самого supervisor временно недоступны обе.

В каждой папке приложения:

- `data/runtime-logs/{supervisor,api,output}.jsonl`: причины выходов, PID/generation, повторные попытки, GPU/дисплеи, причины paint-ошибок; каждые 15 секунд — состояние и RSS дочерних процессов. До 5 файлов по 10 МБ **на роль**, примерно 150 МБ на приложение плюс последняя запись. Ошибки записи журналов не выбрасываются в игровой цикл.
- `data/runtime-faults/`: последние 10 JSON-пакетов при неожиданном завершении дочерних процессов, с ограниченными хвостами технических логов. Фото, голосовые записи и дампы памяти в HTTP-выгрузку не входят.
- `data/runtime-crashes/<role>/`: локальный Crashpad, `uploadToServer:false`. Очистка при запуске и раз в минуту: до 3 `.dmp` / 60 МБ на роль, суммарно до 9 / 180 МБ после очистки. В момент падения возможен краткий выход за лимит. Дампы могут содержать память процесса; их не публиковать и не прикладывать к публичным багрепортам автоматически.
- `data/supervisor.json`, `runtime.json`, `output-worker.json`: владельцы процессов. `runtime-desired.json` хранит намерение оператора, не секреты.

Сбор дампов использует [официальный crashReporter Electron](https://www.electronjs.org/docs/latest/api/crash-reporter). Наличие файла для каждого вида native-сбоя не гарантируется; Windows WER остаётся независимым источником сведений. В тестах ниже проверены ограничения хранения, а не воспроизведение конкретного `0xc0000409` с получением дампа.

## Windows watchdog и обновления

`launcher/Install-RuntimeWatchdog.ps1 -AppRoot <папка приложения>` готовит интерактивную задачу `KDW-Runtime-<app.id>`: запуск после входа пользователя, до трёх повторов при аварийном выходе supervisor с интервалом минута. Скрипт не запускает приложение и отказывается заменять чужую задачу с другим путём. Windows до входа в интерактивную сессию не считается готовым графическим стендом.

`Launch.ps1` использует установленную задачу, иначе запускает supervisor напрямую. `Control.ps1` умеет остановить его через независимую панель, если API недоступен. Без установленной задачи автоматическое восстановление после завершения **самого supervisor** отсутствует; дочерние процессы восстанавливаются в обоих режимах.

Обновлён существующий `ops/production-build/deploy-sound/install.ps1`, без создания ещё одного установщика: резервная копия файлов, сохранение режимов, регистрация watchdog, восстановление прежней задачи либо удаление вновь созданной при откате. Скрипты прошли синтаксическую проверку. Регистрация и работа задач на production-ПК подтверждены при установке RESILIENCE-20261027-1. Повторный вход в Windows и принудительный rollback с Task Scheduler не проверялись.

## Что проверено

- `npm run build:shared`, `build:max`, `build:stela`: успешная локальная сборка; C++ мост собран MSBuild Release и помещён в `apps/max-game/launcher`.
- `npm run test:audit:all`: прошёл полный набор программных и браузерных регрессий, включая сохранение профиля и retention.
- `npm run test:runtime`: 10 тестов политики повторов, IPC, журналов, дампов, GPU fence/карантина и отзыва старого ARM при reload.
- `node ops/production-build/runtime-resilience-integration.cjs`: реальные локальные Electron-процессы обоих приложений; kill вывода сохраняет PID API; kill API заменяет его и владельца интерфейса; зависший worker заменяется, цикл сбоев ограничивается; диагностика фиксирует timeout; restart API успевает подтвердить запрос; чужой Origin отклоняется; Stop не отменяется watchdog. [Результат](process-tests.json).
- `node ops/production-build/runtime-resilience-integration.cjs --spout`: тот же сценарий MAX на локальном GPU с двумя настоящими потоками; состояние и измеренные счётчики записаны в [отдельный результат](spout-process-tests.json). Это проверка sender, не визуальная приёмка TouchDesigner. На RTX 5070 Ti после перевода фона на собственный RAF за примерно 3 секунды счётчик фона вырос с 72 до 253, контента с 47 до 229 — около 60 кадров/с обоих слоёв. Предыдущий вариант с IPC-таймером давал около 40 кадров/с фона и заменён. Короткий замер не подтверждает целевой показатель в 60-секундных окнах на production-приёмнике.

Тесты работают во временных каталогах `.cache/resilience-integration-*`, на портах 19251/19252 и 19351/19352. Production-настройки, задачи Windows и активные игры они не изменяют. Длительная стабильность памяти, 55+ FPS на реальном приёмнике, восстановление после driver reset/отключения дисплея, 30-минутный аппаратный и 8-часовой непрерывный прогон остаются этапом приёмки. Нельзя выдавать эти короткие проверки за гарантию отсутствия любых вылетов.

Снимок чтения получен **27.10.2026 в 15:45 МСК**, [данные аудита](pc-audit.json). Проверка не меняла драйверы, GPU selection, HAGS, TDR, режимы запуска или дисплеи.

| Runtime / native-модули | Electron, D3D compiler, Vulkan/SwiftShader, MAX bridge и native audio Стеллы присутствуют | То же |

**Замечания:**

- На MAX Windows записала BEX64 / `0xc0000409` для Electron, сбойный модуль `ntdll.dll`. Это подтверждает native-завершение, но **не устанавливает первопричину**. Также в выбранном интервале есть `nvlddmkm` 14/153 и Kernel-Power 41. Их связь с последним падением приложения не доказана.
- На Стелле есть `RADAR_PRE_LEAK_64` для Electron: сигнал для контроля памяти, а не доказанная утечка конкретного модуля. В системных журналах также были аварийные перезагрузки и переходы в сон по Application API.
- HAGS включён на обоих ПК; пользовательские TDR overrides не найдены. Менять их без воспроизведения и сравнения не стали.
- На MAX явное предпочтение дискретной GPU найдено для TouchDesigner, но не для portable Electron. Для dual-GPU ПК это пункт аппаратной приёмки: сравнить adapter LUID мостa и GPU приёмника. Автоматически отключать Intel или изменять выбор GPU не стали.
- Отключены Bluetooth PAN на MAX и NewTek WDM на Стелле (код 22); признаков отсутствующего NVIDIA-драйвера нет. Это не подтверждение работоспособности каждого аудиоканала, камеры и периферии.
- HTTP health обеих установленных сборок не ответил в пределах 2 секунд во время снимка. По этому снимку нельзя объявить приложения работающими. В рамках проверки они не запускались и не перезапускались.

Вывод аудита: необходимые основные GPU/runtime-компоненты присутствуют и таймеры сна настроены; утверждать, что стенды полностью аппаратно стабильны, пока нельзя. Следующий сбой следует сопоставлять по времени с локальным runtime bundle, dump и Windows WER/System, а не объяснять только JavaScript-ошибкой или версией драйвера.
