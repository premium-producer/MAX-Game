# Связанные сборки MAX и Стеллы — 23.10.2026

**Следующая архитектура, 27.10.2026:** [независимая работа Стеллы и MAX, отдельная доставка фото](STELA_MAX_ASYNC_ARCHITECTURE.md). Это подготовленный проект v2, ещё не внедрённый; ниже описана действующая связка v1.

**Production-итерация реализована 23.10.2026.** Параметры находятся в runtime JSON; текущие решения и операторские действия — [STAND_SETTINGS.md](STAND_SETTINGS.md). Подробные результаты — [проверки](verification-stand-production-20261023/README.md). Физическая установка и проверка на стенде ещё не выполнены.

Подготовлены переносимые Windows-сборки `KDW-MAX-STAND-PRODUCTION-20261023` и `KDW-MAX-STELA-STAND-PRODUCTION-20261023`. Дополнительно подготовлены production-комплекты для одного и двух ПК; см. [PRODUCTION_KITS.md](PRODUCTION_KITS.md). Публичные сайты этим изменением не обновлены.

Папки `STARTUP`, `stela`, `max-game` должны лежать рядом. Запуск — `apps/STARTUP/Start.bat`. Окна используют прежние порты 18751/18752. Порядок запуска свободный: недоставленная миссия остаётся в очереди Стеллы до запуска MAX. Для самостоятельного запуска игры без приёма назначений доступен параметр `link=0`.

После выбора миссии Стелла создаёт `gameId` (UUID), сохраняемый при пересъёмке и подтверждении. Выбор другой миссии создаёт новый ID. На результате после подтверждения снимка или явного «Без фото» она передаёт `gameId`, исходный `voiceSessionId`, миссию, аудиторию/цель и чистый JPEG 1080×1920. В MAX этот же `gameId` становится **реальным `state.sessionId` ядра**, ключом сохранения IndexedDB и записи сервера. `business-promotion` Стеллы сопоставляется с `business` игры; остальные ID миссий совпадают.

MAX автоматически открывает назначенную миссию и ждёт реального удержания ладони. На подход отведено 30 секунд; при неявке — следующий FIFO либо standby. Каждое задание получает 60 секунд с автозачётом, 120 секунд без касаний возвращают standby, финальный QR показывается 15 секунд после готовности GPU. Хаб больше не освобождает финальную запись своим прежним 30-секундным таймером: ядро подтверждает окончание показа. Обычный перезапуск сохраняет ID, фото, ответы, прогресс и закреплённые сроки в IndexedDB; отключение окна не обнуляет отсчёт. Следующий посетитель получает отдельное сохранение. Общая политика передаётся через /__kdw/settings; параметры и режимы описаны в STAND_SETTINGS.md.

Снимок применяется к 17 подготовленным SVG: аватар, исходный портрет, звонки/общение, цифровой ID и подготовленные профили. Нативные поля регистрации бизнеса используют тот же аватар. Геометрия кругового guide и обрезки сохранена; эмблема выбранного бизнеса и официальный бот независимы. При выборе без фото используется нейтральный силуэт, а не тестовая фотография. Исходные reviewed assets на диске не переписываются: динамические SVG имеют отдельный путь `assets/kdw-linked/<gameId>/…` и SHA256. Они обслуживаются с `Cache-Control: no-store`.

Передача проходит через сервер Стеллы, а не прямой cross-origin запрос браузера. Он проверяет текущий voice lease, token, result stage, revision, gameId и наличие подтверждённого фото. Миссия и аудитория берутся из серверного контроллера. MAX проверяет отдельный pairing key; веб-страница не может выбрать адрес приёмника. Тот же ID и содержимое возвращают прежнюю квитанцию; изменённое содержимое с тем же ID отклоняется. Потерянный ответ приводит к повторной доставке. Дисковые записи заменяются атомарно.

Данные находятся только в закрытых каталогах `data/`, вне `www` и Git:

- `stela/data/link/outbox/<gameId>.json` — очередь и подтверждение доставки. После подтверждения байты снимка удаляются из этой копии.
- `max-game/data/link/key.json` — случайный секрет соединения; соседняя Стелла читает его автоматически.
- `max-game/data/link/games/<gameId>.json` — назначение, фото, служебные ID/статус и последняя квитанция прогресса; `active.json` указывает активную игру.
- Полное игровое сохранение остаётся в прежнем Electron `data`/IndexedDB. Для переноса действующей игры копируют **оба каталога data после закрытия окон**.

Фото принимающей стороны и недоставленные фото имеют срок 24 часа; очистка выполняется при обслуживании записи/очереди работающим сервисом. Метаданные MAX старше 30 суток удаляются при следующем приёме, кроме активной записи. Лимит — 200 одновременно ожидающих/активных назначений; завершённая история в этот лимит не входит. Переполнение возвращает ошибку, а не удаляет действующую игру. Фото не попадает в Qwen, журнал диагностики или публичную статику. Это новое, явно запрошенное пользователем исключение из прежнего правила «снимок только в памяти окна».

Для отдельного защищённого приёмника сервер Стеллы умеет читать `data/game-link.local.json`: поля `gameOrigin` (HTTPS либо HTTP loopback) и `key` (ключ MAX). В новом production-комплекте настройку выполняет Configure-Link.bat: ввод IPv4 и закреплённый сертификат уникальной пары, HTTPS-приёмник18753 на MAX. Из публичного web-export добавлен только проход `/__kdw/link/submit` через прежнюю проверку Origin; сам приёмник MAX должен разворачиваться отдельно, статический сайт игры его не заменяет.

Канонический протокол — `apps/STARTUP/tools/game-link.cjs`; `sync-game-link.mjs` копирует его в оба launcher. MAX подключает UI через `kdw-game-link.mjs` и `adapt-stand-main.mjs`; замороженная stand-base не меняется. Голосовой Qwen/VAD/AEC/VST тракт не менялся, локальные конфиги и полные пресеты сохранены. Снимок камеры и команда выбора проходят прежние guards и анимации.

Проверки: [протокол и восстановление](verification-linked-builds-20261023/link.test.cjs), [два окна Electron](verification-linked-builds-20261023/browser-checks.json). Сквозной прогон использует синтетическую камеру, голос выключен; реальная камера/микрофон и второй физический ПК здесь не проверялись.
