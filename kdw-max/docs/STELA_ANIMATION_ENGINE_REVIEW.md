# Движение стелы: пересмотр решения после регрессии

Продолжение: по запросу пользователя выполнен [точечный откат анимации](verification-20261021/stela-animation-rollback/README.md) с сохранением новых финалов. Новый движок и описанный ниже эксперимент не запускались; рекомендации остаются анализом.

21.10.2026 пользователь сообщил: после переработки анимация стала значительно хуже. Это фактическая отрицательная визуальная приёмка. SOFT-SURFACES нельзя считать успешным исправлением по прежнему изолированному A/B. Текущая FINAL-MISSIONS сохраняет эту систему плавания; её последний перенос результатов отдельно не менял surface-motion/HybridSelection. В этом разборе runtime/код/параметры не изменены.

## Что известно и что остаётся гипотезой

В активном HybridSelection:9WAAPI-анимаций transform/translate3d, отдельная трансформация вложенной кнопки, общий дробный scale1080×1920, крупные2×PNGматериалы, filter/drop-shadow, живой backdrop-filter+mask на стекле и5frame-read геометрии дляLumiCells. В предыдущей попытке несколько этих факторов изменены одновременно. Тест прямого края одной back-кнопки показывал только локальную стабильность профиля при заданном перемещении, не пропуски/время кадров полного UI с живым фоном/голосом/фильтрами.

Кандидаты для проверки: лишние compositing-слои/промежуточные фильтры, повторное пересэмплирование текста/материала под родительскимscale, затратное живое размытие, согласованность часовDOMиGPU. Увеличение количества ключевых точек само по себе не доказывает плавность и не установлено причиной регрессии. Реального профиля GPU/paint/compositor пользователя в этой итерации нет. Не следует утверждать, что каждый getBoundingClientRect обязательно вызывает layout либо что WAAPI всегда выполняется вне главного потока.

## Рекомендуемый следующий эксперимент

Не переносить всюстелу без сравнения. Сделать отдельную тестовуюстраницу одного экрана выбора:4карточки+4плашки+back. ВариантA — облегчённыйDOM, вариантB — PixiJS с тем же размером/траекторией/видимым материалом. Предыдущую рабочую систему можно включить третьимконтролем при наличии точного среза. Новые финальныеэкраны/фото/Controller/голос не откатывать вместе с экспериментом.

Один владелец позиции наэлемент, движение по времени без округления доцелыхpx, затемhover/press, затемизмерение и фон. ДляPixiJSподобратьresolution/antialias под фактическийDPR, проверить ценуфильтров и не перерисовыватьтекст каждыйкадр. На обоихвариантах сначала сопоставимая сцена безживогоblur, затемотдельно включать эффекты. Сравнение только разныхматериалов без фиксации этихусловий снова будет неоднозначным.

Существующий пиксельныйфон — отдельныйWebGLрендерерLumiCells. Другойcanvas поверх него автоматически не получает его содержимое длястекла. Настоящее размываниефона потребует совместного рендера/явнойпередачи текстуры с оценкойстоимости; простая стекляннаястилизация не должна называться реальнымbackdropblur. Контракт состояний ИИ можно сохранить в обоихвариантах.

Приёмка на реальномПК: записатьбраузер/GPU/viewport/WindowsDPI, смотретьполныйэкран в движении, frame-time/p95/пропуски, затратыpaint/composite и стабильностьконтуров. Изолировать влияниефона/фильтров, повторить во время локального тестовогоPCM/RTC безновыхоблачныхгенераций. Прежниеавтотесты маршрутов остаются функциональными, не доказательствомкачестваанимации. Решение о переносе — после сравнения, без обещания «движок исправит всё».
