# RESILIENCE-20261027-1 — установлено 27.10.2026

Оба приложения MAX и Стелла обновлены на обоих production-ПК: MAX / DR7 (DESKTOP-64J4BMN), Стелла / DR2 (DESKTOP-DBD624H). CHUWI и TouchDesigner не менялись.

Пакет: 36 изменённых файлов, ZIP 336 385 байт. Доставка заняла 2,37 секунды на MAX и 2,57 секунды на Стеллу. Использован существующий установщик с проверкой SHA256 и резервной копией.

Оба установщика завершили работу с phase=complete; на каждом ПК сохранены контрольные суммы 10 файлов настроек. Звуковые панели доступны, библиотеки сохранились: MAX 32 файла / 16 событий, Стелла 13 файлов / 11 событий.

Перед обновлением обе программы на обоих ПК были остановлены. После установки работают API/админки и supervisor, графический вывод остаётся выключенным (outputEnabled=false), ARM не включался. Production-Spout и полноэкранная Стелла в этой установке не запускались; короткий GPU-тест был локальным в предыдущей итерации.

На обоих ПК проверены работающие задачи KDW-Runtime-kdw-max-game и KDW-Runtime-kdw-max-stela, отдельные PID API/supervisor, доступность диагностики, существование каталогов локального Crashpad и ненулевые api.jsonl / supervisor.jsonl. Журнал output.jsonl начнёт заполняться при следующем запуске сцены. Нативное падение специально не вызывалось; фактическое создание дампа при следующем конкретном типе сбоя не гарантируется.

## Где искать причину сбоя

В каждом приложении внутри `C:/KDW-Stand/releases/KDW-Stand-20261027-RC4-1/apps/<max-game или stela>/data/`:

- `runtime-logs/` — выходы процессов, GPU/renderer-ошибки, heartbeat, память и повторные запуски
- `runtime-faults/` — последние технические пакеты при неожиданном завершении дочерних процессов
- `runtime-crashes/` — локальные дампы; автоматическая отправка выключена

В админке: «Состояние и восстановление» → «Скачать диагностику». Независимые локальные панели: MAX `http://127.0.0.1:18852/__kdw/runtime/panel`, Стелла `http://127.0.0.1:18851/__kdw/runtime/panel`.

Если падает графический worker, API продолжает работать. Повторные сбои ограничены бюджетом; после его исчерпания состояние degraded требует оператора. Старый ARM не восстанавливается автоматически. Содержимое дампов памяти не следует публиковать: оно может включать пользовательские данные.
