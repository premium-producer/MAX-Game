# Управление текущей игрой MAX — 28.10.2026

Готово локально. Стенды не обновлялись. Объём и навигация по отдельным экранам согласованы пользователем до разработки.

В существующую /admin/ добавлен раздел «Текущая игра»: миссия, задание, screenId и номер экрана, стадия, оставшееся время; запуск одной из четырёх миссий; Назад/Вперёд по отдельным экранам; завершение сессии с возвратом в главное меню. Данные обновляются существующим опросом раз в секунду. Пропавшие/устаревшие данные и незавершённый переход отключают навигацию; значение времени не выдаётся за свежий отчёт при отсутствии renderer. Панель доступна по прежнему LAN-входу, его allowlist и Origin-проверки сохранены.

## Архитектура и границы

- Существующий operator HTTP → API worker → supervisor RPC → output worker → sandboxed preload → зарегистрированный обработчик движка. Исполняемые строки JavaScript по сети не передаются. Native reply принимается только от content webContents с ожидаемым UUID.
- Разрешены только next/back; переход сверяет sessionId/runId/status/mission/task/screen. Сервер защищает запуск и завершение по ожидаемому active gameId. Повторы блокируются на время обработки, устаревшая команда не применяется к следующему экрану/посетителю.
- Ядро добавляет receipt-backed OPERATOR_GOTO, требующий внутреннего trusted контекста. Application-port разрешает его только при operatorControls=true, заданном для штатного desktop preload. Обычный sendCommand и managed/server facade права не получают. Сохранённая история восстанавливается с новыми квитанциями; обычные visitor ACT и production-запреты сохранены.
- Визуальная смена использует существующий fade. Новый runId снимает старые касания; операторский переход не запускает заново вступительную анимацию ладони. Короткий null controller при смене сессии допускается диагностикой.
- Переходы помечаются operatorControlled/operatorTasks. Просмотр оператором не засчитывает пропущенные задания как самостоятельные достижения посетителя. Текущие черновики ввода сохраняются.
- Запуск оператором доступен независимо от способа входа «Стелла/вручную/оба». Он отменяет только текущее назначение, создаёт новое с нейтральным фото и оставляет остальных ожидающих в FIFO. Завершение сессии не удаляет очередь; следующий ожидающий может быть приглашён штатно.
- Фото, тексты посетителя и секреты в мониторинг не включены. Исходники MAX source/operator являются каноническими; www/admin генерируется build:max. Общие runtime/game-link изменены в apps/STARTUP/tools, выполнен build:shared.

## Проверки

183 теста MAX, 14 runtime и 16 link; отдельно четыре новых проверки ядра/доверенного application-port: обход всех экранов всех миссий в обе стороны, replay, неверные/чужие targets, запрет обычным игровым командам и отсутствие ложного visitor completion. IPC-тест проверил sender, дубли и тайм-аут. build:max и check:generated прошли.

Браузер использует реальную собранную игру и HTTP-админку с эмуляцией только desktop transport: запуск при режиме «только Стелла», цифровой ID next/back, устаревший запрос, смена на блогера с отменой предыдущего gameId, next/back в блогере, закрытие до standby, Origin 403. Ошибок JavaScript нет. Именно аппаратный Spout/LiDAR путь нового IPC на стенде ещё не проверялся.

Запущен test:audit:all: все не-браузерные этапы, profile и retention прошли. Общий browser-check выполнил функциональные сценарии MAX и Стеллы, но строгая проверка console.errors завершилась ошибкой из-за HTTP 409 в Stella audience/result. Это не отмечено как успешный общий аудит; результаты в general-browser-audit.json. Эти ответы Стеллы в данной задаче не исправлялись. В специализированном operator-сценарии ожидаемые 409 при отзыве прежней сессии не считаются исключением JS.
