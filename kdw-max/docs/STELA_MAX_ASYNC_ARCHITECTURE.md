# Независимая работа Стеллы и MAX

Архитектурное решение от 27.10.2026. **Основной независимый обмен реализован; ниже сохранён полный целевой проект.** Фактический контракт, ограничения первой реализации, проверки и поставка описаны в [отчёте реализации](verification-async-link-20261027/README.md). Не все дополнительные механизмы этого проектного документа входят в первый выпуск.

Восстановление процессов, Spout и renderer описано отдельно в [архитектуре устойчивости production](PRODUCTION_RESILIENCE_ARCHITECTURE.md). Независимая доставка между ПК сама по себе не изолирует native/GPU-сбой внутри MAX.

## Цель

Посетитель проходит Стеллу до результата независимо от доступности MAX. MAX после получения миссии играет независимо от Стеллы. Фотография подтверждённого посетителя доставляется в MAX отдельно и не блокирует ни переход со Стеллы, ни начало или продолжение игры.

Независимость относится к связи между приложениями. Она не отменяет необходимость собственного работающего сервера, камеры для съёмки, внешнего AI для голосовых ответов и исправного вывода игры. Исчезновение HDMI/Spout-сигнала и потеря API — разные неисправности.

Физическая схема: Стелла — DESKTOP-DBD624H / DR2, 10.0.0.12; MAX — DESKTOP-64J4BMN / DR7, 10.0.0.13. Идентичность задаётся проверенной конфигурацией пары, а не названием ПК или одним IP. Роли: `ops/production-build/stand-roles.json`.

## Что уже есть и что меняется

| Область | Сейчас | Следующая версия |
|---|---|---|
| API | Свой сервер у каждого приложения | Сохраняем |
| Настройки Стеллы | Запрос MAX при начале, затем кэш/defaults; возможна задержка | Собственная локальная конфигурация, синхронизация совместимых настроек в фоне |
| Передача результата | JSON миссии и base64 JPEG одним сообщением | Малое сообщение миссии и независимая загрузка JPEG |
| Надёжность | Дисковая outbox, повторы, проверка ключа/TLS | Сохраняем; добавляем отдельные очереди миссий и фото, явные ревизии и сроки |
| Завершение Стеллы | Возврат с результата зависит от статуса доставки | Возврат не зависит от MAX; доставка продолжается сервером |
| Фото в MAX | Получение манифеста связано с загрузкой игры | Локальный placeholder доступен сразу, фото обновляется отдельно |
| Готовность | Приём API и состояние назначения; доступность частично определяется heartbeat | Отдельные состояния API, вывода, ввода и конкретного приглашения |

Основание: `apps/STARTUP/tools/game-link.cjs`, `game-link-network.cjs`, `apps/max-game/source/client/src/kdw-game-link.mjs`, `use-omni-prototype.ts` и `delivery-status.ts` в исходниках Стеллы. Существующие гарантии после claim, сохранения прогресса и визуального допуска остаются обязательными.

## Владение состоянием

| Компонент | Единственный владелец |
|---|---|
| Диалог, выбор, подтверждение снимка, текущий посетитель | Сервер Стеллы |
| Исходящий результат и подтверждённый JPEG до доставки/истечения | Локальное хранилище Стеллы |
| Очередь принятых миссий, приглашение, claim, прогресс и завершение | Сервер MAX и существующее игровое ядро |
| Полученный JPEG и его применение в игре | Локальное хранилище и renderer MAX |
| Тайминги, звук и параметры Стеллы | Локальные настройки Стеллы |
| Режим входа, тайминги игры, лидар, ARM | Локальные настройки MAX |

Браузеры общаются только со своим сервером. Сетевой обмен выполняют серверные фоновые workers. Центральный брокер, интернет и облачное хранилище для связи двух ПК не нужны. MAX не делает обратный синхронный запрос к Стелле для загрузки сцены или фотографии.

Стелла отправляет события и читает статусы MAX. Прямой сетевой push статусов обратно на Стеллу для первой версии не требуется: фоновый опрос даёт ту же независимость и сохраняет одну настроенную TLS-точку входа. Каждый UI получает состояние из локального API.

## Путь посетителя

1. Стелла открывается на локальных настройках без ожидания MAX. Проверка соседа запускается параллельно.
2. Диалог, ручной выбор и фото работают как обычно. До подтверждения снимка данные никуда не передаются; «Без фото» не порождает загрузку.
3. На результате локальный сервер атомарно сохраняет миссию. После этого UI получает `accepted-local`, даже если MAX выключен. Сохранение JPEG и его доставка имеют отдельный статус.
4. Стелла показывает результат и доступное действие завершения. Автовозврат следует её локальному таймингу после готовности экрана/озвучки, без проверки доставки. Сброс UI не удаляет уже принятую outbox-запись.
5. MAX принимает миссию, подтверждает сохранение и ставит её в очередь. Отсутствие JPEG не препятствует приглашению и удержанию ладони.
6. Игра использует нейтральный аватар до готовности фото. Снимок загружается и декодируется в фоне, затем обновляет только визуальные ресурсы этого посетителя.
7. Обрыв связи во время игры не вызывает выход, перезапуск или отмену. Финал, QR, таймеры и освобождение активного посетителя остаются под управлением MAX.

Если локальное сохранение миссии невозможно, Стелла всё равно показывает выбранную рекомендацию, но не утверждает, что она сохранена/доставлена. Отдельное сообщение предлагает повторить передачу; техническая причина видна оператору. Сбой записи фото не отменяет успешно сохранённую миссию.

## Протокол v2

Базовый префикс сетевого MAX API: `/__kdw/link/v2`. В следующем контракте ответы обязательно содержат `protocolVersion`, `receiverInstanceId`, `stateRevision`. Перезапуск приёмника меняет instance ID; клиент перечитывает snapshot, а не сравнивает ревизии разных экземпляров.

| Запрос | Назначение и подтверждение |
|---|---|
| `GET /capabilities` | Поддерживаемые версии, лимит JPEG, возможности late-photo и readiness |
| `POST /missions` | Сохранить миссию без бинарного фото; ответ `accepted` только после атомарной записи |
| `PUT /missions/{gameId}/photo/{photoRevision}` | Передать бинарный JPEG; подтвердить после проверки и атомарного сохранения |
| `GET /missions/{gameId}` | Назначение, приглашение, состояние фото, ревизии и код причины |
| `POST /missions/{gameId}/cancel` | Идемпотентно отменить не начатое назначение; после claim вернуть `already-playing` |
| `GET /readiness` | Доступность приёма и готовность вывода/ввода; без персональных данных |

На локальном API Стеллы: `POST /__kdw/link/v2/submit` принимает результат в свою outbox, `GET /__kdw/link/v2/local-status/{gameId}` возвращает сохранённый локальный статус без сетевого ожидания. Авторизация через собственный session token и серверную проверку stage/revision сохраняется. После сброса UI доставки идут с серверной идентичностью пары, а не с истёкшим токеном браузера.

### Сообщение миссии

Поля: `schemaVersion=2`, `messageId`, `gameId`, `voiceSessionId`, монотонный `selectionRevision` внутри одного посетителя, `missionId`, `audience`, `goal`, `createdAt`, `expiresAt`, `remainingTtlMs`, `photoIntent`.

`photoIntent` — `none` либо `{photoRevision, status: expected}`. Это намерение, а не условие принятия миссии. MIME, размер и SHA256 JPEG передаются в запросе фото; `confirmed-local` у Стеллы не означает `stored` у MAX.

`gameId` остаётся реальным session ID игры. Повтор сообщения с тем же ID и семантическим содержимым возвращает исходное подтверждение. Изменение mission/audience/goal с тем же ID — конфликт. Поля повторной доставки и уменьшающийся остаток TTL не входят в семантический хеш; они не могут продлевать уже установленный deadline.

Более новый выбор одного `voiceSessionId` замещает более старый только до claim. MAX сохраняет наибольший `selectionRevision`, поэтому запоздавший пакет старого выбора не вытеснит новый. После claim никакое новое событие выбора, cancel или истечение приглашения не отменяет активную игру. Claim, отмена, замена и приём фото согласуются одной короткой локальной транзакцией на gameId; сетевых ожиданий внутри неё нет.

### Состояния

Не объединять три независимые оси в одну строку «готово»:

- Доставка: `pending → sending → accepted`, отдельно `expired / rejected`.
- Назначение MAX: `queued → invited → playing → completed`; отдельно `cancelled / superseded / no-show / expired`. Недоступность API/вывода — состояние готовности, не новый игровой прогресс.
- Фото: `none` или `expected → receiving → stored → applied`; отдельно `failed / expired`. `applied` подтверждает renderer, а не HTTP-сервер.

Оператор различает «получено сервером», «приглашение показано», «игра началась», «фото применено». Поздний статус от предыдущего instance/revision не откатывает более новое состояние.

## Фото без блокировки игры

Сохраняем существующий формат: подтверждённый JPEG 1080×1920, до 4 МиБ. Приёмник проверяет размер, сигнатуру, декодируемость/геометрию и SHA256, а также соответствие `gameId + voiceSessionId + photoRevision`. Произвольные пути и внешние URL не принимаются.

Фото хранится отдельным файлом в private `data/`, не base64 внутри задания. Запись — временный файл → проверка → atomic rename → обновление метаданных → ACK. После обрыва повторяется только JPEG; миссия не отправляется заново. Первый вариант обходится без chunk-upload для файла до 4 МиБ. Если замеры потребуют возобновления по частям, оно добавляется без изменения контракта миссии.

Фотографический worker начинает загрузку после ACK миссии. Если ACK потерян, повтор миссии возвращает существующее назначение. Если фото пришло к ещё неизвестной миссии, MAX возвращает retryable `MISSION_NOT_ACCEPTED`, не создаёт сиротский файл. Удаление/замена миссии во время загрузки проверяется повторно перед фиксацией JPEG; временный файл очищается.

В MAX:

- Placeholder и все необходимые SVG доступны локально сразу. Ошибка запроса фотографии/фото-манифеста не включает общий экран восстановления игры.
- `photoRevision`/SHA меняют только персонализированные ресурсы. Они не меняют `contentRevision` игрового каталога, session ID, ответы, маршрут и таймеры.
- Фото применяется ко всем прежним точкам персонализации: аватару, подготовленным SVG, звонкам, цифровому ID и полям профиля. Эмблемы бизнеса и официальный бот остаются самостоятельными.
- Ресурс сначала загружается и декодируется вне видимой сцены. Затем текущий аватар/портрет заменяется мягко, если данный компонент допускает замену; иначе — при следующем появлении экрана. Структура экрана не пересоздаётся, переход не повторяется, взаимодействие не блокируется.
- URL включает gameId, ревизию фото и SHA. Старый async callback не применяется после ухода с игры или смены посетителя. На cleanup сбрасываются binding, GPU-ресурсы и object URL.
- Если JPEG не доставлен, повреждён или просрочен, посетитель заканчивает игру с нейтральным аватаром. Ошибка фото видна оператору, но не становится экраном ошибки игры.
- После завершения/освобождения игры или явной отмены фото не применяется и не возрождает назначение. При восстановлении ещё активной игры после перезапуска используется её сохранённое фото.

## Readiness и пользовательские подписи

`apiReachable` означает только ответ API. Дополнительно нужны `acceptingMissions`, `rendererReady`, `outputReady`, `inputReady`, `armed`, `busy`, `observedAt`, `validForMs`, `reasonCodes`.

MAX может сохранять миссии при неготовом выводе. Статус `invited` выдаётся только для конкретного gameId после допуска и подтверждения показа приглашения renderer. Таймер подхода начинается при этом подтверждении, а не при доставке JSON. Автоматический ARM по восстановлению связи запрещён.

Spout sender сам по себе не доказывает, что изображение дошло до стены. `outputReady` опирается на имеющийся визуальный допуск оператора; heartbeat TouchDesigner, если будет добавлен, помечается отдельным источником. Физическую исправность проектора/HDMI нельзя объявлять по ответу HTTP. Диагностический статус без свежих данных становится `unknown`.

| Ситуация | Поведение Стеллы на результате |
|---|---|
| Конкретное приглашение показано и готово | «Миссия готова! Приложите ладонь к игровому экрану» |
| MAX занят | «Миссия выбрана! Дождитесь приглашения на игровом экране» |
| Данные сохранены локально, MAX недоступен | «Миссия выбрана! Игровой экран пока недоступен» |
| Фото ещё едет, приглашение готово | Обычное приглашение; ожидание фото не показываем |
| Локальное сохранение не удалось | Результат выбора доступен; отдельная возможность повторить передачу без утверждения «сохранено» |

Результат автоматически закрывается по локальной политике Стеллы во всех сетевых состояниях. Он не ждёт бесконечно доставки или статуса игры. Завершение экрана и обычный возврат в standby не равнозначны отмене приглашения; явная смена выбора/отмена отправляет отдельное событие.

## Повторы, актуальность и очистка

- Предлагаемый срок не начатого назначения — 120 секунд с принятия результата Стеллой, включая время офлайна. Это настраиваемый срок обмена, отдельный от действующего таймера подхода. Повторы и перезапуски его не продлевают.
- Стелла считает остаток по монотонным часам, пока процесс жив, и сохраняет deadline. MAX фиксирует свой монотонный deadline по минимальному допустимому остатку при приёме. При восстановлении процесса проверяются сохранённое время и сдвиг часов; откат/неопределённость времени не должны создавать свежее приглашение. Консервативный результат — истечение, с диагностикой для оператора.
- MAX проверяет срок и перед приглашением, и перед claim. После claim этот TTL больше не действует на игру; работают её прежние сроки и recovery.
- Для доставки: немедленная попытка, затем 1, 2, 4, 8 секунд, потолок 10 секунд с jitter. Миссии/отмены имеют отдельную очередь и приоритет перед JPEG. Один медленный upload не задерживает локальный API, другие control-запросы или UI.
- Retry: таймауты, разрыв, 5xx и временная занятость. Невалидные данные/несовместимая версия/ошибка авторизации требуют явной диагностики, без бесконечных быстрых повторов. 429 учитывает Retry-After в пределах TTL.
- При кратком восстановлении подтверждённая ещё актуальная миссия может быть приглашена; запуск всё равно требует ладони. Просроченные события не проигрываются задним числом.
- Объём очереди и фото ограничен. Активные записи не вытесняются ради новых. При заполнении Стелла продолжает консультацию, но честно сообщает локальную невозможность передать результат; фото не должно занимать резерв места для метаданных миссии.
- Предлагаемая очистка: недоставленные фото удаляются при истечении/отмене; MAX удаляет персональные ресурсы после освобождения игры с учётом существующего recovery. Для зависших записей верхняя граница фото — 24 часа. Точные правила recovery/retention согласуются с уже действующим аудитом до реализации; нельзя случайно удалить фото ещё восстанавливаемой активной игры.
- Дедупликационные tombstones без фото сохраняются минимум дольше максимального срока повторов, чтобы старый пакет после очистки не породил новую игру. Ни фото, ни токены, ни полные payload не пишутся в диагностические журналы.

## Безопасность и совместимость

Сохраняем pinned TLS, ключ пары на сервере, ограничение размера, проверку Origin локальных действий и session lease Стеллы. Credentials не передаются renderer и не попадают в Git. Сетевой порт MAX не открывает админ-панель, произвольное чтение файлов или публичную выдачу фото. Readiness и capabilities также требуют авторизации пары.

Порядок миграции: сначала MAX с поддержкой v1+v2, затем Стелла с v2. Возможности проверяет фоновый worker; это не gate запуска UI. На старой паре v1 продолжает существовать до согласованного переключения. При включённом v2 отправитель не переходит молча на v1 с объединённой фотографией: несовместимость показывает оператору и сохраняет результат до истечения срока.

Хранилища v2 имеют отдельный schema/version namespace; старые queued-записи не импортируются автоматически как новые приглашения. Переключение/откат проводят без активного посетителя. Откат кода не проигрывает накопившиеся v2-задания через v1. Сохраняются секреты, app.json, режимы входа и аудио/калибровочные профили.

MAX остаётся в выбранном режиме `stella/manual/combined`. Независимость от Стеллы не включает самовольно ручной выбор миссии: действующая игра продолжается, а при отсутствии назначения показывается штатное ожидание. Изменение режима — отдельное операторское действие.

## План реализации

1. **Контракт и серверные тесты:** схемы v2, независимые состояния, idempotency, selectionRevision/claim, TTL/часы и атомарное хранилище. Общий код — `apps/STARTUP/tools`; обновление копий через `npm run build:shared`.
2. **Автономная Стелла:** локальные настройки и outbox без синхронного обращения к MAX; отдельный photo-worker; независимое завершение результата. Менять canonical source Стеллы, сохранить существующие photo-confirm/retake и голосовые guards.
3. **MAX:** приём v2 и JPEG, readiness, placeholder, асинхронная подмена фото во всех точках персонализации. Изменения генерируемого входа через `apps/max-game/source/adapt-stand-main.mjs`, затем `npm run check:generated`. Игровое ядро и frozen stand-base не переписывать.
4. **Админ-панели:** локальный статус пары, адрес/последний ответ, очередь, срок задания, состояние доставки фото, ошибки и возможность повторной доставки ещё актуального события. Технические ошибки не выносить на весь посетительский экран.
5. **Локальная приёмка:** два изолированных процесса, управляемая потеря сети/ACK, задержка и порча JPEG, перезапуски. Никаких SSH-проверок для разработки.
6. **Разрешённая поставка:** малый патч существующим установщиком по команде пользователя. Сначала совместимый приёмник, затем отправитель; аппаратная приёмка на новых ролях ПК. CHUWI исключён.

## Критерии приёмки

| Проверка | Обязательный результат |
|---|---|
| MAX выключен до запуска Стеллы | Начало/диалог/выбор/фото/результат проходят без сетевого ожидания MAX |
| MAX отключён во время фото или результата | Локально сохранённая миссия остаётся в outbox, Стелла штатно возвращается в standby |
| JPEG медленный, потерян или повреждён | MAX приглашает и проводит игру с placeholder; миссия не переотправляется из-за фото |
| JPEG приходит во время игры | Фото нужного посетителя появляется без reset, повторного перехода, сдвига таймеров или блокировки ввода |
| Следующий посетитель вошёл раньше завершения старого upload | Его аватар не меняется на чужое фото; запоздавший callback отбрасывается |
| ACK миссии или фото потерян | Повтор даёт исходный результат; нет дубликата игры/файла |
| Пакеты старого/нового выбора переставлены | До claim побеждает наибольшая selectionRevision; после claim активная игра сохраняется |
| Истёк TTL, затем вернулась сеть | Старое приглашение и фото не оживают |
| Перезапуск/откат часов | Очередь восстанавливается, сроки не продлеваются; неопределённость не порождает старую игру |
| API работает, но renderer/Spout/ввод не готовы | Сохранение разрешено, приглашение «приложите ладонь» не выдаётся преждевременно |
| Стелла выключена после начала MAX | Игра, её финал и QR работают; remote status не требуется |
| Диск заполнен/очередь переполнена | Нет ложного ACK и надписи «сохранено»; уже начатая игра не повреждается |
| Retake, «Без фото», cancel, несовместимый протокол | Точные серверные проверки; нет старой фотографии, скрытого fallback или повторного запуска |

Измеряем отдельно задержку локального ACK миссии, время доставки control-сообщений, загрузки/декодирования JPEG и кадры при его применении. Цель: local ACK до 200 мс на стендовом SSD при малой очереди; это бюджет для проверки, не уже измеренный результат. Главный инвариант — в критическом пути UI отсутствует ожидание удалённого ПК или JPEG.
