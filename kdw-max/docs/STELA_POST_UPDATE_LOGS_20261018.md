Исторический срез до исправления. Выявленный отказ получения команды устранён в следующей итерации COMMANDS; [реализация и полный голосовой проход](verification-20261018/stela-command-fix/README.md). Факты исходного прохода ниже сохранены.

18.10.2026. Версия `KDW-MAX-STELA-OMNI-P1-WARM-512-20261018`. Последняя завершённая пользовательская сессия: **14:30:55–14:31:44 МСК**, `8afd4685-f875-4cc4-8b76-d1e9a66a5731`. Только production JSONL из `apps/stela/data/logs/voice`; синтетические/браузерные проверки из docs сюда не включены. Четыре голосовых хода, одна начальная отменённая озвучка и одна озвучка после касания «назад».

Источник: `voice-20261018T112823-c7098cd3392f-00001.jsonl`. [Воспроизводимый расчёт](verification-20261018/stela-persistent/analyze-fresh.mjs), [машинный результат](verification-20261018/stela-persistent/fresh-log-analysis.json). Общий операторский отчёт обновлён в `apps/stela/data/voice-analysis/REPORT.md` и summary.json. ## Почему прохождение остановилось

Непосредственная причина подтверждена: на выборе личного использования **канал решения дважды вернул обычный текст вместо function_call resolve_turn**. Есть `response.text.done`, completed response и `command.proposed.parseReason=NO_TOOL_CALL`; команды `personal` нет. Контроллер получает null, возвращает INVALID_COMMAND и сохраняет audience/revision=1. Голосовой канал затем заново произносит тот же вопрос. Это ошибка протокола решения/его обработки, скрытая для посетителя под повторением вопроса.

| МСК, результат решения | Распознанная реплика | Решение | Экран после |
|---|---|---|---|
| 14:30:58,696 | «Привет» | clarify, принято | intro |
| 14:31:12,514 | «Начать» | begin, принято | audience, revision=1 |
| 14:31:25,188 | «личное использование» | NO_TOOL_CALL → INVALID_COMMAND | audience, revision=1 |
| 14:31:37,996 | «для личного использования хочу» | NO_TOOL_CALL → INVALID_COMMAND | audience, revision=1 |
| 14:31:41,560 | касание «назад» | back, принято | intro, revision=2 |

В 14:31:44 локальный WS закрыт, сессия завершена как ws_closed. Конкретную причину закрытия вкладки/соединения без соответствующего события приписывать пользователю нельзя. goal/result не достигнуты, mission.displayed нет. Штатный прототип по-прежнему допускает personal → communication; технического запрета на personal в audience нет. Это не ограничение бэклога бизнеса/блога. Не было SCREEN_BUSY, STALE_REVISION, UI timeout, ошибки микрофона или провайдера. Полные расшифровки обеих реплик пришли, tailMs=512; признаков, что эти конкретные фразы разрезала короткая пауза, нет. ASR диагностическая, не источник управляющего действия, поэтому её правильность не доказывает внутреннюю интерпретацию Omni; отсутствие требуемой команды доказано отдельно.

Что пока нельзя доказать: **почему именно модель перестала вызывать инструмент**. В коде обязательность resolve_turn описана инструкцией, отдельная жёсткая настройка выбора инструмента не задаётся. При session.update передаются только новые instructions. Но журнал текущей версии не сохраняет tools/tool-choice из подтверждённой конфигурации и текст/типы output решения целиком: response.text.done записывает факт, не сам text. Поэтому гипотезы об эффекте истории, частичном обновлении конфигурации или игнорировании инструкции нельзя выдать за установленную причину. JSON с action мог вернуться обычным текстом, но такого текста в журнале нет. Ошибка возникает до валидации конкретного action, а не из-за неверной миссии.

## Насколько быстрее

Сравнение с ранее зафиксированным пользовательским AEC-срезом 13:45:39 МСК: [разбор до обновления](STELA_LATENCY_20261018.md). Старый срез: 5 решений / 4 начавшихся аудиоответа; новый: 4/4. p50 рассчитан одинаковым nearest-rank методом (при N=4 берётся второй отсортированный элемент). Это разные короткие диалоги, не строгий A/B. Два новых ответа не привели к переходу, поэтому быстрый звук не равен успешному выбору.

| Участок | Прежде p50 | Сейчас p50 | Сейчас диапазон |
|---|---:|---:|---:|
| speech.end → решение/отказ | 1571 мс | 964 мс | 925–1049 мс |
| response.create D → response.done | 771 мс | 689 мс | 654–766 мс |
| Решение → первый аудиочанк | 2622 мс | 1093 мс | 860–1585 мс |
| response.create S → первый чанк | 1287 мс | 932 мс | 860–1229 мс |
| speech.end → RTC-отправитель | 4564 мс | **2246 мс** | **1839–2694 мс** |
| Окончание VAD-речи → RTC-отправитель, с паузой | ~5364 мс | **~2758 мс** | **~2351–3206 мс** |

После speech.end p50 уменьшился на 50,8%; с учётом смены паузы 800 → 512 мс — ориентировочно на 48,6%. Последняя строка — сумма измеренного времени и заданного tailMs; физическое окончание речи может отличаться из-за VAD. Звук физической колонки не измерен. RTC jitter buffer: примерно 32–35 мс среднего накопленного буфера, плюс неизвестная аппаратная задержка.

Подтверждение речи: у всех четырёх входов режим ожидания 96 мс; от зарегистрированного кандидата фактически 59–70 мс, поскольку первая 32-мс рамка уже учтена в кандидате. Это не замер абсолютного физического начала речи. Срабатываний режима перебивания 384 мс не было. Конец каждой реплики — 512 мс.

UI-ready для begin занял 653 мс. Начало RTC после первого планирования аудио — 50–52 мс; полная генерация S заняла 2,09–2,74 с и идёт потоково. Три полностью прослушанных ответа длились **10,28 / 8,61 / 8,52 с**: начало ускорилось, но длинное повторение прежнего вопроса всё ещё затягивает диалог.

Подключения: **4 открытия**, а не «всегда два». Два стартовых и по одной ротации D/S после четырёх terminal responses; причина в обоих случаях response_limit. У S в лимит вошло начальное приветствие, отменённое до первого звука. Ротации не прервали проигрывание; S успел прогреться до следующей реплики, ротация D была уже после второго отказа. Сетевых реконнектов и idle timeout в этой 49-секундной сессии нет.

## Самоперебивания

**В этой сессии признаков самоперебивания нет.** Четыре подтверждённых входа соответствуют четырём пользовательским расшифровкам, у всех interrupted=false. Во время озвучки было четыре отвергнутых кандидата VAD; они не создали нового хода и не отменили звук. Причину кандидата (эхо, шум или короткая речь) без акустической записи не установить.

Два playback.interrupted имеют явные причины: touch в момент «назад» и audio_close при закрытии тракта. Первое приветствие отменено по новой реальной реплике «Привет» **до передачи первого аудиочанка клиенту**, не голосом самой стелы. Нет pipeline/provider/runtime errors. Нулевое число ложных срабатываний в 49 с не является полевой приёмкой AEC.

## Следующая правка

Приоритет — надёжность управляющего ответа, затем дальнейшее сокращение задержки. Нужен проверенный обязательный контракт resolve_turn на D, включая сохранность tools после обновления instructions. Если API допускает обычный текст, заранее определить допустимый строго проверяемый формат и безопасную обработку отсутствия команды; не трактовать произвольную речь как переход. NO_TOOL_CALL должен отличаться от смыслового clarify и не создавать незаметный бесконечный повтор вопроса.

В журнал стоит добавить подтверждённые tool count/names/choice и prompt hash, типы response.output, ограниченный обычный текст D (без reasoning, по действующей настройке текстов). Тогда станет видно, вернулась ли допустимая action в обычном JSON или модель просто ответила словами. Контроллер, ревизии, UI-ready и ограничение истории сохранять. Проверить регрессию на точной последовательности **«Привет» → «Начать» → «личное использование» → «хочу общаться с близкими»**, включая повторы и четвёртый ход/ротацию: прежний чистый happy path не поймал этот дефект. Эти исправления этим анализом не выполнены.
